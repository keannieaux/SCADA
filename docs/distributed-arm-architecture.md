# Распределённая архитектура АРМов

Документ является частью ТЗ (ссылка из §5.1). Описывает, как одно и то же
приложение работает в разных ролях на объекте: собирает данные, показывает
их оператору, или делает и то, и другое.

Основная идея — **одна исполнительная поставка, роль станции задаётся
конфигурацией**, а серверная часть может быть встроена в мастер-АРМ или
вынесена на отдельную машину без изменения кода.

---

## Общая концепция

Система состоит из трёх логических частей:

1. **Сервер** (`SCADA.Server`) — опрашивает контроллеры, ведёт архив и
   сигнализацию, обслуживает клиентские подключения по gRPC. Headless.
2. **Клиент** (UI-приложение на Avalonia, проект `SCADA`) — мнемосхемы,
   тренды, аварии, управление. Подключается к серверу.
3. **Общие библиотеки** — `SCADA.Core` (примитивы и модели, ноль
   зависимостей), `SCADA.Runtime` (таблица тегов, движок опроса,
   контракт `IRuntimeClient`), `SCADA.Package` (формат `.scadapkg`).

Один физический ПК может выполнять роль сервера, клиента или обе сразу.

---

## Компоненты системы

### Общие библиотеки

`SCADA.Core` — примитивы, модели и контракты, общие для обеих сторон:
теги и качество, роли и права, схемы, аварии. Ноль внешних зависимостей.

`SCADA.Runtime` — исполнительное ядро: `TagTable`, движок опроса,
сигнализация, архив, сессии, и **единственный контракт UI ↔ ядро**
`IRuntimeClient`. Локальная реализация (`LocalRuntimeClient`) работает
в одном процессе с ядром, будущая remote-реализация — поверх gRPC.
UI выше по стеку эти реализации не различает: ради этого контракт
и спроектирован.

### SCADA.Server

Headless-приложение на `Microsoft.Extensions.Hosting`.

**Задачи:**
- опрос контроллеров (Modbus TCP/RTU, дальше OPC UA);
- ведение архива значений и журнала событий;
- вычисление сигнализации;
- обслуживание клиентских подключений по gRPC (**M7, не реализовано**).

Сегодня проект содержит composition root: регистрацию драйверов, чтение
конфигурации процесса и запуск `RuntimeHost`. Сетевого слоя пока нет —
он добавляется в M7, и **именно этот проект становится gRPC-сервером**,
другого пути в планах нет.

Сборка исходников проекта при старте (когда в конфигурации указан каталог,
а не пакет) — **временное демо-удобство**, уходит вместе с M7: рантайм
исполняет только собранный пакет (§5.4, A5.9).

**Способы запуска:** консольный процесс (разработка), Windows Service
(production на Windows), systemd/launchd (Linux/macOS).

### Клиент (UI)

Avalonia-приложение: мнемосхемы, тренды, таблицы тегов, баннер и журнал
аварий, квитирование, управление. Работает поверх `IRuntimeClient`
и потому одинаково — и на мастере (локальное ядро), и на клиентском АРМе
(ядро по сети).

## Роли ПК на объекте

### 1. Single ARM

Один ПК выполняет все функции: опрос, архив, UI оператора.

**Когда:** один оператор, небольшой объект.

### 2. Master ARM

Один ПК — и сервер, и рабочее место. Остальные ПК — клиенты.

```text
┌─────────────────────┐         ┌─────────────┐
│      ПК мастер      │         │    ПК 2     │
│  UI оператора       │◄───────►│     UI      │
│  Служба сервера     │  LAN    │             │
│  Проект + архив     │         └─────────────┘
│  Связь с ПЛК        │         ┌─────────────┐
└─────────────────────┘         │    ПК 3     │
                                │     UI      │
                                └─────────────┘
```

**Мастер-АРМ всегда с UI.** Это рабочее место, а не только серверная
машина: на нём стоят оба исполняемых, UI подключается к `localhost`.
Принцип «сервер запускается отдельно от GUI» при этом сохраняется —
служба работает независимо, UI можно закрыть и открыть заново.

**Когда:** 2–10 АРМов, отказоустойчивость не критична.

### 3. Dedicated Server

Сервер вынесен на отдельный ПК или ВМ, все АРМы — клиенты. Тот же
исполняемый файл службы, только без рабочего места оператора.

**Когда:** много АРМов, сервер должен работать круглосуточно.

### 4. Client-only ARM

ПК, который только подключается к серверу: рабочие места операторов,
диспетчерская, начальник смены.

Папка проекта такому АРМу не нужна — пакет он получает от сервера
и кэширует (ТЗ §14, M6.5). Управление папками проектов требуется только
там, где работает сервер.

**Кэш клиента — ровно одна версия: та, которой кормит мастер.** Хранить
предыдущие незачем: откатывать проект имеет право только та машина, где он
лежит, а клиенту старая версия дала бы лишь возможность разойтись с мастером.
Кэш существует, чтобы не качать пакет на каждом подключении, и ничего
больше — это зеркало, а не хранилище версий.

**Сверка при подключении обязательна.** Клиент и мастер сравнивают версию
и хеш пакета (то и другое уже есть в манифесте, `PackageManifest`); не
совпало — клиент выбрасывает кэш и качает заново. Без сверки клиент работал
бы по старой модели тегов, а `TagId` присваиваются при сборке: у мастера
номер 417 — «Насос7.Ток», у клиента из старого пакета — «Котёл2.Давление».
Значения пришли бы с качеством Good, схема бы их нарисовала, и это было бы
не то.

**Проект обновили на мастере при живых сессиях** — случай, который нужно
закрыть явно, иначе получится тот же разъезд, только в памяти уже
подключённого клиента.

## Исполнительная поставка и конфигурация станции

### Одна поставка, две программы

Поставка одна: **один установщик**, внутри — служба и UI-приложение.
Отдельных дистрибутивов «для мастера» и «для клиента» нет; роль станции
выбирается конфигурацией при вводе в эксплуатацию.

Два исполняемых файла, а не один процесс с режимами, — потому что служба
стартует **до входа пользователя в систему**, а UI по определению после
(ТЗ §14). Одним процессом это не собирается.

### Файл конфигурации станции

```text
%ProgramData%\SCADA\station.json
```

Содержит:

| Параметр | Смысл |
|---|---|
| Роль станции | `Master` или `Client` |
| Состояние мастера | `Active` / `Standby` (см. «Резервирование») |
| Путь к папке проекта | для роли `Master` |
| Эндпоинт мастера | для роли `Client` |
| Режим аутентификации | `AuthMode`: `Local` или `Full` |
| Сетевые параметры | порт, TLS-сертификат, отпечаток мастера |

Это **не часть проекта и не часть пакета**: конфигурация принадлежит
машине и переживает обновление проекта.

**Почему `%ProgramData%`:**

| Вариант | Почему нет |
|---|---|
| Рядом с exe в `Program Files` | запись требует прав администратора при каждом изменении; обновление программы затирает настройки |
| `%APPDATA%` пользователя | служба стартует до входа пользователя, путь ей недоступен |
| Реестр | вся идеология системы файловая: бэкап копированием, настройки читаются человеком на объекте |
| Папка проекта | у клиентского АРМа папки проекта нет вообще, а настройки нужны именно ему |

### Защита настроек

Два слоя:

1. **ACL на файл** — запись только администраторам станции. Оператор
   физически не может подменить эндпоинт или роль.
2. **Право `ManageStation`** — изменение настроек из работающего UI
   требует этого права; саму запись выполняет служба по запросу,
   проверив право. Тогда для штатной смены настроек не нужен админ
   Windows, а оператор без права не сделает ничего.

Первичная настройка на свежей машине защищается только операционной
системой: проекта ещё нет, ролей нет, защищать нечем. Это та же граница
защиты, что в модели угроз подсистемы пользователей
(`docs/users-plan.md` §4.3).

`ManageStation` — **новое системное право**, шестое. При его введении
правится и `SystemPermissions`, и текст `users-plan.md` §2.1, где сейчас
сказано «ровно пять». Реализуется вместе с настройками станции, не раньше.

### Поиск мастера клиентом

- **Сканирование сети — подсказка, а не источник правды.** Оно избавляет
  от ручного ввода IP, но выбранный эндпоинт **фиксируется в конфигурации**.
- **Личность мастера проверяется** (TLS-сертификат или его отпечаток).
  Иначе подмена мастера в сети даёт полный контроль над тем, что оператор
  видит на экране и какие команды уходят на объект.
- **Ручной ввод эндпоинта остаётся полноценным путём**: на объектах
  мультикаст часто запрещён политиками сети.

## Взаимодействие компонентов

### Клиент ↔ сервер

Единственный транспорт — **gRPC** (ТЗ §5.1): одно двунаправленное
соединение, строгие контракты, потоковые подписки. Альтернативы
(MQTT, SignalR) отклонены — второй транспорт означает второй контракт
и второй набор ошибок.

Передаются: текущие значения тегов, их изменения по подписке, аварии
и события, команды на сервер (запись в тег, квитирование), исторические
данные для трендов, пакет проекта для кэша клиента.

Пароль по сети — только внутри TLS-канала (`users-plan.md` §8).

### Сервер ↔ ПЛК

| Протокол | Оборудование | Статус |
|---|---|---|
| Modbus TCP/RTU | ПЛК, частотники, счётчики | реализовано |
| OPC UA | промышленные контроллеры | планируется |
| S7 | Siemens | по запросу |

### Сервер ↔ хранилище

**Ни одного сервера БД на объекте** (ТЗ §4.1, §8) — требование
к развёртыванию: копирование папки, без установки и администрирования.

| Данные | Хранилище |
|---|---|
| Значения тегов (архив) | собственный бинарный формат, `docs/archive-format.md` |
| События, аварии, аудит | SQLite (`events.db`) |
| Пользователи станции | `users.json` рядом с проектом |
| Проект | пакет `.scadapkg` |

## Резервирование мастера

**В версии 1 не реализуется. Закладывается, чтобы не переделывать ядро.**

### Двойного опроса быть не должно

Два мастера, одновременно опрашивающих один ПЛК, — это конкурирующие
записи, двойная нагрузка на канал, а на Modbus RTU ещё и физически одна
линия на двоих. Поэтому роль мастера имеет **состояние**:

- **Active** — опрашивает контроллеры, ведёт архив, обслуживает клиентов;
- **Standby** — не опрашивает; получает данные от активного.

**Требование к коду, которое надо соблюдать уже сейчас:** опрос и запись
в архив запускаются **не при старте процесса, а при переходе в Active**.
`PollingEngine` уже умеет `StartAsync`/`StopAsync` без перезапуска
процесса — предпосылка есть, ломать ничего не придётся.

### Архивы не синхронизируются — реплицируется поток

Standby подключается к активному **по клиентскому контракту** и пишет
полученные значения в свой архив. Это временная роль клиента у машины,
которая остаётся мастером; принцип «клиент не знает про ПЛК» не нарушен —
про ПЛК знает состояние Active, а не роль клиента.

Что это даёт:

- двойного опроса нет — данные приходят от активного;
- архивы почти идентичны, дыр в истории не возникает;
- при переключении standby просто перестаёт получать поток и начинает
  опрашивать сам — архив продолжается без разрыва;
- специальных контрактов не нужно: репликация — это подписка, которая
  и так есть для клиентов.

Разрыв связи между мастерами оставляет **дыру в архиве резерва** за время
разрыва. Закрывается дозагрузкой диапазона у активного — тем же
контрактом истории, которым пользуются тренды.

Гарантия при этом — **«те же значения с задержкой репликации»**, а не
побайтовая идентичность файлов. Сравнивать архивы двух машин хешем
бессмысленно.

Журнал событий и аварий реплицируется тем же способом: подписка плюс
запись в свой SQLite. **Квитирует только активный.**

### Кто решает, кто активный — открытый вопрос

Зафиксированы только границы:

- **Split-brain недопустим.** Два Active означают двойной опрос
  и расходящиеся архивы.
- **Автоматического возврата к основному нет.** Основной поднялся —
  становится Standby; переключение обратно только по решению человека.
- Простейший механизм на будущее — приоритет плюс heartbeat: standby
  становится активным, если не слышит активного дольше таймаута.

Надёжный арбитраж без внешнего арбитра или разделяемого ресурса
не строится — это классическая задача, и промышленные системы решают её
либо аппаратно (дублированный ПЛК сам знает ведущего), либо ручным
переключением. Способ выбирается под конкретный объект, а не изобретается
заранее.

## Плюсы архитектуры

| Плюс | Описание |
|---|---|
| Гибкость развёртывания | один софт работает сервером, клиентом или обоими |
| Простота установки | один установщик, роль задаётся конфигурацией |
| Масштабируемость | сервер выносится на отдельный ПК без переписывания кода |
| Отделение UI от сбора | служба работает независимо от того, открыт ли GUI |
| Обновление | клиентов можно обновлять, не трогая сервер, и наоборот |

## Минусы и решения

| Минус | Решение |
|---|---|
| Единая точка отказа (мастер) | резервный мастер (см. выше, вне v1) |
| Нагрузка на мастер | вынести сервер на выделенный ПК |
| Зависимость от сети | явное уведомление с блокировкой экрана (см. ниже) |
| Настройка адреса сервера | поиск в сети как подсказка + фиксация в конфигурации |
| Безопасность | TLS, права пользователей, ACL на конфигурацию, firewall/VLAN |

### Поведение клиента при потере связи

**Явное уведомление с блокировкой.** Поверх экрана — модальный слой
«Нет связи с сервером»; мнемосхема под ним не обновляется и не принимает
управление. Показывать устаревшие значения как живые опаснее закрытого
экрана: оператор не должен принимать решения по картинке пятиминутной
давности. Восстановление автоматическое при возврате связи, подтверждения
не требует.

## Развитие

Версия 1 покрывает Single ARM, Master ARM и Dedicated Server с клиентами.
Резервирование мастера — заложено, но не реализовано. Кластеры серверов,
брокеры сообщений и веб-клиенты в объём версии 1 не входят и здесь
не проектируются.

## Открытые вопросы

| Вопрос | Состояние |
|---|---|
| Имя вендора/продукта в пути `%ProgramData%\SCADA\` | взято рабочее `SCADA`, уточняется при выборе названия |
| Способ арбитража Active/Standby | ручное переключение, heartbeat или внешний арбитр — решается под объект |
| Репликация `users.json` на резервный мастер | реплицировать или заводить учётки на обеих машинах — не решено |
| ~~Объём кэша пакета на клиентском АРМе~~ | решено: одна версия, зеркало мастера (см. «Client-only ARM») |
| Как клиент узнаёт об обновлении проекта | два кандидата: клиент сам сверяет версию (периодически либо при каждом запросе схемы) или мастер уведомляет по существующей подписке. Выбирается по надёжности при реализации M6.5/M7; требование одно — клиент не должен продолжать работу на устаревшей модели тегов |

## Ключевые принципы

1. **Сервер не знает про UI.** Он собирает данные и раздаёт их по сети.
2. **Клиент не знает про ПЛК.** Он получает данные от сервера.
3. **Общие библиотеки — единый источник истины.** Модели и контракты
   одни на обе стороны.
4. **Сервер запускается отдельно от GUI.** GUI может быть закрыт —
   служба работает.
5. **Способ запуска сервера зависит от ОС**, сам код кроссплатформенный.
6. **Роль станции — свойство машины, а не сборки.** Одна поставка,
   конфигурация решает, кем станция работает.
