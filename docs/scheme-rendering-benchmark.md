# Замер кадра мнемосхемы: 30 FPS и volatile-анимации

**Дата:** 2026-08-19
**Контекст:** B0.4 (время в выражениях, volatile-привязки) + проверка
жизнеспособности 30 FPS на непрерывных анимациях. Для Dev B: документ
закрывает вопрос «вывезет ли канва сотни/тысячи анимированных элементов»
и фиксирует изменения, внесённые Dev A в файлы SCADA.Graphics.

---

## 1. Что добавлено со стороны ядра (Dev A)

- `EvaluationContext.NowUnixMs` (необязательное, default 0) и builtin
  `now()` — возвращает **секунды** (double) для удобства анимаций.
  Незаполненный контекст → детерминированный 0 (тесты воспроизводимы);
  рантайм/UI заполняют на тик. `AlarmEngine` тоже заполняет — `now()`
  доступно в правилах сигнализации с той же семантикой.
- Оператор `%` (Mod) в языке выражений: лексер/парсер/эмиттер/ВМ.
  Опкод и id функции добавлены **в конец** таблиц — формат пакета и старые
  сборки не затронуты.
- Проверено тестами: `now()` из байткода, сквозной `now() * 90 % 360`.

## 2. Изменения в файлах SCADA.Graphics (сделаны Dev A — не пугаться)

Минимальные, под замер и плавность анимации:

| Файл | Изменение | Зачем |
|---|---|---|
| `SchemeCanvas.cs` | `StartLive`: тик **33 мс** при `_anyVolatile`, иначе 200 мс как было | 200 мс = 5 FPS, вращение дёргалось; 33 мс = 30 FPS (бюджет ТЗ §4.1) |
| `SchemeCanvas.cs` | `Recompute` стал `public static`; тело `Render` вынесено в `public static BuildVisuals(...)` | headless-замер без Avalonia (§4) |
| `SchemeDrawOperation.cs` | класс стал `public`; цикл рисования вынесен в `public static DrawItems(SKCanvas, ...)`; `Render` — тонкая обёртка | тот же код рисует и в приложении, и в бенчмарке |
| `SchemeElementRuntime.cs` | `internal` → `public` | доступ из бенчмарка; класс и так будущая публичная модель движка |
| `SyntheticSchemeGenerator.cs` | параметр `volatileEvery` (0 = как раньше): каждый N-й элемент получает volatile-привязку вращения `now() * 90 % 360` | нагрузочный сценарий «всё крутится» |
| `SchemesViewModel.cs` (SCADA) | только комментарий у `UseLoadTestScheme`; флаг оставлен `false` | для живого показа: `true` + `volatileEvery: 2` |

Логика движка не менялась: IsDirty/эпохи/куллинг/стопы — как были.

## 3. Результаты замера

Машина: Ryzen 5600G (6 ядер, 3,9 ГГц) — **в 3–4 раза быстрее целевого АРМ**
(2 ядра ~2 ГГц, ТЗ §1.1). ShortRun, 3 итерации, разброс до ±50 % —
цифры порядковые. Схема: ВСЕ элементы volatile (худший случай), viewport
на всю схему (куллинг ничего не отсекает), отрисовка на CPU-поверхности
(Skia raster — пессимистичный вариант, без GPU).

| Элементов | Tick (пересчёт) | Render (визуалы + Skia) | Alloc/кадр |
|---|---|---|---|
| 500 | 0,17 мс | 5,6 мс | 262 КБ |
| 1000 | 0,21 мс | 6,8 мс | 524 КБ |
| 2000 | 0,56 мс | 17 мс | 1,0 МБ |

Прогон: `dotnet run -c Release --project SCADA.Benchmarks -- --filter '*SchemeRendering*'`
(`SchemeRenderingBenchmarks.cs`, ShortRunJob + MemoryDiagnoser).

## 4. Выводы

1. **Вычислительная сторона — не проблема вообще.** 2000 непрерывных
   анимаций пересчитываются за ~0,5 мс. Модель «значение = f(теги, время)»
   подтверждена числом; отдельный анимационный механизм (скорость в
   свойствах + докрутка в render-цикле) **не нужен** — он экономил бы
   бесплатную часть и плодил второй источник состояния.
2. **30 FPS разрешены:** тик 33 мс при volatile — безопасен. Статичные
   схемы остаются на 200 мс, нагрузка там нулевая.
3. **Потолок — рендер.** На целевом железе 1000 элементов при 30 FPS —
   впритык, 2000 — не вывезет в текущем виде.
4. **Главный дефицит — аллокации рендера** (до 1 МБ/кадр при 2000,
   ~30 МБ/с мусора на 30 FPS): `SKTypeface`/`SKFont`/`SKPaint` создаются
   на элемент на кадр (`SchemeDrawOperation.DrawItems`), строки текста
   форматируются на каждый тик (`SchemeCanvas.FormatText`). На 4-ГБ машине
   с workstation GC это частые Gen0.

## 5. Рекомендации Dev B

1. **B0.6 — приоритет №1, до B2.** По факту замера обязательны:
   - кэш `SKTypeface`/`SKFont` по (семейство, размер) — одна строка рисования
     сейчас создаёт оба на каждый элемент;
   - кэш/переиспользование `SKPaint` (по цвету — словарь, пуль);
   - статика схемы в `SKPicture` (ТЗ §10.1): неизменные элементы не
     перерисовываются каждый кадр — это самый большой выигрыш;
   - текст: форматировать только при изменении значения (уже есть в
     модели — пересчёт по эпохам; проверить, что volatile не дёргает
     текстовые привязки без надобности).
   Критерий готовности B0.6: тот же бенчмарк, 1000 элементов — Render
   ≤ 8 мс и Alloc/кадр в разы ниже текущих 524 КБ.
2. **Приёмку B0.4/B0.6 мерить этим стендом**, прогоняя 500/1000/2000 —
   потолок виден числом, а не прикидкой. Перед релизом — то же на целевом
   железе (ТЗ §4.1, M8).
3. **Живой показ:** `UseLoadTestScheme = true` в `SchemesViewModel` —
   500 элементов, каждый второй вращается; запуск через «Запустить
   исполнение». Замеры Tick/Draw — в выводе отладчика (Debug.WriteLine).
4. **Не делать:** вторую систему анимации «скорость + vsync-цикл» (см.
   вывод 1); подъём окна в бенчмарке (vsync квантует кадр в 16,6 мс,
   методика BDN ломается — окно это приёмка M8, не бенчмарк).
5. Если после B0.6 потребуется 2000+ непрерывных анимаций на целевом
   железе — следующий шаг dirty-rect (перерисовка только изменившихся
   областей), а не смена модели. Обсуждается отдельно, по факту замера.
