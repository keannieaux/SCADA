## 1. Назначение

Десктопная SCADA/HMI-система для промышленного объекта: сбор данных с
программируемых логических контроллеров, отображение технологического процесса
на мнемосхемах, тренды, сигнализация, архивирование и управление.

### 1.1 Ключевые ограничения

| Ограничение | Значение |
|---|---|
| Целевое железо | Слабый производственный ПК: 2 ядра x64 ~2 ГГц, 4 ГБ RAM, встроенная графика |
| ОС | Windows 10/11 x64 (архитектура кроссплатформенная, но целимся в Windows) |
| Количество тегов | **10 000 (подтверждено заказчиком), проектируем с запасом до 20 000** |
| Глубина архива | 1 год |
| Контроллеры | LicOS (Unionscience Technology Group), серии EC200/EC300/EC400, MC500/MC600 |
| Редактор мнемосхем | Обязателен, встроен в систему |
| Рабочих мест | Возможно несколько (не подтверждено) — архитектурно закладываем |

### 1.2 Приоритеты

1. **Производительность на слабом железе** — главный критерий.
2. **Чистота архитектуры и читаемость кода** — система будет жить годами.
3. Функциональная полнота.

Именно в этом порядке. Если фича требует пожертвовать производительностью или
чистотой слоёв — фича переделывается или откладывается.

## 2. Термины

| Термин | Определение |
|---|---|
| **Тег** (Tag) | Именованная единица данных: значение + метка времени + качество. Аналог «канала» в RapidScada. |
| **Качество** (Quality) | Достоверность значения: Good / Uncertain / Bad. |
| **Драйвер** | Модуль обмена по конкретному протоколу (Modbus, OPC UA). |
| **Устройство** (Device) | Логический контроллер, опрашиваемый драйвером. |
| **Канал связи** (Channel) | Физическое соединение (TCP-сокет, COM-порт), обслуживает одно или несколько устройств. |
| **Мнемосхема** (Scheme) | Векторное изображение техпроцесса с элементами, привязанными к тегам. |
| **Динамизация** | Правило «свойство фигуры зависит от значения тега». |
| **Апертура / Deadband** | Порог изменения, ниже которого значение не пишется в архив. |
| **Квитирование** | Подтверждение оператором факта ознакомления с аварийным сообщением. |
| **Инженерная поставка** | Дистрибутив с редактором и компилятором. Предназначен разработчикам SCADA. См. §5.4. |
| **Исполнительная поставка** | Дистрибутив без инструментальных средств. Передаётся заказчику. См. §5.4. |
| **Пакет** (`.scadapkg`) | Скомпилированный проект: бинарный, с раннесвязанными тегами и байткодом выражений. См. §14.2. |
| **Выражение** | Формула динамизации, компилируемая в байткод стековой ВМ. См. §11.2. |
| **Раннее связывание** | Замена имени тега на индекс в `TagTable` на этапе компиляции пакета. См. §11.6. |
| **Realtime-БД** | Оперативное хранилище текущих значений всех тегов в памяти. |

## 4. Нефункциональные требования

Это **критерии приёмки**, а не пожелания. Проверяются замерами на целевом железе.

### 4.1 Производительность

| Показатель | Требование |
|---|---|
| Запуск приложения до рабочего окна | ≤ 5 с |
| Потребление RAM, 10 000 тегов, установившийся режим | ≤ 500 МБ |
| Загрузка CPU: опрос 10 000 тегов @ 1 Гц + открытая мнемосхема | ≤ 25 % на 2 ядрах |
| Частота кадров мнемосхемы, 500 динамических элементов | ≥ 30 FPS |
| Задержка «значение принято → отображено» | ≤ 200 мс |
| Открытие тренда: 10 тегов за 8 часов | ≤ 1 с |
| Отклик UI при переключении страниц | ≤ 100 мс |
| Пропускная способность `TagTable` на запись | ≥ 1 000 000 значений/с (один поток) |

### 4.2 Надёжность

- Обрыв связи с устройством **не влияет** на работу UI и остальных устройств.
- Автоматическое переподключение с экспоненциальной задержкой (1с → 30с, потолок).
- При потере связи теги устройства получают качество `Bad`, значение сохраняется
  последнее известное с исходной меткой времени.
- Аварийное завершение не приводит к потере архива более чем за последние 10 секунд
  (периодический flush).
- Повреждённый файл архива не блокирует работу — пропускается с записью в лог.

### 4.3 Ресурсы диска

Оценка для 10 000 тегов (см. расчёт в §8.4): **~55 ГБ на год** при политике
хранения по умолчанию.

## 5. Архитектура

### 5.1 Главное решение

> **Ядро и HMI разделены логически, но работают в одном процессе.**

### 5.3 Правило зависимостей

Зависимости направлены **строго вниз**:

```
Scada.App.Runtime          Scada.App.Engineering
        ↓                            ↓
        └──── Scada.App.Shared ──────┘
                     ↓                ↓ (только Engineering)
Scada.Graphics / Scada.Alarms /   Scada.Editor
Scada.Historian / Scada.Package   Scada.Expressions.Compiler
                     ↓                Scada.Package.Builder
              Scada.Runtime
                     ↓
        Scada.Drivers.Abstractions
                     ↓
        Scada.Core / Scada.Expressions
```

Жёсткие запреты:

- Приложения **не знают** о существовании Modbus, OPC UA и любого конкретного протокола.
- `Scada.App.Runtime` **не ссылается** на `Scada.Editor`,
  `Scada.Expressions.Compiler` и `Scada.Package.Builder`. Это ключевое требование
  §5.4: инструментальный код физически отсутствует в поставке заказчику.
- `Scada.Graphics` **не ссылается на Avalonia** — только на SkiaSharp. Модель схемы и
  рендерер должны работать в консольном приложении (для будущей серверной генерации
  изображений и для тестов).
- `Scada.Expressions` содержит **только исполнение** байткода. Парсер и компилятор —
  в отдельной сборке `Scada.Expressions.Compiler`, в исполнительную поставку не входит.
- `Scada.Core` не ссылается ни на что, кроме BCL.
- Конкретные драйверы (`Scada.Drivers.*`) не ссылаются друг на друга.

Правила проверяются автотестом в `Scada.Architecture.Tests`. Это не бюрократия:
без автопроверки слои размываются за пару месяцев. Для запрета на
инструментальные сборки в `Scada.App.Runtime` автопроверка обязательна — нарушение
этого правила обнаружится только при передаче системы заказчику.

### 5.4 Состав поставки: инженерная и исполнительная

Система поставляется **двумя раздельными дистрибутивами из одной кодовой базы**.

| | **Инженерная поставка** `Scada.App.Engineering` | **Исполнительная поставка** `Scada.App.Runtime` |
|---|---|---|
| Получатель | Разработчики SCADA (мы), интеграторы | Заказчик, операторские станции |
| Редактор мнемосхем | Есть | **Нет** |
| Компилятор выражений | Есть | Нет (только исполнение байткода) |
| Сборка пакета `.scadapkg` | Есть | Нет |
| Конфигурация тегов и устройств | Редактирование | Только просмотр |
| Работа с исходным проектом | Да | Нет |
| Загрузка `.scadapkg` | Да | Да |
| Сбор данных, схемы, тренды, сигнализация | Да | Да |
| Диагностика каналов и тегов | Да | **Да, обязательно** (§5.4.2) |

#### 5.4.1 Обоснование

Разделение инструментальной и исполнительной систем — отраслевая норма
(WinCC Engineering / Runtime, InTouch WindowMaker / WindowViewer,
Ignition Designer / Client, RapidScada Administrator / Server).

Рассмотренные и отклонённые альтернативы:

| Вариант | Причина отклонения |
|---|---|
| Единый бинарник, редактор скрыт флагом или лицензией | Код редактора физически поставляется заказчику: лишний вес, время старта и поверхность атаки. Флаг обходится тривиально. Бюджеты §4.1 расходуются на код, который никогда не выполняется. |
| Редактор отдельным продуктом и репозиторием | Дублирование модели схем и формата файлов, неизбежная рассинхронизация, двойная поддержка. Недопустимо при двух разработчиках. |
| Редактор как догружаемый плагин (`AssemblyLoadContext`) | Требует инфраструктуры версионирования плагина против хоста ради выгоды, которую разделение сборок даёт бесплатно. Оправдан только при планах на стороннюю экосистему расширений — такого требования нет. |

Выбранный вариант даёт три эффекта: у заказчика отсутствует инструментальный код,
дистрибутив меньше и стартует быстрее, а невозможность обратиться к редактору из
исполнительной части обеспечивается компилятором, а не дисциплиной.

#### 5.4.2 Следствия

- **Диагностика в исполнительной поставке обязательна.** Раз редактора на объекте
  нет, разбор нештатной ситуации ведётся средствами runtime: состояние каналов
  (§7.4), живые значения тегов, журналы, просмотр состава загруженного пакета.
  Это требование, а не побочный эффект.
- **Общий код выносится в `Scada.App.Shared`.** Дублирование страниц между двумя
  приложениями недопустимо.
- **Решение принимается на M0.** Расплетание двух поставок на M6, когда редактор
  уже написан внутри общего приложения, несоизмеримо дороже.

## 6. Модель данных

### 6.1 Значение тега

Основной тип, от которого зависит вся производительность системы.

```csharp
public readonly record struct TagId(int Value);

public enum Quality : byte
{
    Bad       = 0,
    Uncertain = 64,
    Good      = 192
}

[StructLayout(LayoutKind.Auto)]
public readonly struct TagValue
{
    public readonly double Value;        // 8 байт
    public readonly long   TimestampUtc; // 8 байт, тики UTC
    public readonly Quality Quality;     // 1 байт
    public readonly TagFlags Flags;      // 1 байт
}
```

Требования к модели:

- **Структура, не класс.** ~24 байта, размещается в массиве, не грузит GC.
- **Хранение в плоском массиве** `TagValue[]`, индекс = `TagId`. Доступ O(1)
  без хеширования. Словарь `имя → TagId` используется **только при загрузке
  конфигурации**, в горячем пути запрещён.
- **Никакого `INotifyPropertyChanged` на теге.** 10 000 объектов с событиями
  на каждое изменение — гарантированная смерть производительности.
- Дискретные значения хранятся в том же `double` (0.0 / 1.0). Отдельного типа нет —
  это упрощает архив, тренды и алармы.
- Строковые теги (редкие, < 5 % в типичной SCADA) — в отдельной таблице
  `StringTagTable` с собственной индексацией.

### 6.2 Описание тега (конфигурация)

Загружается при старте, в рантайме не меняется (изменение = перезагрузка конфигурации):

```
TagDefinition:
  Id            TagId
  Name          string      уникальное имя, напр. "Boiler1.Temp"
  Description   string
  Units         string      "°C", "бар"
  DataType      enum        Analog | Discrete | String
  DeviceId      int
  Address       string      адрес в терминах драйвера
  ScaleFactor   double      линейное преобразование
  ScaleOffset   double
  MinValue      double      границы для трендов и валидации
  MaxValue      double
  Deadband      double      апертура архивирования (§8.2)
  ArchiveGroup  int         политика хранения (§8.5)
  IsWritable    bool
```

## 7. Подсистема сбора данных

### 7.1 Контроллеры LicOS

По документации производителя серии EC300/EC400/MC500/MC600 поддерживают:
Modbus, Profibus, EtherNet/IP, Profinet, CANopen, EtherCAT, OPC UA, MQTT.

**Для SCADA релевантны только два:**

- **Modbus TCP/RTU** — основной. Универсален, есть у всех серий, предсказуем
  по нагрузке, прост в отладке.
- **OPC UA** — если потребуется доступ к тегам по именам с типами и метаданными.
  Дороже по CPU и памяти.

EtherCAT, Profinet, CANopen — это **полевые шины между ПЛК и модулями ввода-вывода**.
SCADA по ним не работает: мы общаемся с самим контроллером, а он опрашивает
периферию. MQTT — опционально, при наличии брокера у заказчика.

### 7.2 Драйверы как плагины

```csharp
public interface IDeviceDriver
{
    string ProtocolName { get; }
    Task ConnectAsync(CancellationToken ct);
    Task<PollResult> PollAsync(ReadOnlySpan<TagAddress> addresses, Span<TagValue> results, CancellationToken ct);
    Task WriteAsync(TagAddress address, double value, CancellationToken ct);
    Task DisconnectAsync();
}
```

Добавление нового протокола = новый проект `Scada.Drivers.<Name>`, регистрация
в DI. Правок в остальном коде — ноль.

### 7.3 Требования к циклу опроса

- **Ноль аллокаций в установившемся режиме.** `ArrayPool<byte>` для буферов кадров,
  `Span<byte>` для парсинга, переиспользуемые массивы результатов.
- `PeriodicTimer` вместо `while (true) { await Task.Delay(...) }` — не накапливает дрейф.
- Один канал связи = один `Task`. Устройства на одном COM-порту опрашиваются
  последовательно, устройства на разных TCP-соединениях — параллельно.
- **Частота опроса настраивается на устройство**, не глобально. Аварийные сигналы —
  10 Гц, температуры — раз в 5 секунд. Это главный рычаг снижения нагрузки.
- **Частота опроса ≠ частота записи в архив** (см. §8.2).
- Группировка запросов: соседние регистры Modbus читаются одним запросом
  (оптимизатор объединяет адреса в непрерывные блоки при загрузке конфигурации).
- Все операции ввода-вывода асинхронные, с `CancellationToken` и таймаутом.

### 7.4 Диагностика канала

Каждый канал публикует собственные теги диагностики (доступны на мнемосхемах
и в трендах наравне с технологическими):

- состояние соединения, время последнего успешного обмена;
- количество успешных/неуспешных запросов, число переподключений;
- среднее и максимальное время отклика.

## 8. Историзация

Самая сложная часть по объёму данных. Требование «хранить год» при 10 000 тегов
не решается прямым сохранением.

### 8.1 Оценка «в лоб»

```
10 000 тегов × 86 400 с × 16 байт = 13,8 ГБ в сутки → ~5 ТБ в год
```

Не подходит. Нужны три механизма, все — стандартная практика SCADA.

### 8.2 Механизм 1: апертурное сжатие (deadband)

Значение пишется в архив только если изменилось больше порога `Deadband`
относительно последнего записанного. Для аналоговых технологических параметров
даёт экономию **5–20×**.

Дополнительно: принудительная запись раз в N минут даже без изменений
(«heartbeat»), чтобы на трендах не было бесконечных горизонтальных участков
и чтобы отличать «не менялось» от «не собиралось».

### 8.3 Механизм 2: сжатие потока

Delta-of-delta для меток времени + XOR для значений (схема Gorilla, применяется
в промышленных TSDB). Вместо 16 байт на точку — **1,5–2 байта**. Ещё ~8×.

### 8.4 Механизм 3: многоуровневое хранение

| Уровень | Содержание | Глубина по умолчанию | Объём на 1 тег/год |
|---|---|---|---|
| L0 | Сырые значения (deadband + сжатие) | 60 дней | ~2–5 МБ |
| L1 | Минутные агрегаты: min / max / avg / count / quality | 90 дней (все теги), 1 год (критичные) | ~10 МБ |
| L2 | Часовые агрегаты | 5 лет | ~0,2 МБ |

Оценка итогового объёма для 10 000 тегов:

```
L0, 60 дней, все теги              ~10 ГБ
L1, 90 дней, все теги              ~26 ГБ
L1, 1 год, критичные (~1000)       ~10 ГБ
L2, 5 лет, все теги                 ~9 ГБ
                                   ───────
                                   ~55 ГБ
```

Приемлемо для обычного диска.

### 8.5 Политика хранения — на группу тегов

Хранить всё одинаково глубоко бессмысленно. Каждый тег принадлежит
`ArchiveGroup` со своей политикой (глубина L0/L1/L2, deadband по умолчанию).
Критичные параметры — полная детализация год, вспомогательные — только часовые.

### 8.6 Заморозка вокруг аварий

При срабатывании аларма сырые данные (L0) в окне **±1 час** помечаются флагом
`Frozen` и не удаляются при ротации. Именно эти данные нужны для разбора
инцидента спустя месяцы, когда обычные сырые записи уже удалены.

### 8.7 Формат хранения

- **Значения:** собственный append-only бинарный формат. Файл на сутки на
  группу тегов (подход RapidScada). Колоночная раскладка внутри блока.
  **Обязателен заголовок с версией формата** — миграция года накопленных
  данных без версионирования невозможна.
- **События, алармы, конфигурация, аудит:** SQLite. Объём мизерный,
  нужны запросы и фильтрация.

SQLite для потока значений не используется: ~800 млн строк в сутки слабый ПК
не обслужит.

### 8.8 Сроки проектирования

Формат архива проектируется **на бумаге в M1**, реализуется в M4. Причина:
переделка формата после накопления реальных данных крайне болезненна.

## 9. Оперативное хранилище (TagTable)

Realtime-БД текущих значений в памяти. Один экземпляр на систему.

### 9.1 Синхронизация: seqlock

Между потоками драйверов (запись) и UI (чтение) используется **seqlock** —
счётчик версии на тег: нечётное значение = запись в процессе, чётное = данные целостны.

Обоснование: `TagValue` — 24 байта, её запись **не атомарна**, возможно
чтение «порванной» структуры. Блокировка на каждый тег при 10 000 тегов × 10 Гц
даёт 100 000 захватов блокировки в секунду — недопустимо. Seqlock даёт
свободное от блокировок чтение при том, что записи редки относительно чтений.

### 9.2 Обновление UI

**Не событие на каждый изменившийся тег.** Вместо этого:

1. `DispatcherTimer` с периодом 100 мс.
2. Забирает только теги, чья версия выросла с прошлого кадра («эпоха изменений»).
3. Обновляет только элементы, **реально видимые** на экране.

Это даёт задержку отображения ≤ 200 мс (требование §4.1) при постоянной
нагрузке на UI-поток независимо от количества тегов.

## 10. Мнемосхемы

### 10.1 Рендеринг

**Не дерево из тысяч контролов Avalonia.** Один кастомный `Control` с
`ICustomDrawOperation`, рисующий всю схему напрямую в `SKCanvas`.

- Статика (фон, трубопроводы, надписи, рамки) кэшируется в `SKPicture` и
  перерисовывается только при изменении масштаба/позиции.
- Динамика рисуется поверх, по dirty-областям.
- Частота кадров ограничена 20–30 FPS. Глазу достаточно, экономия CPU кратная.
- Панорамирование и масштабирование — через матрицу преобразования
  (подход PanAndZoom из Core2D).

### 10.2 Модель схемы — сразу под редактирование

Критично: **нельзя** сделать runtime-модель, а потом переделывать под редактор.
С самого начала модель включает:

- стабильные GUID у каждой фигуры;
- слои и z-order;
- группировку фигур;
- сериализацию с версией формата;
- структуру, дружелюбную к undo/redo (стек команд, как в Core2D).

Фундамент закладывается в M3, UI редактора — в M6.

### 10.3 Динамизация

Правило «свойство фигуры зависит от значения тега». Минимальный набор:

| Свойство | Применение |
|---|---|
| Цвет заливки / обводки | Состояние агрегата, выход за уставку |
| Видимость | Появление предупреждающих знаков |
| Текст | Числовое значение с форматом и единицами |
| Поворот | Стрелки, положение задвижки |
| Уровень заполнения | Резервуары, бункеры |
| Положение (X/Y) | Ползунки, индикаторы |
| Мигание | Неквитированная авария |

### 10.4 Библиотека символов

Графические символы (насосы, клапаны, задвижки, ёмкости, двигатели) —
SVG-файлы, рендеринг через **Svg.Skia**. Свой парсер SVG не пишем.

### 10.5 Редактор (M6)

- Инструменты: линия, прямоугольник, эллипс, полилиния, текст, символ из библиотеки.
- Undo/redo через стек команд.
- Привязка к сетке, выравнивание, распределение.
- Панель свойств с настройкой динамизации.
- Копирование/вставка, множественное выделение.
- Предпросмотр в режиме исполнения без выхода из редактора.

## 11. Выражения и скриптование

### 11.1 Разделение двух видов логики

«Скрипты на мнемосхеме» — это **два механизма с противоположными требованиями**.
Объединение их в один даёт либо недостаточную производительность, либо
недостаточную выразительность.

| | **Логика отображения** | **Логика действий** |
|---|---|---|
| Примеры | Цвет насоса, текст в поле, видимость значка аварии | Клик по кнопке → запись в тег и переход на схему |
| Частота | Каждый кадр, каждый видимый элемент: **до 30 000 вычислений/с** | По событию, единицы раз в минуту |
| Требования | Ноль аллокаций, предсказуемое время, гарантия завершения | Время исполнения не критично |
| Механизм | Байткод-выражения (§11.2) | Декларативные действия (§11.3) |

### 11.2 Уровень 1: выражения, компилируемые в байткод

Для динамизации нужен не язык, а **выражения**:

```
Boiler1.Temp > Boiler1.TempHi && Pump1.Running
(Tank1.Level / Tank1.Volume) * 100
Valve1.Open ? "Открыт" : "Закрыт"
```

Редактор компилирует их в компактный байткод стековой машины. **В пакет
попадает байткод, не текст.**

**Набор инструкций:** `LoadTag(индекс)`, `LoadConst(индекс)`, арифметика,
сравнения, логические операции, `JumpIfFalse`, `CallBuiltin(id)`, `Return`.

Обязательные свойства ВМ:

- **Обратные переходы запрещены на уровне формата байткода.** Следствие: циклов
  не существует, завершение выражения гарантировано структурно. Это надёжнее
  сторожевого таймера или счётчика инструкций с прерыванием.
- **Ноль аллокаций.** Стек операндов — `stackalloc Span<double>`, только
  значимые типы.
- Объём реализации — порядка 500–800 строк. Это не разработка языка.

**Обработка недостоверного качества.** Семантика `Temp > 80` при качестве
`Bad` задаётся явными встроенными функциями `IsGood(tag)`, `ValueOr(tag, default)`,
а не неявным распространением недостоверности. Обоснование: предсказуемость
для интегратора. Без явного решения этого вопроса возможна ситуация «зелёный
насос при оборванной связи».

### 11.3 Уровень 2: декларативные действия

Для событий (клик, срабатывание сигнализации, открытие схемы) язык не требуется —
достаточно **списка команд из фиксированного набора**:

```
OnClick:
  - Confirm("Запустить насос №1?")
  - WriteTag(Pump1.Cmd, 1)
  - OpenScheme("boiler-1")
```

Состав набора: `WriteTag`, `ToggleTag`, `OpenScheme`, `ShowDialog`, `Confirm`,
`AckAlarm`, `RunReport`, `Login`. Условия задаются выражениями §11.2.

Полностью валидируется в редакторе, безопасен по построению, не требует
ни компилятора, ни интерпретатора в исполнительной поставке.

### 11.4 Уровень 3: модули на C# — точка расширения

На случай, когда уровней 1–2 недостаточно: редактор компилирует C#-код проекта
через Roslyn в сборку, пакет несёт `Project.Scripts.dll`, runtime загружает её
через `AssemblyLoadContext`.

Совпадение с §5.4: **Roslyn требуется только в инженерной поставке**, у заказчика
компилятора нет — только готовая сборка.

Ограничения, которые необходимо учитывать:

- **Конфликт с NativeAOT.** AOT-приложение не может загружать IL. При выборе
  NativeAOT в M8 уровень 3 исключается. ReadyToRun с ним совместим.
- **Изоляция обязательна.** Обработка исключений по периметру, таймаут
  исполнения, правило «отключить сбойный модуль, записать в журнал, продолжить
  работу». Остановка производства из-за ошибки в скрипте недопустима.
- Версионирование сборки относительно хоста.

**Решение: точка расширения закладывается, реализация откладывается (не ранее M7).**
Уровни 1–2 покрывают подавляющее большинство задач; преждевременное открытие
уровня 3 ведёт к переносу в C# логики, которой там быть не должно.

### 11.5 Отклонённые варианты

| Вариант | Причина отклонения |
|---|---|
| Встраиваемый интерпретатор (Lua/MoonSharp, JavaScript/Jint) | Интерпретация медленнее байткодной ВМ на порядок и более. На 30 000 вычислений/с это переходит из микросекунд в заметные проценты CPU на двухъядерной машине. Дополнительно: нагрузка на GC, лишняя зависимость, ещё один язык для интегратора. |
| Хранение выражений текстом с разбором в рантайме | Разбор при загрузке расходует бюджет старта (§4.1); позднее связывание имён тегов исключает оптимизацию §11.6. |

### 11.6 Раннее связывание тегов

Главная выгода компилированного пакета — не защита от правки, а следующее.

При компиляции имя тега `Boiler1.Temp` заменяется на **индекс в `TagTable`**.
В рантайме инструкция `LoadTag` — прямое обращение к элементу массива:
без поиска по словарю, хеширования строки и разбора имени.

При 30 000 вычислений в секунду разница между обращением по индексу и поиском
строки в словаре определяет, укладываемся ли мы в бюджеты §4.1 на слабом ПК.

Побочный эффект: **несуществующий тег становится ошибкой сборки пакета**,
а не отказом на объекте.

### 11.7 Пересчёт по эпохам

Выражение вычисляется только при изменении хотя бы одного входящего в него тега.

При компиляции редактор записывает в пакет список тегов каждого выражения.
В рантайме выражение хранит последнюю обработанную эпоху изменений; механизм
эпох определён в §9.2 и переиспользуется без изменений.

Поскольку одновременно меняется малая доля тегов схемы, фактическая нагрузка
оказывается кратно ниже оценки в 30 000 вычислений.

### 11.8 Расчётный бюджет

| Показатель | Оценка |
|---|---|
| Выражение из ~10 инструкций | 50–100 нс |
| 30 000 вычислений/с без учёта §11.7 | ~3 мс процессорного времени в секунду |
| Доля ядра | Доли процента |

Запас относительно §4.1 многократный. Для сравнения: интерпретатор JavaScript
на той же нагрузке израсходовал бы сотни миллисекунд в секунду.

### 11.9 Требования к редактору выражений

Поскольку компиляция перенесена в инженерную поставку, редактор обязан обеспечить:

- автодополнение имён тегов и подсветку синтаксиса;
- проверку типов и существования тегов **до** сборки пакета;
- вычисление выражения в реальном времени при подключении к работающему
  runtime — иначе диагностика на объекте сводится к угадыванию;
- обратную распаковку пакета в читаемый вид для разбора нештатных ситуаций.

## 12. Масштабирование на несколько станций

Не подтверждено заказчиком, но вероятно. Закладываем архитектурно, **не реализуем**.

Готовность обеспечивается решением §5.1: весь обмен UI↔ядро через `IRuntimeClient`.
Переход на несколько станций = реализация `RemoteRuntimeClient` поверх gRPC +
headless-хост ядра.

**Следствие, которое надо знать заранее:** при нескольких станциях архив живёт
на **одной машине-сервере**, а не на каждой станции. Наша схема это учитывает —
`IHistorian` тоже за интерфейсом.

## 13. Безопасность и права доступа

- Роли: Наблюдатель (только просмотр), Оператор (+ управление и квитирование),
  Инженер (+ редактирование схем и конфигурации), Администратор (+ пользователи).
- Все операции записи в устройства и квитирования пишутся в **журнал аудита**
  (SQLite): кто, когда, какой тег, старое и новое значение.
- Пароли — хеш с солью (PBKDF2 или Argon2), не открытым текстом.
- Автоматическая блокировка сессии по бездействию (настраивается).

## 14. Конфигурация проекта

Существует в двух формах: **исходной** (редактируется, живёт у разработчиков) и
**скомпилированной** (передаётся заказчику).

```
исходный проект  ──[ Scada.Package.Builder ]──>  project.scadapkg
   (инженерная поставке)                          (исполнительная поставка)
```

### 14.1 Исходная форма

Каталог на диске, версионируемый в git разработчиками:

```
MyProject.scada/
├─ project.json          метаданные, версия формата
├─ devices.json          каналы связи и устройства
├─ tags.json             описания тегов
├─ archive-groups.json   политики хранения
├─ alarms.json           правила сигнализации
├─ users.json            пользователи и роли
├─ schemes/
│  ├─ overview.scheme
│  └─ boiler-1.scheme
├─ scripts/              опционально, уровень 3 (§11.4)
└─ symbols/              библиотека SVG-символов
```

Сериализация — `System.Text.Json` с source-generated `JsonSerializerContext`:
без рефлексии, быстрый старт, совместимость с NativeAOT.

Все файлы конфигурации содержат **номер версии формата** для будущих миграций.

### 14.2 Скомпилированная форма: `.scadapkg`

```
project.scadapkg
├─ manifest.json         версия формата, версия проекта, контрольные суммы
├─ tags.bin              таблица тегов с готовыми индексами
├─ devices.bin           устройства + предгруппированные запросы Modbus
├─ code.bin              единый пул байткода всего проекта
│    ├─ constants        пул строк и чисел
│    ├─ expressions      таблица смещений
│    └─ bytecode         сплошной массив
├─ schemes/
│    └─ overview.bin     геометрия + ссылки на выражения по индексу
├─ symbols/              SVG-символы
└─ modules/              опционально, уровень 3 (§11.4)
     └─ Project.Scripts.dll
```

Два решения в структуре пакета неочевидны и обязательны к соблюдению:

- **Пул байткода общий на проект, а не на схему.** Выражения вида
  `Tag > HiLimit` повторяются в проекте сотни раз; при сборке они
  дедуплицируются. Экономия памяти и времени загрузки существенна.
- **Схема хранит индекс выражения в пуле, а не само выражение.** Загрузка схемы
  сводится к чтению плоских структур без разбора текста.

### 14.3 Обоснование компилируемой формы

| Эффект | Содержание |
|---|---|
| **Скорость старта** | Бюджет — 5 секунд (§4.1). Разбор JSON с описанием 10 000 тегов, построение индексов, группировка запросов Modbus и компиляция выражений выполняются на машине инженера, а не на слабом ПК заказчика. |
| **Раннее связывание** | Имена тегов заменены индексами `TagTable` (§11.6) — ключевое условие соблюдения бюджета по частоте кадров. |
| **Целостность** | Контрольные суммы выявляют повреждение файла. Оператор не изменит конфигурацию текстовым редактором. |
| **Совместимость** | Версия формата в манифесте позволяет runtime сообщить «пакет собран более новой версией редактора» вместо аварийного завершения. |

Цена решения — потеря прозрачности при разборе нештатных ситуаций на объекте.
Компенсируется требованием §11.9: редактор обязан уметь распаковать пакет
в читаемый вид.

### 14.4 Доставка и применение пакета

Требования к исполнительной поставке при получении нового пакета:

1. Проверка контрольных сумм и версии формата **до** применения.
2. Проверка совместимости версий (§14.5).
3. Сохранение предыдущего пакета.
4. Применение с перезапуском runtime.
5. **Автоматический откат к предыдущему пакету при неуспешном запуске.**

Пункт 5 обязателен: неудачное обновление конфигурации не должно приводить
к остановке производства.

### 14.5 Правило совместимости версий

Манифест содержит версию формата пакета. Runtime:

- **загружает** пакет с версией формата, равной или меньшей поддерживаемой;
- **отказывает с внятным сообщением** при большей версии, указывая требуемую
  версию исполнительной поставки;
- **никогда не пытается** интерпретировать неизвестные структуры «по возможности».

## 15. Правила разработки

### 15.1 Настройки сборки (обязательны с самого начала)

```xml
<Nullable>enable</Nullable>
<TreatWarningsAsErrors>true</TreatWarningsAsErrors>
<EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
<PublishReadyToRun>true</PublishReadyToRun>
<TieredPGO>true</TieredPGO>
<ServerGarbageCollection>false</ServerGarbageCollection>
```

`Nullable` и `TreatWarningsAsErrors` включаются **немедленно**. Включить их
на зрелом проекте практически невозможно — тысячи предупреждений.

Версии пакетов — только через `Directory.Packages.props` (Central Package
Management). Одна версия пакета на всё решение.

### 15.2 Правила кода

- В горячих путях (опрос, TagTable, рендер кадра) запрещены: LINQ, boxing,
  замыкания с захватом, `params`-массивы, рефлексия.
- Буферы — `ArrayPool<T>`, работа с ними — `Span<T>` / `Memory<T>`.
- Весь ввод-вывод асинхронный. `async void` запрещён (кроме обработчиков событий UI).
- `CancellationToken` пробрасывается во все асинхронные методы.
- Публичные API документируются XML-комментариями. Комментарии объясняют
  **почему**, а не **что** — «что» должно быть видно из кода.
- Никаких «магических чисел» — именованные константы.

### 15.3 Тестирование

- Автотесты покрывают ядро: `TagTable` (включая многопоточность), парсеры
  протоколов, правила алармов, сжатие и агрегацию архива, сериализацию.
- UI автотестами не покрывается — дорого и хрупко. Проверяется вручную.
- `Scada.Architecture.Tests` проверяет правила зависимостей §5.3.

### 15.4 Бенчмарки

BenchmarkDotNet на горячие пути **начиная с M1**, не «когда-нибудь потом»:
пропускная способность `TagTable`, парсинг кадра Modbus, время кадра рендера,
скорость сжатия архива.

Цель — ловить регрессии производительности сразу, а не обнаружить на M6, что
система не тянет.

### 15.5 Процесс работы

- Одна веха — одна ветка. Не смешивать несколько тем в одном наборе изменений.
- Каждая веха завершается **работающим приложением**, которое можно запустить.
- Перед началом вехи — краткое согласование состава работ.
- Правила проекта дублируются в `CLAUDE.md` в корне репозитория.

## 16. Организация работы команды

Состав: **два разработчика**. Раздел определяет зоны ответственности и порядок
взаимодействия.

### 16.1 Принцип разделения: по слоям, а не по вехам

Разделение вида «ты делаешь M2, я делаю M3» **не применяется**. M3 зависит от M1,
M4 от M2 — при таком делении один разработчик постоянно простаивает в ожидании другого.

Граница проходит по интерфейсу **`IRuntimeClient`** (§5.1). Это правильный шов:

- контракт узкий, согласуется один раз;
- по обе стороны требуются разные навыки;
- контракт можно заглушить, поэтому ни одна сторона не блокирует другую.

### 16.2 Фаза 0: совместная работа (M0 и ядро M1)

Первые 1–2 недели разработчики работают **совместно** — парно либо в режиме
«один пишет, второй немедленно читает».

Обоснование: на этом этапе формируются контракты и соглашения по коду.
Раздельная работа с самого начала приводит к двум несовместимым стилям и
расхождению в понимании доменной модели.

До разделения должны быть окончательно зафиксированы:

1. `TagValue`, `TagId`, `Quality` — модель данных (§6.1);
2. `TagDefinition` — описание тега (§6.2);
3. `IRuntimeClient` — контракт UI ↔ ядро;
4. формат файлов конфигурации и пакета `.scadapkg` (§14);
5. состав встроенных функций и семантика качества в выражениях (§11.2).

Дальнейшее изменение этих сущностей допускается **только по обоюдной
договорённости**, а не единоличным коммитом.

### 16.3 Зоны ответственности

| | **Разработчик A — Ядро и данные** | **Разработчик B — Графика и UI** |
|---|---|---|
| Проекты | `Scada.Core`, `Scada.Expressions`, `Scada.Expressions.Compiler`, `Scada.Runtime`, `Scada.Drivers.*`, `Scada.Historian`, `Scada.Alarms` (движок правил), `Scada.Package`, `Scada.Package.Builder` | `Scada.Graphics`, `Scada.Editor`, `Scada.App.Shared`, `Scada.App.Runtime`, `Scada.App.Engineering` |
| Вехи | M1 (ядро), M2, M2.5, M4 (архив), M5 (движок), M7 (запись в устройства) | M3, M4 (тренды), M5 (UI сигнализации), M6, M7 (UI прав доступа) |
| Характер работы | Многопоточность, бинарные форматы, сетевые протоколы, байткод-ВМ, оптимизация | SkiaSharp, композиция, эргономика оператора, undo/redo |
| Бенчмарки | Пропускная способность `TagTable`, сжатие архива, исполнение выражений | Время кадра рендера |

Распределение ролей — по профессиональной склонности. Объём работ сопоставим:
у A два протокола, архив и подсистема выражений, у B редактор мнемосхем
(M6 — самая объёмная веха проекта).

**Разграничение по выражениям (§11):** A владеет байткодом, ВМ и компилятором
(язык, набор инструкций, семантика). B владеет UI редактора выражений
(§11.9: автодополнение, подсветка, отображение ошибок). Граница — публичный API
`Scada.Expressions.Compiler`. Согласуется в M1 вместе с остальными контрактами.

### 16.4 Заглушки, обеспечивающие независимость

Реализуются в M1. Без них разработчик B простаивает значительную часть времени.

| Заглушка | Назначение |
|---|---|
| **Драйвер-симулятор** (`Scada.Drivers.Simulator`) | Генерирует 10 000–20 000 правдоподобных тегов: синусоиды, ступени, шум, имитация обрывов связи. Позволяет B разрабатывать схемы и тренды без контроллера и без готового драйвера Modbus. |
| **`InMemoryHistorian`** | Кольцевой буфер на последний час, реализует `IHistorian`. Позволяет B разрабатывать тренды до готовности реального формата архива. Замена на боевую реализацию — изменение одной регистрации в DI. |

### 16.5 Параллельные треки

| Период | Разработчик A | Разработчик B |
|---|---|---|
| 1 | **M0 + ядро M1 — совместно** | |
| 2 | M1: `TagTable`, движок опроса, бенчмарк | M1: shell, страница тегов, симулятор |
| 3 | M2: Modbus TCP/RTU | M3: модель схемы, Skia-рендерер |
| 4 | M4: формат архива, сжатие, агрегаты | M3: динамизация, SVG-символы, pan/zoom |
| 5 | M5: движок правил сигнализации | M4: тренды на ScottPlot |
| 6 | M2.5 / оптимизация / M7 | M6: редактор мнемосхем |
| 7 | Поддержка M6 со стороны данных, M7 | M6: редактор (продолжение) |
| 8 | **M8 — совместно: профилирование, установщик** | |

Длительная работа B над M6 — штатная ситуация: A в этот период закрывает архив,
сигнализацию и управление.

Подсистема выражений и сборка пакета (§11, §14.2) выполняются разработчиком A
в составе M1 и M3: они являются входными данными для схем, поэтому должны быть
готовы к моменту, когда B приступает к динамизации.

### 16.6 Порядок работы с репозиторием

- Ветка `main` защищена, слияние **только через pull request**.
- Именование веток: `feature/m2-modbus-tcp`, `feature/m3-scheme-renderer`.
- **Взаимный ревью обязателен.** При двух разработчиках это единственный барьер
  против накопления технического долга. Ревью содержательный, не формальный.
- **PR дробятся.** Веха одним PR на несколько тысяч строк не поддаётся ревью.
  Ориентир: M3 — это 4–5 отдельных PR (модель, рендерер, динамизация, символы, pan/zoom).
- CI на каждый PR: сборка без предупреждений, прогон тестов, проверка
  архитектурных правил (`Scada.Architecture.Tests`).

### 16.7 Работы, выполняемые совместно

Независимо от зон ответственности, совместно проектируются и реализуются два узла,
где цена ошибки максимальна, а последующее исправление наиболее затратно:

1. **`TagTable` на seqlock** (§9.1). Ошибки многопоточности не выявляются
   ревью по диффу. Требуются две пары глаз и отдельный стресс-тест.
2. **Формат архива** (§8.7). Переделка после накопления данных за месяцы
   практически невыполнима. Проектируется совместно на бумаге в M1.

По завершении каждой вехи — взаимный разбор сделанного. Требование: каждый
разработчик должен в общих чертах понимать зону ответственности коллеги, чтобы
отсутствие одного не останавливало работу.

### 16.8 Синхронизация

- Ежедневно, кратко: текущая задача, возникшие затруднения.
- Еженедельно: сверка с настоящим ТЗ — какие пункты закрыты, есть ли движение
  по открытым вопросам (§18).
- **Настоящий документ обновляется при каждом изменении принятых решений.**
  ТЗ, разошедшееся с кодом, теряет ценность и начинает вводить в заблуждение.

### 16.9 Известные риски совместной работы

| Риск | Мера |
|---|---|
| Конфликты слияния в `.sln` и `.csproj` | Central Package Management (§15.1) выносит версии пакетов в один файл и снижает частоту конфликтов |
| Расхождение стиля кода | `.editorconfig` + `TreatWarningsAsErrors` + дисциплина ревью |
| Пересечения в `Scada.App` (A добавляет страницы диагностики каналов) | Правка файла из чужой зоны — с предварительным уведомлением. Систематические правки одних и тех же файлов обоими — признак неверно проведённой границы, требует пересмотра зон |
| B опережает A и упирается в неготовое ядро | Заглушки §16.4 |

## 17. Дорожная карта

Исполнители указаны согласно зонам ответственности §16.3. M0 и M1 выполняются
совместно (§16.2) — на них формируются контракты, разделение зон начинается с M2.

### M0 — Фундамент — *совместно*

Структура решения по §5.2, `Directory.Build.props`, `Directory.Packages.props`,
`.editorconfig`, `CLAUDE.md`, DI через `Microsoft.Extensions.Hosting`,
логирование, главное окно с навигацией.

**Разделение поставок закладывается здесь** (§5.4): создаются `Scada.App.Shared`,
`Scada.App.Runtime` и `Scada.App.Engineering`, включая автотест запрета ссылок
на инструментальные сборки из исполнительной поставки.

**Критерий приёмки:** обе поставки запускаются, показывают shell с пустыми
страницами, решение собирается без предупреждений, автотест правил
зависимостей проходит.

### M1 — Ядро реального времени — *совместно*

`TagTable` на seqlock, `TagDefinition` и загрузчик конфигурации,
драйвер-симулятор, движок опроса, `IRuntimeClient` + `LocalRuntimeClient`,
`InMemoryHistorian` (заглушка, §16.4), страница «Теги» с живыми значениями.

Подсистема выражений (§11.2): набор инструкций, ВМ, компилятор, встроенные
функции, семантика качества. Первичная версия `Scada.Package.Builder` и
`Scada.Package` — чтобы схемы в M3 сразу разрабатывались на пакете, а не
на исходных файлах.

**Критерий приёмки:** бенчмарк на **20 000 тегов** укладывается в бюджеты §4.1
(RAM ≤ 500 МБ, CPU ≤ 25 %, задержка ≤ 200 мс). Исполнение выражения из
10 инструкций — не более 100 нс без аллокаций (§11.8). Формат архива описан
на бумаге.

Это контрольная точка архитектуры: если бюджеты не держатся, правим здесь,
пока это дёшево.

### M2 — Драйвер Modbus — *исполнитель: A*

Modbus TCP и RTU, группировка запросов, переподключение, таймауты,
диагностические теги канала.

**Критерий приёмки:** чтение реального контроллера LicOS, устойчивая работа
при обрыве и восстановлении связи.

### M2.5 — OPC UA — *исполнитель: A* *(только при подтверждении необходимости)*

### M3 — Мнемосхемы (режим исполнения) — *исполнитель: B*

Модель схемы под редактирование (§10.2), Skia-рендерер, динамизация через
выражения (§11.2), декларативные действия (§11.3), SVG-символы, панорамирование
и масштабирование.

**Критерий приёмки:** 30 FPS при 500 динамических элементах на целевом железе.
Схема загружается из `.scadapkg`; пересчёт выражений выполняется по эпохам (§11.7).

### M4 — Архив и тренды — *исполнители: A (архив) + B (тренды)*

Реализация формата, deadband, сжатие, минутные и часовые агрегаты, ротация,
политики на группу. Тренды на ScottPlot: realtime и исторический режим,
курсор, экспорт CSV.

**Критерий приёмки:** открытие тренда 10 тегов за 8 часов ≤ 1 с. Рост объёма
архива соответствует расчёту §8.4 (проверяется прогоном симулятора на сутки).

### M5 — Сигнализация — *исполнители: A (движок правил) + B (UI и журнал)*

Правила HiHi/Hi/Lo/LoLo, дискретные, отклонение от уставки, скорость изменения.
Квитирование, звуковая сигнализация, журнал событий с фильтрами,
заморозка архива вокруг аварий (§8.6).

### M6 — Редактор мнемосхем — *исполнитель: B*

Инструменты, undo/redo, сетка и привязки, библиотека символов, панель свойств,
настройка динамизации, редактор выражений по §11.9 (автодополнение, подсветка,
проверка до сборки, вычисление в реальном времени).

Самая объёмная веха проекта. Параллельно A закрывает M4, M5 и M7 со стороны данных.

### M6.5 — Сборка и доставка пакета — *исполнитель: A*

Завершение `Scada.Package.Builder`: полная валидация проекта, дедупликация пула
байткода, контрольные суммы. В исполнительной поставке — приём пакета,
проверка совместимости версий (§14.5), применение и **автоматический откат**
при неуспешном запуске (§14.4).

**Критерий приёмки:** неудачное обновление пакета не приводит к неработоспособности
системы — выполняется откат к предыдущей версии.

### M7 — Управление и права — *исполнители: A (запись в устройства) + B (UI прав доступа)*

Запись в устройства с подтверждением, роли и права доступа, журнал аудита.
Диагностика в исполнительной поставке по §5.4.2.

### M8 — Полировка и выпуск — *совместно*

Профилирование на целевом железе, ReadyToRun (опционально NativeAOT),
**два установщика** — инженерный и исполнительный, документация оператора
и инженера.

При выборе NativeAOT — окончательный отказ от уровня 3 скриптования (§11.4).
