### Ключевые решения, которые легко забыть

- **Текста выражений в пакете нет нигде** — только байткод в `code.bin`
  и индексы. Правило сквозное: строковые шаблоны параметров навигации
  сборка разбирает и кладёт разобранными (литералы + индексы). Следствие:
  исходный словарь `Parameters` из пакета не восстанавливается, и **парсер
  скобок существует только в сборке**.
- **Адресация действий не выходит за границу своей схемы** (внутри тела
  шаблона — за границы экземпляра). Межсхемное состояние — сессионный тег:
  у него есть память и он не зависит от того, что сейчас на экране.
- **Область видимости имени элемента** — тело схемы или тело шаблона,
  считается до раскрытия экземпляров. Контейнер областью не делается:
  область появляется там, где появляется копирование.
- **Свойство под привязкой не задаётся действием** и не порождает событие
  изменения: пересчёт привязки затрёт заданное.
- **Цвет из выражения не делаем.** Формально ВМ его даёт (при `Direct`
  результат кастуется в ARGB), но ключ темы из числа не получится никогда —
  такой элемент молча выпал бы из перекраски проекта. Вычисляемый цвет —
  привязка со стопами.

## 4. C4 и всё, что вокруг событий, — ОТЛОЖЕНО (решение 21.08)

**Решено вернуться к этому, когда появится с чем работать: контролы от Dev B
(C3) и редактор, в котором эти события настраивают.** Причина простая:
сегодня свойства меняет только наше же действие `SetProperty`, то есть
цепочку пишет тот же инженер, который может дописать продолжение прямо в неё.
Событие без независимого источника изменений проверить негде, кроме как
искусственно.

**Ориентир, к которому возвращаемся** (сценарий пользователя, куда понятнее
абстракций ниже):

> Поле ввода со свойством `Value`, не привязанное ни к какому тегу. Оператор
> ввёл 75 → выполняется цепочка → введённое значение попадает **в параметры
> действия** (например, вызов метода интеграции). Заводить тег ради значения,
> живущего три секунды, инженер не должен — хотя через тег тоже можно, если
> значение кому-то ещё нужно.

Что под этот сценарий понадобится сделать (всё — наше, всё маленькое):

1. **Событие изменения свойства**: вид события + поле «какое свойство»,
   валидация по `ElementSchemas`, запрет на свойстве под привязкой.
2. **Четвёртый вид значения параметра действия — ссылка на свойство
   элемента** (в дополнение к константе / строковому тегу / шаблону из C2).
   Хост читает значение в момент выполнения: ни ВМ, ни эпох, ни тега.
   Проверки — по образцу C5 (элемент в своей области, свойство есть у вида).
3. **Префикс длины у записи события в секции.** Сейчас это единственная
   запись без него; как только у события появляется собственное поле,
   старый читатель не сможет пропустить незнакомый вид события и развалит
   разбор всей секции. Делать заодно с п. 1.

От Dev B к тому моменту нужно: список событий контролов и **семантика
«ввод завершён»** у поля ввода — иначе вызов интеграции уедет на каждый
набранный символ.

**Мост «свойство → тег»** (отдельное действие, зеркальное C5) остаётся
в запасе для случая, когда значение должно пережить цепочку или уехать
на другой экран («что выбрано в журнале»). Для сценария выше он не нужен —
проверено ниже, разбор оставлен как готовая проработка.

### Проработка моста (если понадобится)

Механизм универсальный (любой элемент, валидация по `ElementSchemas`),
а не «про контролы». Модель, формат и валидация — наши; гашение по
равенству и предел глубины каскада — Dev B.

Замысел: новый вид события `PropertyChanged` с полем «какое свойство»,
дальше обычная цепочка действий. Менять свойство в рантайме могут
`SetProperty` (C5) и сам контрол (C3), отсюда каскад и предел глубины.

### Мост «свойство → тег» (вариант A) — проверено, готово к реализации

Событие само по себе не доносит новое значение: действия читают теги,
а не свойства элементов. Выражения ходят в `TagTable` и пересчитываются
по эпохам — свойств там нет и не будет (ровно та причина, по которой
аварии сделаны тегами, а не функцией ВМ). Значит нужен мост: действие
«записать свойство элемента в тег», зеркальное C5.

Что выяснила проверка кода:

- строковые теги полноценны: `ITagTable.WriteString`/`ReadString`, общая
  эпоха, грязный пересчёт их покрывает;
- сессионные теги умеют строки (`SessionTagRouter.WriteString`) и пишутся
  локально — без сети, права `Operate` и аудита (`LocalRuntimeClient`,
  `WriteMixedAsync`);
- **операторской записи строк нет**: `TagWriteItem` — это `(TagId, double)`;
  в `IRuntimeClient` прямо записано, что строковый вариант — отдельная
  задача. Есть только системная `WriteLocalString`.

Отсюда граница моста:

| Свойство | Куда | Как |
|---|---|---|
| Number / Boolean / Choice | любой числовой тег | существующий путь, изменений ноль |
| String | только **сессионный** строковый тег | новый метод контракта, локальная запись |
| String | объектный строковый тег | ошибка сборки: операторская запись строк — M7 |
| Color | никуда | ARGB числом бессмысленно, запрет |

Добавка к контракту — одна:

```csharp
ValueTask<TagWriteResult> WriteStringAsync(TagId tag, string text,
    string requestedBy, CancellationToken ct = default);
```

Локально: сессионный тег → локальная запись; объектный → `Failed`
с пояснением. Та же проверка при сборке, чтобы инженер узнал не на объекте.

Вопрос «делать мост сразу или с C3» снят вместе с откладыванием C4.

## 4а. Разбор жалобы Dev B на `GetChangedSince` (закрыто 21.08)

Метод возвращает **полное** число изменившихся тегов, а буфер заполняет
насколько хватило места: результат больше длины буфера — сигнал переполнения.
Так сделано намеренно (вернув число записанных, мы сделали бы неразличимыми
«буфер полон ровно» и «изменений втрое больше», и потеря прошла бы молча),
но правило нигде не было записано — и два места нашего кода поняли его
по-разному. Контракт описан в `ITagTable` и `IRuntimeClient`, в конвейере
аварий починено сравнение `==` → `>=` (при >4096 изменений за тик поток
падал), добавлены три теста. Сигнатуру решили не менять сейчас: оба
вызывающих у Dev B корректны, вернёмся к этому вместе с C3/C4.

## 4б. Кольцо `InMemoryHistorian` — припарковано (решение 21.08)

Всплыло попутно: **в рантайме кольцо никто не наполняет**. По концепту
(`archive-format.md` §3, §13.4) его должен наполнять `ArchivePipeline`, но
ветку не дотянули — конвейер о кольце не знает, а `RuntimeHost` создаёт его
без таблицы, так что и встроенный подаватель не стартует. Живьём работает
только в тестах и бенчмарках.

Разобрались и решили **не трогать**:

- **архив при этом работает**: диск, WAL, блоки, ротация, восстановление —
  всё запущено и покрыто тестами;
- **корректности кольцо не добавляет**: `FileArchiveStore` отдаёт и
  незакрытый блок, поэтому свежий край виден и без кэша;
- **realtime-режиму тренда история не нужна** — он копит точки сам из
  живой таблицы по эпохам;
- выигрыш остаётся только на повторных чтениях свежего окна, и он **не
  измерен**; строить ради него нечего, замер тоже решили пока не делать;
- по памяти «всё в кольцо» не проходит: 24 байта на точку, 10k тегов
  по 3600 точек = 824 МБ при бюджете АРМа 500 МБ (замер
  `MemoryFootprintMeasurement` показывает 1649 МБ на 20k). Формулировка
  концепта «последний час в памяти» при тике 100 мс арифметически
  не сходится: час — это 36 000 точек на тег.

Класс помечен в коде как отладочный, там же записаны дефекты подавателя
на случай, если ветку когда-нибудь дотянут.

Следствие, принятое сознательно: **неархивируемые теги истории не имеют**.
Показывать это в рантайме признаком в ответе не будем — правильнее не пускать
такие теги в тренд: редактор их не предлагает, сборка проверяет перья.
Проверка перьев требует схемы конфигурации контрола, поэтому едет вместе
с C3.
