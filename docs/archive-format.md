# Формат архива значений

**Статус:** проект v1.0
**Дата:** 2026-08-14
**Относится к:** ТЗ §8, веха M4

Документ закрывает долг §8.8 ТЗ («формат проектируется на бумаге») и является
частью ТЗ. По §16.7 формат относится к узлам, которые проектируются совместно:
переделка после накопления данных за месяцы практически невыполнима.

---

## 1. Границы документа

**Здесь:** хранение значений тегов (аналоговых и дискретных) на диске —
раскладка, кодеки, журнал упреждающей записи, восстановление, ротация.

**Не здесь:** события, алармы, аудит, пользователи и строковые теги. Они
реляционные, событийные и малы по объёму; их хранилище — SQLite,
описывается отдельно в рамках M5.

---

## 2. Что определило конструкцию

Требование заказчика — «архив за год». Из него и из бюджетов ТЗ вытекают
четыре ограничения, каждое из которых видно в формате:

| Требование | Откуда | Как отражено в формате |
|---|---|---|
| Год данных при 10 000 тегов, из них 10–30 % логируемых | §1.1 | Один уровень хранения, сырые значения за весь год. Уровней агрегатов нет |
| Потеря не более 10 с при аварийном завершении | §4.2 | Журнал упреждающей записи (WAL), сброс на диск не реже 10 с |
| Повреждённый файл не блокирует работу | §4.2 | CRC на блок, обрезка порванного хвоста при открытии, изоляция «один тег — один месяц» |
| Тренд 10 тегов за 8 часов ≤ 1 с | §4.1 | Сжатые блоки с summary-заголовком; широкий диапазон читается по заголовкам без разжатия |

Ключевое решение — **хранить сырые значения за весь год, а не строить уровни
агрегации**. Обоснование в ТЗ §8.5: год сырых данных на 2000 логируемых тегов —
десятки гигабайт, тогда как минутные агрегаты на тех же данных занимают больше,
чем сырьё, которое они обобщают. Агрегаты нужны для скорости чтения, а не для
экономии места, и в этом формате они получаются бесплатно из заголовков блоков.

## 3. Конвейер

```
ArchivePipeline — BackgroundService с PeriodicTimer, читает TagTable сам
   │
   ├─ выбор по режиму логирования (§6): Periodic / OnChange / Schedule
   ├─ проверка качества (§6.2) и монотонности меток (§6.3)
   ├─ приведение представления (§7): целое по решётке ScaleFactor либо double
   │
   ├──→ кольцевой буфер в памяти, последний час      → realtime-тренды, диска не касаются
   │
   ├──→ WAL: append + CRC, сброс не реже 10 с        → закрывает §4.2
   │
   └──→ буфер потока заполнен либо истёк час
            → блок: метки времени + значения + качество, сжатые
            → summary-заголовок блока
            → дописывается в файл archive/<год-месяц>/<streamId>.dat
                    │
                    └─ ротация: удалить каталоги месяцев старше RetentionDays
```

**Конвейер тянет данные сам, его никто не вызывает.** Интерфейса вида
`Append(tag, value)` не существует, и это принципиально: режим Periodic обязан
писать отсчёт, когда значение **не** менялось, — разбудить его событием
невозможно. Поэтому конвейер тикает по таймеру и читает `TagTable`, а
изменившиеся теги для режима OnChange находит через механизм эпох (ТЗ §9.2),
который уже существует.

Побочная выгода: публичного способа дописать в архив в обход правил режима,
качества и монотонности просто нет.

**Период тика конвейера равен периоду самого частого опроса** (по умолчанию
100 мс при максимальных 10 Гц). Более редкий тик терял бы короткие импульсы
дискретных тегов: переключение длительностью 200 мс между тиками осталось бы
незамеченным. Если замеры покажут, что общий тик обходится дорого при малой
доле логируемых тегов, он разделяется на быстрый контур для OnChange и медленный
для Periodic — но начинать с двух контуров без замера незачем.

Конвейер не знает, куда пишет: всё, что ниже кольцевого буфера, спрятано за
`IArchiveStore` (§13.3). Выбор режима, представления и квантование — выше шва и
не меняются при смене хранилища.

## 4. Идентификация потока

**Поток (stream)** — последовательность значений одного тега во времени.
Единица хранения и адресации в архиве.

Поток **нельзя** идентифицировать по `TagId`. `TagId` — индекс в `TagTable`,
он приходит из скомпилированного пакета (ТЗ §11.6, раннее связывание), а у
диагностических тегов ещё и выводится из порядка каналов
(`SCADA.Runtime/Configuration/DiagnosticsGenerator.cs`). Удаление канала
сдвигает индексы, и архив, ключёванный по `TagId`, молча сошьёт историю одного
тега с историей другого. Обнаружится это через месяцы.

Поток идентифицируется **именем тега** — оно уникально по §6.2 и стабильно
между пересборками пакета.

### 4.1 Реестр потоков

Файл `archive/streams.idx`. Текстовый UTF-8, по строке на поток, append-only.
Текстовый — сознательно: на объекте нет редактора (§5.4.2), реестр должен
читаться и чиниться подручными средствами.

```
# streamId ; name ; dataType ; createdUtc
1;Boiler1.Temp;Analog;2026-08-14T09:12:31Z
2;Pump1.Running;Discrete;2026-08-14T09:12:31Z
3;$Channel1.State;Analog;2026-08-14T09:12:31Z
```

Правила:

- `streamId` назначается один раз и **никогда не переиспользуется**, даже после
  удаления тега из конфигурации.
- Запись из реестра **не удаляется никогда**. Удалённый из проекта тег
  сохраняет свой поток до истечения срока хранения.
- При загрузке конфигурации строится отображение `TagId → streamId`. Имя,
  отсутствующее в реестре, добавляет новую строку.
- Переименование тега в конфигурации создаёт **новый поток**; история остаётся
  под старым именем. Это осознанное поведение: молча приписать чужую историю
  хуже, чем разорвать её явно. Слияние выполняется правкой реестра вручную.
- Битая строка при чтении — пропускается с записью в журнал, остальные потоки
  работают.

## 5. Раскладка на диске

```
archive/
├─ streams.idx                 реестр потоков (§4.1)
├─ wal/
│  ├─ 00000001.wal             сегменты журнала упреждающей записи
│  └─ 00000002.wal
├─ 2026-07/
│  ├─ 000001.dat               поток 1 за июль
│  └─ 000002.dat
└─ 2026-08/
   ├─ 000001.dat
   └─ 000002.dat
```

**Файл на поток на месяц.** Обоснование выбора:

- 2000 логируемых тегов × 12 месяцев = 24 000 файлов в год, по 2000 в каталоге.
  NTFS это не замечает.
- Чтение одного тега за год — 12 последовательных файлов, никакого внутрифайлового
  каталога не нужно.
- Ротация — удаление каталога месяца. Одна операция, без переписывания файлов.
- Повреждение изолировано: теряется один тег за один месяц, а не архив.
- Файл потока за месяц — порядка 1–2 МБ (§10). Читается целиком, поэтому
  **индекс блоков внутри файла не нужен**: блоки проходятся последовательно по
  полю длины.

## 6. Режимы логирования

Режим определяется природой сигнала и выводится из `DataType`; настройка на тег
не требуется, но допускается.

| Режим | По умолчанию для | Что пишется |
|---|---|---|
| **Periodic** | `Analog` | Отсчёт через фиксированный интервал, независимо от того, изменилось ли значение |
| **OnChange** | `Discrete` | Отсчёт при изменении значения либо качества |
| **Schedule** | — (только явно) | Отсчёт в заданные моменты: смена, сутки, месяц. Для отчётных срезов и счётчиков |

Интервал Periodic по умолчанию: `max(период опроса устройства, 1 с)`. Тег,
опрашиваемый на 10 Гц ради алармов, пишется в архив раз в секунду, если явно не
задано иное. Это единственный рычаг снижения объёма, и он **предсказуем**: объём
считается из конфигурации точно, в отличие от порогового отбора, где объём
зависит от поведения процесса и растёт именно в аварию.

Механизм задаётся `TagLoggingConfiguration` (`SCADA.Core/Tags/`).
`GetNextLoggingTime` вызывается на каждый записанный отсчёт каждого
логируемого тега, поэтому LINQ и замыкания в нём недопустимы (ТЗ §15.2):
обход расписания — обычный цикл.

**Расписание задаётся в местном времени объекта, а не в UTC.** «08:00» — это
начало смены на объекте. Пояс приходит параметром (`SiteTimeZone`, §21), а не
берётся из ОС: сервер может стоять не на объекте (ТЗ §5.1), а на промышленных
ПК, развёрнутых клонированием образа, пояс нередко остаётся чужим. При неявной
настройке сменные итоги молча уезжают на несколько часов, и расхождение
замечают при сверке с бумажным журналом через месяцы. Неизвестный
идентификатор пояса валит запуск, а не подменяется поясом системы молча.

Оба перехода на летнее время решены явно, иначе раз в год сменный отчёт
терялся бы либо задваивался:

| Случай | Поведение |
|---|---|
| Час пропущен при переходе вперёд (02:30 не существует) | Запись сдвигается на ближайший существующий момент |
| Час повторён при переходе назад (02:30 наступает дважды) | Берётся **первое** наступление, запись происходит один раз |

Хранение при этом всегда в UTC: пояс влияет только на выбор моментов.

### 6.1 Семантика пропуска — различается по режиму

Формат файла у обоих режимов одинаков, а **смысл отсутствия отсчёта
противоположен**:

| Режим | Отсутствие отсчёта означает | Как читатель рисует тренд |
|---|---|---|
| Periodic | «не собирали» — связь оборвана, сервер стоял | **разрыв линии** |
| OnChange | «не менялось» | **горизонтальное удержание** до следующей точки |

Поэтому режим логирования хранится **в заголовке каждого блока**, а не только в
конфигурации: конфигурация может измениться, а прочитать старые данные надо
правильно. Без этого оборванная связь на тренде выглядит как «параметр стабильно
держался» — ровно та ошибка, из-за которой разбор аварии уходит не туда.

### 6.2 Качество: пишется только достоверное

Правило одно для всех режимов:

- качество `Good` — отсчёт пишется по режиму логирования;
- переход `Good → Uncertain` или `Good → Bad` — пишется **одна** точка с новым
  качеством и фактическим значением на момент перехода;
- пока качество не `Good` — **не пишется ничего**;
- восстановление — пишется первый достоверный отсчёт.

`Uncertain` обрабатывается так же, как `Bad`: в архив попадает только
достоверное.

Обоснование. Наивная реализация при Periodic и трёхчасовом обрыве запишет
10 800 копий устаревшего значения — они хорошо сожмутся, но будут утверждать,
что измерение велось. При выбранном правиле образуется пропуск, а пропуск в
Periodic-потоке по §6.1 и означает «не собирали». Смысл совпадает с фактом без
дополнительных механизмов.

Одна точка на переходе нужна, чтобы на тренде было видно **когда именно**
оборвалось, а не только что данных нет.

### 6.3 Монотонность меток времени — обязательный инвариант

Кодек (§9) и поиск по диапазону предполагают **строго возрастающие** метки
внутри потока. Нарушить это могут:

- коррекция системных часов назад (NTP, ручная правка, пауза виртуальной машины);
- повторная запись одного и того же значения. Подтверждённый случай:
  `PollingEngine.MarkTagsBad` обновляет метку времени, оставляя прежнее значение,
  и вызывается на каждой неудачной попытке переподключения — при обрыве метка
  тега обновляется каждые несколько секунд при неизменном значении.

Правило записи:

```
если ts <= lastWrittenTs потока:
      отсчёт отбрасывается, счётчик DroppedNonMonotonic += 1
```

Счётчик отброшенных — диагностический тег (§22). Молча отбрасывать нельзя:
устойчивый рост счётчика означает неверно настроенное время либо ошибку в
конвейере.

**Скачок часов вперёд отдельного порога не имеет.** Блок закрывается, когда его
пролёт превышает `BlockTimeout` (§8.6, час), и этого достаточно: скачок дальше
часа рвёт блок, а более мелкий оставляет внутри пропуск, не портя
summary-заголовок.

Более короткий порог был бы вреден: у тега в режиме OnChange разрыв в минуты и
часы — норма, а не аномалия, и закрытие блока на каждом таком разрыве вернуло бы
блоки из одной-двух точек, ради устранения которых и заведено накопление (§8.6).
Отличить «часы прыгнули» от «дискрет не менялся полчаса» по одному интервалу
нельзя, поэтому единственный критерий — пролёт блока.

## 7. Представление значения

### 7.1 Решётка ScaleFactor

Значение аналогового тега приходит из целого регистра ПЛК:

```
value = raw × ScaleFactor + ScaleOffset
```

Множество достижимых значений — решётка с шагом `ScaleFactor`. Тег с
`ScaleFactor = 0.01` физически не принимает значение 75,313: только 75,31 или
75,32. Значит хранить надо **целое `raw`, а не double**:

```csharp
long units = (long)Math.Round((value - offset) / scale);
// обратно: units * scale + offset — побитово тот же double
```

Это **без потерь**: восстанавливается тот же самый `double`, что отдал драйвер,
бит в бит.

Выигрыш — в кодеке. Целые кодируются разностью разностей, и на равномерно
меняющихся сигналах она вырождается в ноль:

| Поведение тега | `units` | Разность разностей | Бит на значение |
|---|---|---|---|
| стоит | 7531, 7531, 7531 | 0 | **1** |
| дрожит на младший разряд АЦП | 7531, 7532, 7531 | ±2 | 9 |
| линейный разгон | 7531, 7535, 7539 | **0** | **1** |
| счётчик-накопитель | +17 каждый раз | **0** | **1** |
| скачок | — | велика | 12–16 |

Для сравнения: XOR по `double` на разгоне и на счётчике стоит 12–20 бит на
точку, потому что мантисса меняется каждый отсчёт. Именно на интеграторах,
наработке и расходах целочисленное кодирование выигрывает на порядок.

### 7.2 Выбор кодека — автоматический, настройки нет

Кодек выбирается **на каждый блок**, проверкой решётки по факту:

```
для каждого значения блока:
    units = round((value - offset) / scale)
    если units × scale + offset != value побитово  →  решётки нет
все прошли  →  кодек ScaledInt, scale и offset пишутся в заголовок блока
иначе       →  кодек GorillaXor по double
```

Проверка — одно умножение и сравнение на значение, в горячем пути бесплатна.
Неверный `ScaleFactor` в конфигурации, вычисляемый тег, float прямо из ПЛК,
переполнение на больших значениях — всё откатывается на XOR автоматически.
`ScaleFactor` работает как **подсказка**, корректность проверяется, а не
предполагается.

`scale` и `offset` хранятся в заголовке блока, а не в реестре: инженер может
исправить неверный масштаб в конфигурации, и старые блоки обязаны продолжать
декодироваться со своим прежним масштабом. Блок самодостаточен.

### 7.3 Квантование — обязательное лекарство, а не украшение

Замер (`CodecCalibrationTests`) показал, что для потоков без решётки XOR не
просто плохо сжимает, а **раздувает данные**:

| Архетип | Байт на отсчёт | МБ на тег в год при 1 Гц |
|---|---|---|
| На решётке, стабильный | 0,28 | 8 |
| На решётке, типовой (20 % изменений) | 0,53 | 16 |
| На решётке, активный (100 %) | 0,95 | 29 |
| На решётке, линейный разгон | 0,28 | 8 |
| float32 из ПЛК, расширенный до double | 1,37 | 41 |
| **Вычисляемый double** | **8,39** | **252** |
| Дискретный | 0,27 | 8 |

8,39 байта — это больше, чем 8 байт несжатого значения. Причина в схеме: у
соседних вычисляемых значений XOR не оставляет ни ведущих, ни хвостовых нулей,
и Gorilla тратит 13 служебных бит поверх полной мантиссы. Это свойство схемы,
а не дефект реализации.

**Объявленная точность `Precision` создаёт решётку искусственно** и переводит
тег с раздувающего XOR на разность разностей по целым:

```
вычисляемый double без квантования:  8,39 байт/отсчёт
он же с точностью 2 знака:           0,78 байт/отсчёт
                                     ────────────────
                                     выигрыш 10,8×
```

Квантование выполняется **той же формулой, которой стор проверяет
принадлежность решётке** — `round((v - offset) / quantum) * quantum + offset`.
Поэтому переключение кодека гарантировано по построению, а не по совпадению
округлений.

Округление **с потерями**, поэтому применяется только по явному указанию
инженера и **только на записи в архив**: в `TagTable`, на мнемосхеме и в
правилах сигнализации живёт полное значение.

Калькулятор объёма (ТЗ §4.3) считает теги без решётки и без точности по худшей
константе и предупреждает о них при сборке пакета: отличить вычисляемый тег от
честного float32 по конфигурации нельзя, а занижать оценку опаснее, чем
завысить — заниженная обнаруживается заполненным диском.

Отличие от порогового отбора (deadband), который в этом формате не применяется:
квантование округляет к **фиксированной абсолютной решётке**, ошибка ограничена
половиной шага и не накапливается. Пороговый отбор сравнивает с **последним
записанным** значением, поэтому медленный дрейф выедает целиком, а ошибка копится
без предела.

## 8. Двоичная раскладка

Все целые — little-endian. Битовые потоки заполняются от старшего бита к
младшему, хвост последнего байта дополняется нулями.

### 8.1 Единица времени

Метки времени хранятся в **миллисекундах UTC** (не в тиках). Обоснование:
разность разностей должна быть малым числом, а в тиках интервал 1 с — это
10 000 000. При максимальной частоте опроса 10 Гц (ТЗ §18) миллисекунды
избыточны с запасом.

Преобразование не требуется: `TagValue.TimeStampUtc` **уже хранится в
Unix-миллисекундах** (`SCADA.Core/Tags/TagValue.cs`, использование в
`PollingEngine`), единица совпадает. Описание в ТЗ §6.1 («тики UTC») разошлось с
кодом и приводится в соответствие.

Локальное время в архиве не используется нигде. Часовой пояс объекта
(`SiteTimeZone`, §21) влияет только на режим Schedule и на границы отчётных
периодов.

### 8.2 Заголовок файла потока

```
смещение  размер  поле
0         4       магия "SCAR"
4         2       версия формата = 1
6         4       streamId
10        2       резерв, нули
                  → 16 байт, далее подряд блоки
```

### 8.3 Блок

```
смещение  размер  поле
0         2       магия блока = 0xB10C          для поиска границы при ремонте
2         4       blockLength                   полная длина блока, включая CRC
6         2       flags                         см. 8.4
8         4       count                         число отсчётов
12        8       firstTimestampMs
20        8       lastTimestampMs
28        8       summaryA                      см. 8.5
36        8       summaryB
44        8       summaryC
52        4       goodCount                     сколько отсчётов с качеством Good
56        8       scale                         только при кодеке ScaledInt
64        8       offset                        только при кодеке ScaledInt
--------  ------  ---------------------------------------------------------
          n       битовый поток меток времени   §9
          n       битовый поток значений        §10
          n       поток качества                §11
--------  ------  ---------------------------------------------------------
last-4    4       CRC32 всего блока до этого поля
```

Заголовок — 56 либо 72 байта. При целевом размере блока 4096 отсчётов накладные
расходы составляют 3–5 %.

### 8.4 Поле flags

```
биты 0–3    кодек значений: 0 = ScaledInt, 1 = GorillaXor, 2 = Discrete
бит  4      наличие полей scale/offset
биты 5–6    режим логирования: 0 = Periodic, 1 = OnChange, 2 = Schedule
биты 7–8    тип данных: 0 = Analog, 1 = Discrete
бит  9      блок закрыт по таймауту, а не по заполнению
биты 10–15  резерв, нули
```

### 8.5 Поля summary — смысл зависит от типа данных

Это и есть «агрегаты», получаемые ценой ноль байт: широкий диапазон читается по
заголовкам блоков без разжатия содержимого.

Слоты по 8 байт, читаются как int64; у аналогового в них лежат биты double.

| Поле | Analog | Discrete |
|---|---|---|
| summaryA | minValue (double) | число переключений (int64) |
| summaryB | maxValue (double) | время в состоянии 1, мс (int64) |
| summaryC | сумма значений (double), для среднего | резерв |

Среднее по аналоговому — `summaryC / goodCount`. Среднее по дискретному так
считать **нельзя**: при OnChange отсчёты неравномерны, нужна доля времени, для
чего и хранится `summaryB`.

**В min/max/сумму входят только достоверные значения** (§6.2): точка перехода в
`Bad` несёт последнее известное значение, и в агрегате ей не место. Делитель для
среднего — `goodCount`, а не `count`. Если достоверных значений в блоке нет
вовсе, все три слота содержат NaN, а признаком служит `goodCount == 0`.

Отсюда же смысл полей бакета при чтении: `Count` считает все отсчёты и отличает
пропуск (`Count == 0`) от участка без достоверных данных
(`Count > 0, GoodCount == 0`), а `Min`/`Max`/`Avg` пустого бакета равны NaN, а
не нулю — ноль читался бы как измеренное значение.

### 8.5.1 Замеренная цена заголовочного пути

Бенчмарк `ArchiveBenchmarks` (ТЗ §15.4), блоки по 4096 отсчётов, сутки данных
при 1 Гц:

| Операция | Время | Аллокации |
|---|---|---|
| Сборка блока 4096 отсчётов | 72 мкс | 116 КБ |
| Разбор блока 4096 отсчётов | 76 мкс | 201 КБ |
| **Проход по заголовкам суток** | **63 нс** | **0** |
| Полный разбор суток с разжатием | 1,47 мс | 4,8 МБ |

Разница между двумя последними строками — **более четырёх порядков** — и есть
причина, по которой формат построен вокруг summary-заголовков. Экстраполяция на
бюджет ТЗ §4.1 «тренд 10 тегов за год ≤ 2 с»: по заголовкам это доли секунды,
полным разжатием — около пяти секунд, то есть бюджет не держится.

Аллокации при полном разборе блока (массивы меток, значений, качества и точек)
приемлемы: сырое чтение редко и ограничено `MaxPointsPerQuery` (§14.1).
Оптимизировать его до появления замера, показывающего проблему, незачем.

### 8.6 Условия закрытия блока

Блок закрывается и дописывается в файл при первом из событий:

- накоплено 4096 отсчётов;
- с момента первого отсчёта в блоке прошёл 1 час;
- смена календарного месяца;
- штатная остановка службы.

Ограничение по времени обязательно: без него медленный поток (дискрет при
OnChange) держал бы сегмент WAL сутками. Короткий блок допустим, `count`
указывает фактическое число отсчётов.

### 8.6.1 Вместимость блока выводится из бюджета памяти

Открытый блок держит отсчёты в памяти до закрытия: **24 байта на отсчёт на
каждый логируемый поток**. При 4096 отсчётов и 2000 тегах это 196 МБ —
заметная доля бюджета мастер-АРМа в 800 МБ (ТЗ §4.1), и до замеров M4 эта
статья не фигурировала ни в одной оценке.

Задавать вместимость блока напрямую нельзя: это требовало бы от интегратора
считать `теги × вместимость × 24` — ровно то, чего мы не стали требовать от
него по диску. Поэтому задаётся **бюджет памяти**, а вместимость выводится:

```
BlockPoints = clamp(MaxOpenBlockMemoryMb × 1 МБ / (логируемые теги × 24), 256, 4096)
```

| Логируемых тегов | Вместимость блока | Пик памяти при бюджете 64 МБ |
|---|---|---|
| 100 | 4096 (максимум) | 10 МБ |
| 2000 | ~1400 | 64 МБ |
| 6000 | ~460 | 64 МБ |
| 20 000 | 256 (пол) | 123 МБ — бюджет превышен сознательно |

Малый проект получает максимальный блок и наилучшее сжатие; большой ужимается
автоматически. Нижняя граница в 256 отсчётов — предел, ниже которого заголовок
блока в 76 байт стоит сопоставимо с самими данными: там экономия памяти
оплачивалась бы уже заметным ростом архива, и бюджет сознательно нарушается.

Цена уменьшения вместимости — рост числа заголовков: вчетверо меньший блок даёт
вчетверо больше заголовков, что для тега на 1 Гц означает примерно +10 % объёма
на диске. Обмен «память против диска» настраивается одним числом и правки
формата не требует.

Явный `BlockPoints` отменяет расчёт: инженер вправе решить сам.

Ожидаемый пик памяти сообщается при сборке пакета рядом с оценкой объёма
(ТЗ §4.3) и при запуске службы — так же, как требование к диску.

**Журнал упреждающей записи в этот счёт не входит:** он пишется через
`FileStream` и живёт на диске, а не в памяти (§12.1).

## 9. Кодек меток времени

Разность разностей, схема Gorilla. Первая метка — полные 64 бита, вторая —
разность 32 бита, далее:

```
dod == 0                    →  '0'                     1 бит
-63   ≤ dod ≤ 64            →  '10'   + 7 бит          9 бит
-255  ≤ dod ≤ 256           →  '110'  + 9 бит         12 бит
-2047 ≤ dod ≤ 2048          →  '1110' + 12 бит        16 бит
иначе                       →  '1111' + 32 бита       36 бит
```

При Periodic интервал постоянен, `dod` равен нулю почти всегда — **1 бит на
метку**. Дрожание планировщика в пределах ±63 мс укладывается в 9 бит.

## 10. Кодеки значений

### 10.1 ScaledInt

Разность разностей по `units`, собственный набор корзин (асимметричные,
как у кодека меток времени, см. §9):

```
dod == 0                    →  '0'                      1 бит
-63   ≤ dod ≤ 64            →  '10'    + 7 бит          9 бит
-255  ≤ dod ≤ 256           →  '110'   + 9 бит         12 бит
-2047 ≤ dod ≤ 2048          →  '1110'  + 12 бит        16 бит
-2³¹  ≤ dod ≤ 2³¹ − 1       →  '11110' + 32 бита       37 бит
иначе                       →  '11111' + 64 бита       69 бит
```

Первое значение — полные 64 бита, второе — разность 64 бита.

### 10.2 GorillaXor

Классическая схема для `double`:

```
XOR с предыдущим == 0       →  '0'                                  1 бит
иначе, окно предыдущего подходит  →  '10' + значащие биты
иначе                       →  '11' + 5 бит (ведущие нули)
                                   + 6 бит (длина)
                                   + значащие биты
```

### 10.3 Discrete

Один бит на отсчёт. При OnChange значение всегда меняется на противоположное и
формально выводимо, но бит хранится явно: отсчёт может быть записан и по
изменению качества при том же значении, и явный бит снимает этот особый случай
ценой 4096 бит на блок.

---

## 11. Поток качества

Качество (§6.1 ТЗ: Good / Uncertain / Bad) хранится **обязательно**: иначе
период с оборванной связью неотличим от нормальной работы, а последнее известное
значение при `Bad` выглядит как достоверное измерение.

Кодирование — длинами серий, качество меняется редко:

```
[varint длина серии][1 байт качество] ... пока сумма длин не даст count
```

Типичный блок — одна серия, 2–3 байта на 4096 отсчётов.

`goodCount` в заголовке позволяет оценить достоверность агрегата, не разжимая
блок.

## 12. Журнал упреждающей записи (WAL)

Закрывает требование §4.2: потеря не более 10 секунд.

Сегменты `archive/wal/NNNNNNNN.wal`, ротация по достижении 16 МБ.

```
запись:
  4 байта   длина полезной части
  4 байта   CRC32 полезной части
  n байт    полезная часть:
              4 байта   streamId
              8 байт    timestampMs
              8 байт    value (double, как пришёл от драйвера)
              1 байт    quality
```

Значение пишется в WAL **как есть**, без приведения к решётке: WAL — это сырой
журнал, всё преобразование происходит при сборке блока.

Сброс на диск (`FileStream.Flush(true)`) — не реже одного раза в 10 секунд и
при штатной остановке.

### 12.1 Освобождение сегментов — обязательная часть, а не оптимизация

Сегмент удаляется, когда все его записи дошли до файлов потоков. Признак
готовности считается так: самая ранняя метка среди **открытых** блоков — это
граница незакоммиченного; всё строго старше неё уже на диске, и журнал для него
не нужен.

Освобождение выполняется на каждом сбросе журнала, то есть не реже
`FlushIntervalMs`. **Без него журнал растёт всё время работы службы и обгоняет
сам архив:** при 2000 логируемых тегах на 1 Гц это 58 КБ/с, то есть около
5 ГБ в сутки против ~70 МБ полезных данных. Проверяется тестом
`Journal_DoesNotGrowWithoutBound`.

Гранулярность освобождения — сегмент целиком, поэтому `WalSegmentSizeMb`
влияет на то, насколько быстро журнал ужимается: слишком крупный сегмент
удерживает данные дольше нужного.

Верхняя граница размера журнала — объём данных за время жизни самого старого
открытого блока, то есть `BlockTimeout` (§8.6). При часовом таймауте и
2000 тегах на 1 Гц это порядка 200 МБ. Величина считается точно и уменьшается
сокращением `BlockTimeout` — тем же параметром, что ограничивает и память под
открытые блоки.

## 13. Слои и контракты

Раздел определяет границу между зонами ответственности разработчиков (ТЗ §16.1):
тренды разрабатываются параллельно с архивом и кодируются против этих
интерфейсов.

```
Тренды, страница диагностики (B)
   │
IRuntimeClient                    те же четыре запроса, результат — массивы
   │   (gRPC либо локально)
─────────────────────────────────── граница процесса
   │
IHistorian                        фасад чтения. Говорит в TagId (§13.1)
   │
   ├── кольцевой буфер, последний час
   ├── отображение TagId → streamId, реестр потоков (§4)
   │
ArchivePipeline                   запись: режимы, качество, представление (§3)
   │
IArchiveStore                     шов хранилища. Говорит в streamId (§13.3)
   │
FileArchiveStore │ InMemoryArchiveStore │ (TimescaleStore когда-нибудь)
```

Правило границы: **`TagId` живёт только выше `IHistorian`, `streamId` — только
ниже.** Отображение и реестр потоков сосредоточены в одном месте, и это то, что
защищает от сшивания истории разных тегов при пересборке пакета (§4).

### 13.1 IHistorian — фасад чтения

```csharp
/// Чтение истории. Скрывает горячее кольцо, отображение TagId → поток
/// и конкретное хранилище.
public interface IHistorian
{
    /// Сырые точки диапазона. Свежие — из кольца, остальные с диска.
    ValueTask<HistoryResult> ReadRawAsync(
        TagId id, long fromMs, long toMs,
        Memory<TagValue> destination, CancellationToken ct);

    /// Агрегаты. Запросил N бакетов — дал Memory на N.
    ValueTask<HistoryResult> ReadBucketsAsync(
        TagId id, long fromMs, long toMs,
        Memory<ArchiveBucket> buckets, CancellationToken ct);

    /// Последнее значение не позже atMs. Левый край тренда.
    ValueTask<TagValue?> ReadAtAsync(TagId id, long atMs, CancellationToken ct);

    /// Последние N из кольца: без диска, без await.
    int ReadRecent(TagId id, Span<TagValue> destination);
}

public readonly record struct HistoryResult(
    int         Count,
    LoggingMode Mode,          // Periodic | OnChange | Schedule
    bool        Downsampled);  // сработал MaxPointsPerQuery (§14.1)

public readonly record struct ArchiveBucket(
    long   StartMs, long EndMs,
    double Min, double Max, double Avg,
    int    Count,        // 0 = данных в бакете не было
    int    GoodCount);
```

Обоснование каждого решения:

- **Записи в интерфейсе нет.** Конвейер тянет данные сам (§3), дописать в архив в
  обход правил невозможно.
- **`Mode` в результате обязателен, а не справочен.** Без него тренд нельзя
  нарисовать правильно: при Periodic пропуск означает разрыв линии, при
  OnChange — удержание значения (§6.1). Читатель обязан получать семантику
  вместе с данными.
- **`ReadAtAsync` — отдельный запрос, а не частный случай диапазона.** У тега в
  режиме OnChange последнее изменение могло произойти трое суток назад: запрос
  «последний час» вернёт ноль точек, и тренд нарисует пустоту вместо
  горизонтальной линии на правильном уровне. Без якоря левый край тренда
  систематически неверен.
- **`Count == 0` в бакете — это пропуск**, отличимый от «значение равно нулю».
  Отдельного флага не требуется.
- **`Memory<T>`, а не `Span<T>`, — вынужденно:** чтение с диска асинхронно
  (ТЗ §15.2), а `Span` в async-сигнатуре запрещён компилятором. Синхронный
  `ReadRecent` работает с кольцом в памяти, ему `Span` допустим.
- **Буфер даёт вызывающий.** Для бакетов это ещё и естественный предел ответа:
  сколько запросил — столько максимум и получит.
- **`ReadRecent` оставлен в этом же интерфейсе намеренно:** он единственный
  синхронный и единственный, кто гарантированно не касается диска. Соседство с
  асинхронными методами делает наличие дешёвого пути очевидным. Его потребители —
  realtime-тренд и правила сигнализации (`RateOfChange`, ТЗ §17 M5) через
  `EvaluationContext`.

### 13.2 IRuntimeClient — тот же контракт через границу процесса

Клиент повторяет **те же четыре запроса**, чтобы тренды писались один раз и
одинаково работали в режимах single ARM и выделенного сервера (ТЗ §5.1).

Но это **отдельный интерфейс, а не тот же самый**: через gRPC буферами
управлять нельзя, результат приходит массивами. Попытка объединить их упрётся в
`Memory<T>` и в сетевую асинхронность. Совпадают формы запросов и смысл полей,
а не сигнатуры.

```csharp
ValueTask<HistorySeries[]> ReadHistoryAsync(
    IReadOnlyList<TagId> ids, long fromMs, long toMs,
    int maxPointsPerTag, CancellationToken ct = default);

ValueTask<BucketSeries[]> ReadBucketsAsync(
    IReadOnlyList<TagId> ids, long fromMs, long toMs,
    int bucketCount, CancellationToken ct = default);

ValueTask<TagValue?[]> ReadAtAsync(
    IReadOnlyList<TagId> ids, long atMs, CancellationToken ct = default);

int ReadRecent(TagId id, Span<TagValue> destination);
```

**Запросы пакетные по тегам.** Тренд на 10 тегов не должен порождать 10 сетевых
обменов; пакетные варианты существуют только на этом уровне, ниже шва работа
идёт по одному потоку.

`HistorySeries` и `BucketSeries` несут `Mode` и `Downsampled` рядом с данными —
без режима логирования тренд нельзя нарисовать правильно (§6.1), без признака
прореживания читатель принял бы агрегаты за сырые точки.

**Архив может быть выключен.** Тогда запросы истории отдают пустые ряды, а не
падают: мнемосхемы, текущие значения и диагностика от архива не зависят.

`ArchiveBucket` живёт в `SCADA.Core`, а не в хранилище: это примитив модели
данных, общий для стора, фасада и контракта UI. Иначе клиентская сторона тянула
бы за собой всю механику формата.

### 13.3 IArchiveStore — шов хранилища

Реализация на PostgreSQL + TimescaleDB в M4 **не пишется** (ТЗ §8.7), но шов
проектируется так, чтобы она была возможна без переделки конвейера.

```csharp
public interface IArchiveStore
{
    void RegisterStream(int streamId, ArchiveStreamConfig config);

    void Write(int streamId, ReadOnlySpan<ArchivePoint> points);

    ValueTask<int> ReadRawAsync(int streamId, long fromMs, long toMs,
                                Memory<ArchivePoint> destination, CancellationToken ct);

    ValueTask<int> ReadBucketsAsync(int streamId, long fromMs, long toMs,
                                    long bucketMs, Memory<ArchiveBucket> destination,
                                    CancellationToken ct);

    ValueTask<ArchivePoint?> ReadAtAsync(int streamId, long atMs, CancellationToken ct);

    ValueTask FlushAsync(CancellationToken ct = default);

    StoreCapabilities Capabilities { get; }
}
```

`FlushAsync` закрывает открытые блоки и отбрасывает журнал. Без него открытый
блок жил бы в памяти до часа и терялся при остановке; вызывается конвейером в
`StopAsync`.

`ReadAtAsync` находится и здесь, и в фасаде, потому что искать назад умеет
только стор: у него раскладка файлов, и он может уйти на нужную глубину вместо
фиксированного окна.

**Открытый блок обязан быть виден в чтении.** Стор владеет им единолично,
поэтому `ReadRawAsync`, `ReadBucketsAsync` и `ReadAtAsync` дочитывают его после
файлов. Иначе только что записанные данные не читались бы до закрытия блока —
до часа.

Четыре правила, без которых шов бесполезен:

1. **`ReadBuckets` обязателен наравне с `ReadRaw`.** Тренду за год нужно не
   30 миллионов точек, а тысяча бакетов. Если в шве только чтение диапазона,
   реализация на TimescaleDB будет вынуждена тащить всё в клиент вместо
   `time_bucket` на сервере — то есть окажется **хуже** файловой. Файловая
   реализация отвечает на `ReadBuckets` по заголовкам блоков (§8.5).
2. **Запрошенный бакет мельче блока — разрешено и обязано работать.** Блок
   покрывает около 68 минут (§8.6), и на запрос минутных бакетов заголовков не
   хватает: стор разжимает нужные блоки и считает бакеты по точкам. Возвращать
   бакеты крупнее запрошенных **нельзя** — вызывающий рассчитывает разметку по
   `StartMs`/`EndMs`.
3. **Агрегация и ротация — за интерфейсом, а не в конвейере.** Файловый стор
   считает агрегаты сам и удаляет каталоги; TimescaleDB умеет continuous
   aggregates и retention policies декларативно. `Capabilities` объявляет, что
   стор делает сам, конвейер добавляет недостающее. Иначе при переезде окажется,
   что наш агрегатор и агрегатор БД считают одно и то же дважды.
4. **Conformance-тесты.** Набор правил контракта, отделённый от механики и
   прогоняемый против каждой реализации: `ArchiveStoreConformance`, 24 правила
   на `FileArchiveStore` и `InMemoryArchiveStore`. Абстракция с единственной
   реализацией через год оказывается формой этой реализации, и добавление
   третьей превращается в археологию.

### 13.4 Судьба существующего кода

`InMemoryHistorian` (ТЗ §16.4) **перестаёт быть заглушкой и становится штатным
узлом** — кольцевым буфером последнего часа внутри фасада. Работа, сделанная в
M1, не выбрасывается, меняется только роль: realtime-тренды и правила
сигнализации обслуживаются им и диска не касаются.

Метод `Append` из существующего `IHistorian` **удаляется**: кольцо наполняет
конвейер, публичной записи не существует (§3).

`EvaluationContext` ссылается на `IHistorian` как на точку роста для M5 —
попадает на `ReadRecent`, синхронный и без диска. Для сигнализации ничего не
усложняется.

## 14. Чтение

| Запрос | Как выполняется |
|---|---|
| Последний час | Кольцевой буфер в памяти, диск не задействован |
| Диапазон в пределах суток-недель | Читается файл месяца целиком (1–2 МБ), блоки вне диапазона пропускаются по `blockLength`, нужные разжимаются |
| Диапазон в месяцы-год | Читаются **только заголовки блоков**; `summaryA/B/C`, `count`, `goodCount` дают min/max/avg на бакет без разжатия |
| Смешанный | Заголовки для грубой части, разжатие для краевых блоков |

Год по одному потоку — около 7700 блоков, 12 файлов, порядка 550 КБ заголовков.
Тренд на 10 тегов за год — единицы мегабайт чтения.

### 14.1 Границы запроса — защита сервера

По ТЗ §5.1 сервер обслуживает все операторские станции. Клиент через gRPC может
запросить сырой год по сотне тегов, и без ограничений один неудачный тренд на
одном АРМе выведет сервер из строя для всех остальных.

Обязательные пределы, проверяемые **на сервере**, а не в клиенте:

| Предел | Умолчание | Поведение при превышении |
|---|---|---|
| `MaxPointsPerQuery` | 200 000 | Ответ прореживается до `ReadBuckets` автоматически, признак прореживания возвращается клиенту |
| `MaxStreamsPerQuery` | 100 | Отказ с внятным сообщением |
| `QueryTimeoutMs` | 30 000 | Отмена по `CancellationToken`, частичный результат не возвращается |

Автоматическое прореживание вместо отказа выбрано осознанно: оператор,
запросивший год, хочет увидеть год, а не сообщение об ошибке. Тренд получает
бакеты и признак, что показаны агрегаты, а не сырые точки.

## 15. Ротация и глубина хранения

Глубина хранения — **параметр проекта, а не свойство формата**. Формат не
содержит ничего, что ограничивало бы срок: метки времени 64-битные, потоки
нумеруются 32 битами, файлы нарезаны по месяцам. Год, два года, пять лет — одна
и та же конструкция, разница только в занятом месте и в количестве файлов.

Конфигурация: `RetentionDays`, по умолчанию **400** (год плюс запас на разбор
инцидентов конца периода).

Фоновая задача раз в сутки удаляет данные, вышедшие за срок.

### 15.1 Срок разрешается на поток, а не глобально

Срок резолвится **через отдельный узел**, даже пока ответ всегда один и тот же:

```csharp
public interface IRetentionPolicy
{
    int GetRetentionDays(int streamId);
    int MinRetentionDays { get; }
}
```

В M4 работает `FixedRetentionPolicy` — один срок на систему. Смысл узла в том,
что глубина на класс тегов — это **предсказуемое требование следующих
проектов**: «аварийные параметры три года, вспомогательные полгода».

Удаление идёт **пофайлово, а не каталогами месяцев**: обход стоит столько же
(каталог всё равно перебирается), но разные сроки по потокам работают сразу,
без переделки. Каталог месяца удаляется, когда в нём не осталось файлов.

Заводить сущность «группа архивирования» заранее не нужно: узел стоит пять
строк, а группы — это конфигурация, миграция и UI. Добавляются, когда появится
заказчик, которому они нужны.

`MinRetentionDays` — пол досрочного удаления, договорное обязательство перед
заказчиком. Ниже него не удаляется ничего и никогда, включая случай
заполненного диска (§15.3). Конфигурация с полом выше основной глубины
отвергается при создании политики: при нехватке места система не смогла бы
освободить ничего.

### 15.2 Что меняется при большой глубине

Место растёт линейно и предсказуемо: ~24 ГБ на год при 2000 логируемых тегов
(§19), два года — ~48 ГБ, пять лет — ~120 ГБ. Для промышленного ПК это не
проблема, и требование к диску выдвигается заказчику на этапе проектирования —
для этого и нужен калькулятор объёма в сборщике пакета.

Упирается раньше не место, а **чтение широких диапазонов**. Год по одному потоку
— около 7700 заголовков блоков, 554 КБ; тренд на 10 тегов за год читает единицы
мегабайт и укладывается в бюджет 2 с (ТЗ §4.1). За пять лет это уже ~2,8 МБ
заголовков на поток и порядка 600 файлов на запрос — на пределе.

Поэтому: **при глубине более 2–3 лет вводится часовая свёртка** — отдельный файл
на поток на год, считаемый пакетным заданием из сырых данных. Это единственное
место, где уровень агрегации оправдан, и оправдан он скоростью чтения, а не
экономией места. Формат сырых данных при этом не меняется, свёртка добавляется
как отдельный тип файла и отдельная реализация `ReadBuckets`.

Второй эффект большой глубины — **количество файлов**: 2000 потоков × 12 месяцев
× 5 лет = 120 000 файлов. NTFS это выдерживает (по 2000 файлов в каталоге), но
копирование архива на съёмный носитель заметно замедляется. При необходимости
старые месяцы упаковываются в один контейнер на месяц; на глубине до двух лет
вопрос не возникает.

Заморозка данных вокруг аварий не требуется ни при какой глубине: в пределах
срока хранения не удаляется ничего, замораживать нечего.

### 15.3 Нехватка места на диске

Заполнение диска — штатная ситуация, а не отказ: она обязана обрабатываться так
же, как обрыв связи по ТЗ §4.2, то есть **не влияя на опрос и на HMI**.

Ключевой принцип: потерять новые данные хуже, чем потерять старые. Инцидент,
который будут разбирать, — тот, что происходит сейчас; остановка записи при
заполнении диска гарантирует отсутствие записей ровно про него. Но и молча
срезать обещанный заказчику срок нельзя. Отсюда лестница с полом:

| Состояние | Действие |
|---|---|
| Норма | Удаление по возрасту, `RetentionDays` |
| Свободно меньше `MinFreeDiskMb` | **Аларм** оператору, запись продолжается |
| Место кончается, `OnDiskFull = DeleteOldest` | Глубина ужимается вдвое за проход (400 → 200 → 100 → 50 → пол), каждое ужатие в журнал |
| Место кончается, `OnDiskFull = StopWriting` | Запись прекращается, не удаляется ничего |
| Пол `MinRetentionDays` больше не удержать | Запись прекращается независимо от настройки |
| Запись прекращена | Опрос и HMI работают, аларм, счётчик потерянных отсчётов растёт |
| Место освободилось | Ограничения снимаются, глубина возвращается к штатной |

Шаг ужатия крупный (деление пополам) намеренно: мелкие шаги дали бы десятки
проходов ротации подряд на заполненном диске, каждый со сплошным чтением
каталога.

При приостановленной записи `Write` **считает потерянные отсчёты и возвращает
управление**, а не бросает исключение: исключение остановило бы конвейер, а с
ним и сбор данных по всем остальным тегам. Счётчик уходит в
`$Archive.DroppedNoSpace` (§22) и обнуляется при возобновлении — он показывает
потери текущего эпизода, а не за всё время.

`MinRetentionDays` — договорный минимум. Выше пола досрочное удаление допустимо
как самолечение, ниже — запрещено: вместо этого система останавливает запись и
сообщает. Если срок хранения жёсткий, интегратор ставит
`MinRetentionDays = RetentionDays`, и досрочного удаления не будет никогда.

Ни один из режимов не молчит. Тихая потеря данных недопустима — о ней узнают
через полгода, когда данные понадобятся.

### 15.4 Защита ротации от неверных часов

Удаление по календарю при часах, ушедших вперёд, уничтожит свежие данные.
Поэтому решение принимается по **меткам времени внутри самих данных**: файл
удаляется, только если `lastTimestampMs` его последнего блока старше срока.
Имя каталога месяца — подсказка для обхода, а не основание для удаления.

Два следствия, обязательных к соблюдению:

- **Нечитаемый файл не удаляется.** Если заголовок разрушен и возраст
  определить нельзя, файл остаётся: данные из него ещё могут вытащить, а
  удаление необратимо.
- **Переименованный каталог не может унести свежие данные.** Проверяется
  тестом: каталог, переименованный в древний месяц, при живых метках внутри
  сохраняется целиком.

Проход ротации выполняется при старте службы (она могла простоять дольше суток)
и далее раз в сутки. Штатное удаление по возрасту пишется в журнал уровнем
Information, досрочное из-за нехватки места — Warning: это отступление от
обещанной заказчику глубины, и оно должно быть заметно.

## 16. Восстановление после сбоя

### 16.1 Единственный писатель

Каталог архива открывается **исключительно**: при открытии создаётся и
удерживается `archive/.lock`. Второй процесс, нацеленный на тот же каталог,
получает отказ с внятным сообщением и не стартует.

Без этого два экземпляра службы — типичная ошибка развёртывания, когда служба
уже зарегистрирована, а инженер запускает консольный вариант, — дают
перемешанный WAL и порванные блоки. Стоит несколько строк, предотвращает
неремонтируемое повреждение.

Читатели каталог не блокируют: чтение возможно параллельно с записью, включая
чтение стороннего экземпляра для разбора.

### 16.2 Порядок восстановления

При открытии архива:

**Файлы потоков.** Блоки проходятся последовательно, проверяется магия и CRC.
При первом несовпадении файл **обрезается** по началу дефектного блока, факт
пишется в журнал. Последняя корректная `lastTimestampMs` запоминается как точка
восстановления потока.

**WAL.** Сегменты читаются по порядку. Запись с несовпавшим CRC означает
порванный хвост — чтение сегмента прекращается. Записи с
`timestampMs > точка восстановления потока` подаются в конвейер и попадают в
новые блоки.

**Реестр потоков.** Битая строка пропускается с записью в журнал.

Повреждение изолировано конструкцией: теряется не более одного тега за один
месяц плюс не более часа данных из WAL.

Обязательный тест M4: убийство процесса под нагрузкой, проверка что архив
открывается, хвост обрезан, потеря не превышает 10 секунд.

## 17. Версионирование и эволюция

- **Версия формата** — в заголовке файла потока. Читатель отказывается открывать
  файл с версией выше поддерживаемой и сообщает об этом, а не пытается
  интерпретировать неизвестные структуры (правило §14.5 ТЗ).
- **Идентификатор кодека** — в `flags` каждого блока. Смена кодека локальна:
  новые блоки пишутся новым кодеком, старые продолжают читаться прежним.
  Переход с Gorilla на Chimp через год не потребует миграции данных.
- **Режим логирования и масштаб** — в заголовке блока, а не в конфигурации.
  Изменение конфигурации не портит чтение накопленных данных.

Порядок эволюции: поля заголовка блока только добавляются, для чего в `flags`
и в конце заголовка оставлен резерв; существующие поля не меняют смысл и
положение.

## 19. Оценка объёма

Смесь: 2000 логируемых тегов, из них 1500 аналоговых при Periodic 1 Гц и
500 дискретных при OnChange.

```
Аналоговый тег, типичная активность (80 % отсчётов без изменения):
    0,8 × 2 бита  +  0,2 × 13 бит   ≈ 4 бита на отсчёт
    86 400 отсчётов в сутки          ≈ 43 КБ в сутки
    + заголовки блоков (~4 %)        ≈ 45 КБ в сутки
                                     ≈ 16 МБ на тег в год
    1500 тегов                       ≈ 24 ГБ в год

Дискретный тег при OnChange, ~50 переключений в сутки:
                                     ≈ 55 КБ на тег в год
    500 тегов                        ≈ 0,03 ГБ в год

Итого                                ≈ 24 ГБ в год
```

**Разброс оценки — 2–3 раза**, потому что она получена расчётом на бумаге, а не
замером: доля неизменившихся отсчётов зависит от реального техпроцесса. Поэтому:

- требование к диску в §4.3 задано с трёхкратным запасом — **100 ГБ на год**;
- критерий приёмки M4 сформулирован **самосогласованно**: фактический рост за
  суточный прогон симулятора сравнивается не с этим числом, а с предсказанием
  калькулятора объёма по фактической конфигурации, допуск 25 %. Такой критерий
  проверяем при любом исходе и заодно проверяет сам калькулятор;
- калькулятор встраивается в `SCADA.Package.Builder` и предупреждает при сборке
  пакета. Он защищает от единственного реального способа исчерпать диск —
  «залогировать 10 000 тегов на 10 Гц», что даёт порядка терабайта в год.

## 20. Открытый вопрос

**Periodic против OnChange для аналоговых тегов.** Расчёт даёт порог окупаемости
около 85–90 % неизменившихся отсчётов: тег стабильнее — выигрывает OnChange,
активнее — Periodic. Где лежит реальная смесь, без замера неизвестно.

Выбран Periodic, и не по объёму (разница в пределах двух раз в обе стороны), а
по предсказуемости: объём считается из конфигурации точно, тогда как при
OnChange он растёт именно в аварию, когда дрожат все теги, — то есть диск
заполняется в тот день, когда архив нужнее всего.

Вопрос закрывается замером на суточном прогоне M4. **Риск ограничен
конструкцией:** режим логирования — это конвейер, а не формат. Если замер
покажет двукратный выигрыш OnChange, он включается настройкой, файлы не
переписываются, кодеки не меняются.

## 21. Параметры конфигурации

Значения проекта, а не константы кода. Живут в `runtime.json` папки проекта
(ТЗ §14.6).

### 21.1 Размещение и время

| Параметр | Умолчание | Назначение |
|---|---|---|
| `ArchiveRoot` | `<папка проекта>/archive` | Каталог архива. Должен быть на записываемом томе, не под `Program Files` |
| `SiteTimeZone` | пояс ОС при создании проекта, далее фиксирован | Часовой пояс **объекта** в формате IANA (`Asia/Yekaterinburg`). Влияет только на режим Schedule и границы отчётных периодов; хранение всегда в UTC |

`SiteTimeZone` задаётся явно, потому что сервер может стоять не на объекте
(ТЗ §5.1), а промышленные ПК разворачивают клонированием образа, в котором пояс
нередко остаётся чужим. При неявной настройке сменные и суточные итоги молча
уезжают на несколько часов, и расхождение замечают при сверке с бумажным
журналом через месяцы. Расхождение объявленного пояса и пояса ОС выносится в
диагностику.

### 21.2 Глубина и дисковое пространство

| Параметр | Умолчание | Назначение |
|---|---|---|
| `RetentionDays` | 400 | Глубина хранения (§15) |
| `MinRetentionDays` | 30 | Пол досрочного удаления. Ниже него данные не удаляются никогда |
| `OnDiskFull` | `DeleteOldest` | `DeleteOldest` — удалять старое до пола, чтобы продолжать сбор; `StopWriting` — прекратить запись, ничего не удалять |
| `MinFreeDiskMb` | 5 000 | Порог аларма о нехватке места |

`MinFreeDiskMb` задаётся в мегабайтах намеренно: порог должен быть
детерминированным и совпадать с тем, что вписал интегратор. Оценка «на сколько
суток хватит» вычисляется из **фактически измеренной** скорости роста и выдаётся
диагностическим тегом (§22), а не участвует в срабатывании порога — на первом
запуске мерить нечего, и порог, зависящий от истории, невозможно объяснить.

### 21.3 Запись

| Параметр | Умолчание | Назначение |
|---|---|---|
| `FlushIntervalMs` | 10 000 | Периодичность сброса WAL на диск. Потолок задан ТЗ §4.2, уменьшение повышает надёжность ценой нагрузки на диск |
| `MaxOpenBlockMemoryMb` | 64 | Бюджет памяти под открытые блоки; из него выводится вместимость (§8.6.1) |
| `BlockPoints` | 0 (авто) | Вместимость блока в отсчётах. Ноль — вывести из бюджета памяти |
| `BlockTimeoutMinutes` | 60 | Принудительное закрытие блока. Определяет, сколько данных удерживает WAL |
| `WalSegmentSizeMb` | 16 | Размер сегмента журнала |


### 21.4 Чтение

`MaxPointsPerQuery`, `MaxStreamsPerQuery`, `QueryTimeoutMs` — см. §14.1.

## 22. Диагностика архива

ТЗ §7.4 требует диагностических тегов у каналов связи; §5.4.2 требует разбирать
нештатные ситуации на объекте без редактора. Архив обязан публиковать такой же
набор — иначе единственным способом понять, почему нет данных, остаётся чтение
журналов вручную.

Теги генерируются тем же механизмом, что диагностика каналов
(`SCADA.Runtime/Configuration/DiagnosticsGenerator.cs`), и доступны на
мнемосхемах и в трендах наравне с технологическими.

| Тег | Смысл |
|---|---|
| `$Archive.PointsPerSecond` | Записано отсчётов в секунду |
| `$Archive.DroppedNonMonotonic` | Отброшено из-за неверного порядка меток времени (§6.3). Устойчивый рост означает сбитые часы либо ошибку конвейера |
| `$Archive.DroppedNoSpace` | Потеряно отсчётов из-за нехватки места |
| `$Archive.WalLagMs` | Отставание: возраст самой старой записи WAL, не попавшей в блок |
| `$Archive.LastFlushUtc` | Время последнего успешного сброса на диск |
| `$Archive.SizeMb` | Текущий размер архива |
| `$Archive.FreeDiskMb` | Свободно на томе архива |
| `$Archive.DaysRemaining` | На сколько суток хватит места при измеренной скорости роста |
| `$Archive.GrowthMbPerDay` | Измеренная скорость роста |
| `$Archive.OldestDataUtc` | Дата самых старых данных — фактическая глубина архива |
| `$Archive.CrcErrors` | Ошибки контрольных сумм при чтении |
| `$Archive.State` | Норма / мало места / запись остановлена |

`$Archive.OldestDataUtc` и `$Archive.State` — главные для оператора: они отвечают
на вопросы «за какой период у меня вообще есть данные» и «пишется ли архив
прямо сейчас», а сегодня на них нет способа ответить.
