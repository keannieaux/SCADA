## 1. Цель

Подсистема пользователей, ролей и прав: аутентификация, разграничение
доступа к действиям на мнемосхемах и операциям ядра, аудит действий под
реальным логином. Закрывает заглушку `"os-user@station"` в аудите и
`AcknowledgedBy` в журнале аварий.

Работаем на локальном мастер-АРМе (in-process `IRuntimeClient`). gRPC —
после локального запуска, но контракты проектируются под него сразу (§8).

## 2. Модель прав

### 2.1 Право = строка-идентификатор

- **Системные права** — ровно пять, хардкодятся в `SystemPermissions`
  (SCADA.Core), их проверяет код ядра:
  - `View` — просмотр (базовое, есть у всех авторизованных);
  - `Operate` — операторская запись в теги (`WriteTagsAsync`);
  - `AckAlarms` — квитирование аварий;
  - `ManageUsers` — управление пользователями;
  - `UpdateProject` — обновление пакета (под будущий лаунчер, M6.5).

  Решено при проектировании поставки: шестым станет `ManageStation` —
  изменение настроек станции (роль, эндпоинт мастера, AuthMode). Вводится
  вместе с конфигурацией станции, тогда же правится это «ровно пять»
  (`docs/distributed-arm-architecture.md`).
- **Проектные права** — произвольные строки от инженера
  (`Уставки.Edit`, `Насосная.Control`, ...). Система семантики не знает,
  только сверяет наличие в правах пользователя. Вешаются на элементы и
  действия схем (§5).
- Валидатор сравнивает проектные права из ролей с правами, реально
  использованными в `RequiredRight` схем, — несовпадение это warning
  (защита от опечаток), не ошибка.

### 2.2 Роли — данные проекта

- `RoleDefinition` = имя + список прав. Без хардкода: инженер создаёт
  свои роли в проекте.
- Фабричный сид (при создании проекта): Наблюдатель (`View`), Оператор
  (+`Operate`, `AckAlarms`), Инженер, Администратор (всё + `ManageUsers`).
- Хранятся в `roles.json` в исходниках проекта → компилируются в секцию
  `roles.bin` пакета (§4).

### 2.3 Пользователи — данные эксплуатации

- `UserDefinition` = логин + PBKDF2-хеш + соль + число итераций + список
  имён ролей.
- Хранятся в `users.json` в **папке проекта** (рядом с архивом и журналом
  аварий), НЕ в исходниках и НЕ в пакете. Обоснование — §3.

## 3. Почему пользователи не в пакете (и не вшиты в проект, как в TIA)

Пакет — артефакт сборки с циклом жизни «собрал → пролил». Пользователи —
эксплуатационные данные с циклом жизни «завели на объекте → живут, пока
живёт станция». Смешение циклов даёт:

1. Смена пароля / новый оператор / уволившийся сотрудник = пересборка и
   проливка проекта на работающем АРМе. Неприемлемо.
2. Обновление проекта затирало бы учётки, заведённые на объекте,
   состоянием «как у инженера на столе» — конфликт с M6.5.
3. Хеши паролей объекта разъезжались бы по git, бэкапам и почте вместе
   с исходниками.
4. Интегратор обязан был бы знать эксплуатационные пароли — не должен.
5. Два АРМа от одного проекта (стенд/объект) не могли бы иметь разные
   наборы пользователей.

Из TIA-подхода берём удобную часть (роли и права проектируются в проекте
и едут в пакет), болезненную (пароли в артефакте) — убираем.

## 4. Форматы хранения

### 4.1 `roles.bin` (секция пакета)

Шаблон существующих секций (`BinaryWriter`/`BinaryReader`, префиксы длин
записей для пропуска неизвестных полей, как в `AlarmsSectionReader`):

```
Int32  roleCount
per role:
  Int32    recordLength
  String   name
  Int32    permissionCount
  String[] permissions
```

Писатель `RolesSectionWriter` (SCADA.Package.Builder), читатель
`RolesSectionReader` (SCADA.Package). Источник — `roles.json`, читается
`ProjectLoader`, валидируется `ProjectValidator` (новый приватный метод +
строка в `Validate` — класс спроектирован под расширение).

### 4.2 `users.json` (папка проекта)

```json
[
  {
    "login": "ivanov",
    "passwordHash": "base64...",
    "salt": "base64...",
    "iterations": 100000,
    "roles": ["Оператор"]
  }
]
```

- Хеширование: PBKDF2-HMACSHA256 (`Rfc2898DeriveBytes`), соль 16 байт,
  ~100k итераций. Без внешних зависимостей; код в SCADA.Core (им пользуется
  и редактор).
- **Атомарная перезапись**: временный файл → `File.Move` поверх. Защита
  от порчи при сбое питания посреди записи. Обязательно, не опция.
- ACL: data-папка проекта — только для службы/админов станции (требование
  к доке поставки).
- Формат JSON, а не SQLite: пользователей — десятки, записи — редкие;
  JSON прозрачен, бэкапится и переносится вместе с проектом, читается
  человеком на объекте.

### 4.3 Модель угроз

Граница защиты — операционная система станции (кто вошёл в Windows, права
NTFS). Имеющий доступ к файловой системе может подменить сам пакет или
exe — шифрование users.json «от админа машины» смысла не имеет. Подсистема
защищает от оператора за пультом: действие без права не выполняется и
попадает в аудит. Как у WinCC/iFix: локальные пользователи — файлы/
локальная база на станции. Доменная авторизация (AD) — отдельная тема,
если появится запрос; модель прав под неё не меняется, меняется источник
проверки пароля.

### 4.4 Восстановление доступа

- Штатный путь — команды лаунчера (M6.5; отдельной утилиты до него не будет,
  см. этап 8):
  - `scada-user reset <login>` — сброс пароля конкретной учётки, остальные
    не трогаются;
  - `scada-user ensure-admin` — создаёт дефолтного admin, если ни одного
    носителя `ManageUsers` не осталось.
  - Работает только локально с машины. Сетевого сброса нет и не будет.
- Рантайм при старте проверяет «есть ли хоть один носитель `ManageUsers`»;
  если нет — выполняет ensure-admin сам и пишет предупреждение в журнал.
  Закрывает сценарий «удалили последнего админа через UI».
- Удаление users.json — аварийный fallback (ресид при следующем старте).
- Вшитый мастер-пароль / недеletable-учётка — **не делаем никогда**: это
  бэкдор, всплывёт при любом аудите у заказчика.

## 5. Права на мнемосхемах (три уровня)

| Уровень | Свойство | Где проверяется |
|---|---|---|
| Элемент | `RequiredRight` + `DeniedState: Hidden\|Disabled` | клиент (видимость/доступность) |
| Действие | `RequiredRight` + `DeniedFeedback: Silent\|Notify` | клиент (выполнение) |
| Ядро | системные `Operate` / `AckAlarms` / `ManageUsers` | `LocalRuntimeClient` (запись, квитирование, управление пользователями) |

- `DeniedState.Hidden` — элемент не отображается; `Disabled` — отображается
  серым, не работает.
- `DeniedFeedback.Notify` — клик без права → сообщение «Недостаточно прав
  (требуется: Уставки.Edit)».
- Право задано и на элементе, и на действии — проверяются оба.
- Компиляция: строки прав — в пул строк схемы, в скомпилированных формах —
  индексы (как имена тегов и шаблоны сообщений).
- Проверка клиентом — lookup в HashSet прав сессии, права меняются только
  при логине/логауте → пересчёт состояния элементов на смену сессии, не на
  кадр.

**Почему не `hasRight()` в ВМ выражений:** выражения вычисляются в
разделяемом контексте (AlarmEngine, пересчёт привязок, remote-сервер) —
контекст не знает, кто смотрит. Видимость по правам — свойство конкретной
сессии: на двух АРМах одна схема выглядит по-разному при одинаковых
значениях тегов. Персональный `EvaluationContext` ломал бы модель
разделяемого рантайма и в remote-варианте заставлял сервер пересчитывать
схему на каждого клиента. Если появится кейс «право внутри логики
выражения» — вернёмся осознанно; пока закрыто свойствами элемента.

## 6. Сессии и вход

- `IUserStore` (SCADA.Runtime): загрузка/сохранение users.json (атомарно),
  проверка пароля, CRUD пользователей.
- Сессия: `Authenticate(login, password)` → пользователь + эффективные
  права (объединение прав ролей, HashSet, вычисляется один раз при логине)
  + время последней активности.
- Политика паролей первой итерации: минимальная длина в настройках
  (`minPasswordLength`, умолчание 4); блокировки после N неудачных попыток
  нет.

### 6.1 Завершение сессии: поводов будет много, механизм один

Автоблокировка по бездействию (ТЗ §13) — не единственный повод завершить
сессию: на объектах просят и лимит длительности, и выход по расписанию
(пересменка), и «выйти при потере связи с сервером». Поэтому в коде это не
один таймаут, а **правило** — и добавление второго правила не должно
трогать вызывающие стороны. Заложено так:

1. **Одна точка вычисления.** Сервис сессий на тике рантайма спрашивает
   правила: `Evaluate(session, now)` → `SessionEndReason?`. Ни UI, ни ядро
   не знают, какое правило сработало: они получают исход и причину.
2. **Причина — часть контракта с первого дня.** `SessionEndReason`
   (`Manual`, `Idle`, ...) идёт в аудит и в текст на экране блокировки
   («сессия завершена: бездействие»). Новое значение enum не ломает
   старые записи; ретроспективно причину не восстановить, поэтому пишем
   сразу.
3. **Исход правила — `Lock` или `Logout`.** Бездействие блокирует экран,
   сессия сохраняется, разблокировка — паролем того же пользователя.
   Пересменка требует полного выхода: следующая смена входит своим
   логином. Одно правило — один исход, это его свойство, не глобальная
   настройка.
4. **Мнемосхема при блокировке остаётся на экране.** Блокируется
   управление, а не наблюдение: оператор не должен терять картину объекта
   в момент аварии из-за таймера.
5. **Время — через `TimeProvider`**, а не `DateTime.UtcNow`: правило
   «выход в 08:00» иначе не проверить тестом.
6. **Настройки — хвостом секции `roles.bin`** (§4.1): новое правило = новое
   поле в конце, старые пакеты читаются прежним кодом.

Реализуется сейчас одно правило — бездействие (`idleTimeoutMinutes`,
умолчание 10, `0` = выключено, исход `Lock`). Лимит длительности
(`maxSessionMinutes`) и расписание пересменки — по одному полю и одному
правилу каждое, делаются при реальном запросе с объекта, а не впрок.
- **`AuthMode` в `RuntimeHostOptions`:**
  - `Local` (умолчание сейчас) — автологин встроенным «локальным
    администратором» со всеми правами; текущее поведение не ломается,
    разработка экранов не встаёт на пароле;
  - `Full` — окно входа.

## 7. Аудит и аварии

- Заглушка `"os-user@station"` (`SchemeCanvas.cs`, `LocalRuntimeClient`)
  заменяется реальным логином сессии.
- `AcknowledgedBy` в журнале аварий получает смысл.
- Попытка действия без права фиксируется в аудите (отказ тоже событие).
- Отказ записи: новое значение `TagWriteStatus.Denied`.
- **Признак автоматического действия — задел, когда появятся события
  изменения свойства** (`docs/visualization-concept.md` §8.6). Сейчас запись
  в тег всегда инициирует человек кликом, поэтому логина сессии достаточно.
  Как только на изменение свойства можно будет повесить цепочку действий,
  в журнале появятся записи без человека — и «кто нажал» перестанет быть
  ответом. Записи аудита понадобится признак «выполнено автоматически
  по цепочке» плюс, желательно, источник цепочки (экран и элемент).

## 8. Remote-готовность (проектируем, не реализуем)

- Пользователи существуют **только на сервере**. Remote-АРМ базу не
  хранит и пароли не проверяет: окно входа шлёт логин/пароль на сервер
  (`AuthenticateAsync` в контракте `IRuntimeClient` — UI одинаковый в
  обоих режимах), получает токен сессии + набор прав (для серых кнопок).
- Все проверки прав на сервере; АРМ с запросами шлёт токен.
- Управление пользователями — через сервер (`ManageUsers`), users.json не
  реплицируется на АРМы.
- Пароль по сети — только внутри TLS-канала gRPC (требование к M7).
- **Офлайн-вход отложен**: сервер недоступен → войти нельзя. Для
  мастер-АРМ не проблема (он и есть сервер); кэшированная проверка
  последнего пользователя — отдельное решение при реальном запросе.

## 9. Системные теги подсистемы

**Раздел перенесён в `docs/session-tags-concept.md`.** Набор остался тот же —
`@User.Name` (строковый; кейс «Оператор: Иванов» на мнемосхеме, первый реальный
потребитель строковых тегов из A7), `@User.IsAuthenticated` (0/1) и
`@Right.<Имя>` (0/1 на каждое право проекта). Изменился механизм: это не
обычные теги в общей таблице, а **сессионные теги** — иначе на мастере
с несколькими клиентами логин показывал бы того, кто вошёл последним.

Не тегами: список пользователей, роли, пароли — не потоковые данные.

   - Исходники: `requiredRight`/`deniedState`/`deniedFeedback` в
     `schemes/*.scheme`; строковые enum-конвертеры в `ProjectJsonContext`.
   - Пакет: права вошли в раскладку секции схем (право схемы — в заголовке,
     права элемента и действия — в хвостах их блоков). Версия секции
     остаётся 1: до релиза совместимость не поддерживается, пакет,
     собранный старым сборщиком, надо пересобрать.
   - Права — строки, не параметры шаблона: параметрическое право нельзя
     сверить при сборке, и опечатка всплыла бы на объекте.
   - Сборка: права схем сверяются с правами ролей, несовпадение — warning
     (`Source = "rights"`), системные права выданы по определению. Права
     без единой роли в проекте — одно предупреждение.
   - Тесты: `SchemeRightsTests` (8).

**Осталось:**

7. **Системные теги `@User.*`** — **вынесено из этого плана**
   (`docs/session-tags-concept.md`). Замысел «сгенерировать два тега и писать
   в них при логине» неверен для распределённой системы: `TagTable`
   разделяемая, а логин персонален для АРМа — на мастере с тремя
   клиентами тег показывал бы того, кто вошёл последним. Правильная форма —
   сессионные теги как отдельный механизм ядра, где
   `@User.Name`, `@User.IsAuthenticated` и `@Right.<Имя>` лишь одни из
   потребителей наряду с `@Station.*` и локальными переменными экрана.
   Там же снят вопрос `hasRight()`: право становится тегом, функция в ВМ
   не нужна. Подсистему пользователей это не блокирует — вход, права и аудит
   работают без системных тегов.
8. **Утилита `scada-user`** — **перенесена в веху лаунчера (M6.5)**: у него
   та же задача (локальное обслуживание станции), та же граница безопасности
   (файловые права, §4.3) и те же команды, делать дважды незачем.
   Состав, когда дойдём: `reset <login>` (пароль спрашивается интерактивно —
   аргумент командной строки осел бы в истории оболочки и в списке
   процессов), `ensure-admin`, `list` (логины и роли, без хешей). Создание
   пользователей и раздача ролей туда не идут: это работа UI под правом
   `ManageUsers`. Поверх `IUserStore` — без второй реализации формата.
   Два решения, принятых заранее: команда отказывается работать при
   запущенной службе (иначе рантайм, держащий `users.json` в памяти, затрёт
   изменения своей следующей записью), и сброс пароля пишется в аудит под
   учёткой ОС — иначе вход под чужой учёткой не оставлял бы следов.

   **Чем это оплачено до лаунчера:** сценарий «единственный администратор
   забыл пароль» закрыт только аварийным путём из §4.4 — удалить
   `users.json` и получить ресид `admin` при следующем старте, потеряв
   остальные учётки. Сценарий «удалили последнего носителя `ManageUsers`»
   закрыт штатно: рантайм сам создаёт учётку восстановления при старте.
9. **UI (Dev B).** Окно входа (AuthMode.Full), состояния элементов по
   правам (Hidden/Disabled), DeniedFeedback.Notify, экран управления
   пользователями (право ManageUsers), индикатор сессии и блокировка.
   Зависит от этапов 4–6 (готовы); отображение логина на схеме — после
   сессионных тегов, до тех пор берётся из сессии напрямую.

## 11. Отложено сознательно

- Офлайн-вход на remote-АРМ; блокировка после N неудачных входов; сложная
  политика паролей; recovery-ключ; доменная авторизация.
- `hasRight()` в ВМ — закрыто окончательно: право становится сессионным
  тегом `@Right.<Имя>`, функция в ВМ не нужна
  (`docs/session-tags-concept.md` §3.3).
- Лаунчер и удалённая проливка — только после пользователей и gRPC.
- Версия формата пакета и доставка/откат (M6.5) — ближе к релизу.
