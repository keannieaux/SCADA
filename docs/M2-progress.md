# M2 — Драйвер Modbus: текущее состояние (2026-08-13)

Продолжение `M1-report.md`. Веха M2 закрыта, кроме RTU (отложено осознанно —
см. дизайн `IChannel` ниже) и приёмки на реальном железе LicOS.

## Сделано

**Проекты:** `SCADA.Drivers.Modbus` (+ FluentModbus 5.3.2), `SCADA.Drivers.Modbus.Tests`,
`SCADA.ModbusProbe` (консольный пробник, проверен против живого устройства).

**Драйвер TCP:** `ModbusAddress` (грамматика `таблица:смещение[:тип]`, таблицы
coil/di/ir/hr, типы u16/i16/u32/i32/f32), `RequestGrouper` (слияние внутри таблицы,
лимиты 125 рег / 2000 бит, `maxGap`), `ModbusTcpDriver`, `RegisterDecoder`
(big-endian; шов под word swap — ждёт реальное железо). `ModbusSettings`:
`"host:port;unit=..;timeout=..;maxregs=..;maxgap=.."` с валидацией диапазонов
и понятными ошибками. `unit` = slave id, по умолчанию 0 (прямой TCP).
Отложено: классическая нотация 4x/3x, порядок байт.

**Исправленные за сессию баги:**
- `maxregs` парсился, но игнорировался — теперь реально передаётся в группировщик.
- При обрыве тег получал `Bad(0, now)` и затирал последнее значение — теперь
  значение сохраняется, обновляются только качество и метка (ТЗ §4.2).
- `ConnectAsync` был синхронным и падение коннекта убивало весь канал — теперь
  коннект асинхронный (DNS async, sync `Connect` FluentModbus в `Task.Run`),
  а сбой одного устройства изолирован от остальных.

**Переподключение — ответственность движка** (решение зафиксировано: единая
политика §4.2, иначе каждый драйвер реализовал бы свою). Драйвер одноразовый:
после ошибки выбрасывается, retry создаёт новый экземпляр через фабрику.
Backoff 1с → 2 → 4 → 8 → 16 → 30с (потолок), успех сбрасывает счётчик.
Работает и для стартового коннекта: недоступное при запуске устройство
подключится само.

**DriverFactory — реестр** (`Register(protocolName, factory)`), не switch.
Встроенные: `simulator`, `internal`. `modbus-tcp` регистрируется из
composition root (ТЗ §7.2: Runtime не ссылается на Modbus).

**Диагностика канала (§7.4):**
- `TagOrigin { Process, Diagnostics }` в `TagDefinition`; `formatVersion`
  остался 1 (до релиза совместимость не поддерживаем).
- `DiagnosticsGenerator` (вызывается из `ProjectLoader.Load` после валидации):
  на канал — псевдоустройство `@<канал>` (DriverName `internal`) + 7 тегов:
  `Connected`, `LastOkTime`, `RequestsOk`, `RequestsFailed`, `ReconnectCount`,
  `ResponseTimeAvg/Max`. Id — плотное продолжение ряда, порядок детерминирован
  (PackageBuilder идёт через тот же Load → индексы пакета и рантайма совпадают).
- Префикс `@` зарезервирован: валидатор запрещает его и `Origin != Process`
  в исходных файлах; `ProjectWriter` сгенерированное не сохраняет.
- `tags.bin`: `Origin` дописан в хвост записи, читатель читает по наличию.
- Движок пишет метрики через `ChannelDiagnostics` раз в секунду (не чаще —
  чтобы не раздувать эпохи). Внутренние устройства в статистику не идут.
- Группировка в UI — по устройству (`@<канал>` — отдельная ветка дерева),
  фильтрация — по `Origin`. Имена с точками моделью не интерпретируются.
- `PollingEngine.OnDeviceError` — hook причин ошибок (таймаут / отказ /
  Modbus-исключение), пробник печатает их в консоль.

**SCADA.ModbusProbe:** конфиг в коде, регистрация драйвера, движок, печать
изменений через `GetChangedSince` (имя, адрес, значение, качество). Проверен
против живого устройства на `127.0.0.1:502` (unit=1): значения читаются,
обрыв → Bad, восстановление → Good.

**Решения по модели (обсуждено, зафиксировано):**
- Повторяющееся оборудование (насосы и т.п.) — будущие **шаблоны типов** в
  исходном проекте: тип + экземпляры с `addressBase`, развёртка в плоские
  теги при сборке (инженерная поставка, M6). Runtime-контракт (плоские
  уникальные имена, TagId = индекс) не меняется. `DiagnosticsGenerator` —
  первый прецедент такого «развёртывателя».

**Тесты:** Modbus 35, Runtime 42, Expressions 12, Compiler 40, Package 11 —
всего 140 зелёных. Приёмочный бенчмарк без регрессий: PollCycle 20k — 0.43 мс,
EpochScan — 9.3 мкс, ReadFrame500 — 0.30 мкс, 0 аллокаций.

**Хозяйственное:** `BenchmarkDotNet.Artifacts/` в `.gitignore` и убран из
индекса. В `SCADA.Benchmarks.csproj` возвращён `<OutputType>Exe</OutputType>`
(потерялся при выносе общих свойств в `Directory.Build.props`).

## Дизайн IChannel (для RTU, НЕ реализовано — зафиксировано, чтобы не перепроектировать)

**Проблема.** Модель «драйвер владеет соединением» работает для TCP (сокет на
устройство), но ломается на шине: на одном COM-порте (или за одним шлюзом
Ethernet↔RS-485) висит несколько ПЛК. Порт/сокет к шлюзу — разделяемый ресурс,
кадры на полудуплексной шине обязаны идти строго по очереди между устройствами.

**Решение.** `IChannel` — владелец транспорта и сериализатор кадров:
- канал открывает порт/сокет один раз и владеет им; reconnect транспорта —
  уровень канала, не устройства;
- драйвер устройства не «подключается», а передаёт кадры через канал;
- параметры шины (бодрейт, паритет) — в `ChannelDefinition.Configuration`
  (поле есть, сейчас пустует), не в устройстве.

**Требование: проектировать сразу под два транспорта** — COM-порт (чистый RTU)
и TCP-сокет к шлюзу (RTU over TCP). Топология и семантика unit-id у них
одинаковые, различается только физика; RTU over TCP на объектах встречается
чаще (MOXA и т.п.). У FluentModbus есть `ModbusRtuClient` (COM) и
`ModbusTcpClient` (MBAP) — RTU-кадры через произвольный TCP-поток из коробки
не идут, нужна своя обвязка кадрирования (CRC); `RequestGrouper` и
`RegisterDecoder` переиспользуются целиком.

**Что уже готово под это:** движок опрашивает устройства внутри канала
строго последовательно (§7.3) — модель «один канал = один Task» заложена на
M1 именно с прицелом на шину; диагностика §7.4 — канальная по построению.
Меняется только то, кем открывается транспорт.
