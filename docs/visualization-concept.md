# Концепт движка визуализации — целевая архитектура

**Дата:** 2026-08-18
**Статус:** согласованная рамка для M3 (графика, Dev B) и секций пакета (Dev A)
**Связанные документы:** `TZ.md` §9, §11, §14; `M5-plan.md` (аварии); `archive-format.md`; `M3-schemes-package-questions.md`

Документ фиксирует целевую архитектуру визуализации: модель элементов, привязки,
экраны, шаблоны, контролы и формат пакета. Упор — не на перечень функций, а на
**точки расширения**: забытое свойство или новый вид объекта обязаны быть
дешёвым добавлением, а не переписью ядра.

---

## 1. Принципы

1. **Свобода уровня TIA Portal и выше**: любое поведение любого элемента
   настраивается выражениями и привязками, без изменения кода движка.
2. **Анимируемо всё, кроме явно запрещённого.** Неанимируемы только
   идентичность и структура (имя, Id, вид элемента).
3. **Система не платит за экзотику, пока её нет.** Ядро маленькое и стабильное;
   новые возможности — добавление в фиксированных точках расширения.
4. **Ошибки конфигурации — ошибки сборки**, а не молчаливый серый
   прямоугольник на объекте. Валидация через `ProjectBuildService`.
5. **Всё, от чего зависит отображение, едет в пакет**: схемы, символы,
   картинки, шрифты, звуки.
6. **UI не знает внутренностей движка.** Вся работа через `IRuntimeClient`;
   local и remote (gRPC в будущем) неотличимы для визуализации.

## 3. Модель данных

### 3.1 Элемент

```
Элемент = вид (число) + имя + геометрия (X, Y, Width, Height)
        + опциональный ParentId            // иерархия, UC12/группы
        + разреженные значения свойств     // хранятся только ≠ умолчания
        + привязки:  выражение → свойство + таблица стопов + флаги
        + события:   событие → цепочка действий
```

### 3.2 Схема свойств вида

Каждый вид элемента регистрирует схему — список дескрипторов:

```
Свойство = id + имя + тип (double | color | bool | string | enum)
         + значение по умолчанию + флаг «анимируемо» + категория (для панели свойств)
```

- Разные виды имеют разные свойства: у прямоугольника нет `SymbolPath`, у шкалы
  заполнения нет `Rotation`, у тренда — перья и оси.
- Экземпляр хранит только значения, отличные от умолчания (разреженность).
- Панель свойств будущего редактора генерируется из схемы — редактор не
  хардкодит поля под каждый вид.
- Привязка к несуществующему/неанимируемому свойству — ошибка сборки
  (диагностика `scheme:<схема>:<элемент>`).
- Реестр дескрипторов — код (Core/Graphics), единственный источник истины.

В рантайме у исполняемого элемента — **плоский типизированный массив значений,
индексируемый id свойства**. Словарь — только в холодном пути (загрузка,
редактор); горячий путь — массив.

### 3.3 Иерархия и координаты

- `ParentId` опционален; сейчас все элементы плоские, но вложенность допустима
  форматом (группы, экземпляры шаблонов).
- Контракт координат: всегда мировые единицы схемы; трансформации
  (перенос/поворот/масштаб) накапливаются от корня к листу.
- Hit-test — по реальной геометрии (`SKPath.Contains`), не по
  ограничивающему прямоугольнику: повёрнутые и круглые элементы кликаются
  правильно с первой версии.

## 4. Привязки (динамизация)

### 4.1 Определение

```
Привязка = выражение (индекс в пуле code.bin)
         + целевое свойство (id)
         + таблица стопов: [(вход, выход), ...]
         + флаги: volatile, ...
```

Режимы отображения — одни и те же данные, три интерпретации:

- **прямая**: значение → свойство (PositionX, Rotation, FillLevel, текст);
- **дискретная**: стопы без интерполяции (пороги цвета, видимость);
- **интерполированная**: линейная между стопами (цвет через `SKColor.Lerp`,
  числа — обычный lerp; UC2).

Существующие «каналы» M3 — частные случаи: `Visible` = прямая bool-привязка,
warn/crit = дискретная таблица из двух стопов и т.д. Миграция механическая.

### 4.2 Одно выражение → группа свойств (UC4)

Несколько привязок ссылаются на одно выражение. Пул `code.bin` дедуплицирует
одинаковые выражения при сборке (как для аварий, M5) — вычисление одно.
Редактор может предлагать сахар «анимация на группу свойств», внутри это те
же привязки.

### 4.3 Volatile-привязки (UC5) — критично для ядра

Пересчёт по эпохам видит только изменения тегов. Анимации, зависящие от
**времени** (вращение, бегущая строка, tween), флагом `volatile` помечаются
«пересчитывать каждый тик». Текущее время передаётся в `EvaluationContext`.
Без этого флага непрерывная анимация потребовала бы взлома движка пересчёта —
поэтому закладывается в формат с первой версии, даже если реализация позже.

### 4.4 Ссылки на теги

```
Ссылка = абсолютная (TagId, раннее связывание §11.6)
       | параметрическая (имя параметра шаблона)   // резерв под шаблоны, §7
```

Байт вида ссылки резервируется в формате сразу: параметризация без него —
параллельная система привязок задним числом.

### 4.5 Качество сигнала — автоматически (UC-сквозное)

Если хотя бы один входной тег привязки недостоверен (`Quality != Good`),
элемент получает флаг качества автоматически — без ручного `QualityTagName`.
Отображение (серый/зачёркнутый/значок) — настройка темы. Ручное поле остаётся
для особых случаев.

### 4.6 Строковые теги

Строки нужны на проектах (ASCII из регистров ПЛК, текстовые статусы,
сообщения), поэтому решаются типом данных тега, **а не расширением ВМ**
(реализовано, A7):

- `TagDataType.String` — дискриминатор уже ездит в `tags.bin`, формат не
  менялся. Отдельного `ValueType` нет.
- `TagTable` — текст лежит в том же слоте тега (`StringTagValue`), эпохи
  изменений общие с числовыми: схема, читающая строковый тег,
  пересчитывается общим грязным механизмом. Нетронутый тег читается как
  `("", Uncertain)`. `TagValue` и ВМ остаются числовыми — ядро выражений
  не трогается.
- `IRuntimeClient` — добавочные `ReadString(TagId)` / `ReadStrings(...)` /
  `WriteLocalString(TagId, string)`; аддитивно, контракт не ломается,
  gRPC-вариант позже повторит.
- Привязки: текстовые свойства принимают прямую ссылку на строковый тег
  (текст привязки в точности равен имени тега — оформляется без ВМ:
  `CompiledExpressionIndex = null`, `CompiledTagIndices = [tagId]`).
  Прямая ссылка на строковый тег на нестроковое свойство и строковый тег
  внутри выражения — **ошибки сборки** (StringTagGuard в
  ProjectBuildService): иначе ВМ молча прочитала бы числовой слот.
  Кодированные статусы — по-прежнему таблица стопов «код → текст».
- v1 — только внутренние теги (валидатор проекта): строкового драйвера ещё
  нет. Первый строковый драйвер (OPC UA, Modbus-ASCII) снимет ограничение
  проверкой возможности драйвера, остальное ядро менять не будет.
  Декодирование ASCII из регистров — точка расширения кодировщика
  (как порядок байт, RegisterDecoder).
- Не в v1 (бэклог): архив строк (история изменений строк — журнал событий),
  операторская запись строк (строковый `TagWriteItem`), персистентные
  строки, строковые операции в ВМ (минимум — сравнение на равенство) —
  по факту потребности.

## 5. События и действия

### 5.1 События

У элемента словарь `событие → цепочка действий`:

`Click | MouseDown | MouseUp | DoubleClick | PointerEnter | PointerLeave`

У схемы/шаблона — события жизненного цикла экрана (та же цепочка действий,
тот же формат): `Opened | Closed` — попап при входе, запись «оператор на
экране», старт/стоп звука. Указательные события на уровне схемы и Opened/Closed
на элементе — ошибка исходника при загрузке.

v1 реализует `Click`; формат хранит все — это один байт-тип перед списком.

### 5.2 Действие

```
Действие = тип + поля + опциональное условие-выражение + модификатор Confirm
```

- **Цепочка** исполняется последовательно (async), условие «выполнять, если…»
  на каждом действии — покрывает большинство сценариев, ради которых в TIA
  лезут в скрипты. Полноценный скриптинг (второй язык) сознательно не
  вводится: выражения + условные цепочки. Если когда-нибудь упрёмся — новый
  тип действия, формат не ломается.
- **Параметры действий — выражения, а не константы.** Это главный рычаг
  против размножения типов: `IncreaseTag`, `DecreaseTag`, `CopyTag`,
  `SetTagFromTag`, `ScaleTag` — это один `WriteTag` со значением
  `Тег + 1`, `ДругойТег`, `Уставка * 0.9`. Комбинаторику дают выражения,
  а не каталог.
- **Границы, которых не будет:** циклов и пользовательских переменных.
  Цикл в потоке интерфейса — это зависший АРМ; роль переменных выполняют
  сессионные теги (`docs/session-tags-concept.md`). Когда упрёмся
  по-настоящему — точка расширения `CallIntegration`, исполняемая сервером,
  а не скрипт в интерфейсе.
- **`Confirm` — не действие, а модификатор**: «перед выполнением спросить».
  Стыкуется с `TagDefinition.RequiresWriteConfirmation` (M7): тег может
  требовать подтверждение сам, элемент — дополнительно.
- **Контекст пользователя** (`requestedBy`, роль) протаскивается в исполнитель
  действий с первой версии: запись уходит в аудит (ТЗ §13), действия с правами
  (UC26) появятся без переписи. До M7-user-management — заглушка
  `operator@station` (как в M5 §2.9).

### 5.3 Каталог действий

| Действие | Поля | Версия |
|---|---|---|
| `WriteTag` | тег (ссылка), значение (константа **или выражение**) | v1, идёт через `WriteTagsAsync` (batch, аудит) |
| `ToggleTag` | тег | v1 |
| `OpenScheme` | имя схемы, опционально параметры | v1 |
| `OpenPopup` | шаблон/схема + параметры, позиция | v1 |
| `ClosePopup` | — | v1 |
| `Back` | — | v1 |
| `ShowDialog` | сообщение | v1 |
| `ApplyRecipe` | имя рецепта | v2 (веха рецептов) |
| `ExportCsv` | источник (тренд/журнал) | v2 (веха отчётов) |
| `CallIntegration` | имя интеграции + параметры | v2 (веха интеграций; исполняет сервер) |
| `SetProperty` | элемент (по имени) + свойство + значение | v2, §8.4 — для состояний без памяти и без индикации |
| `Logout` / `Lock` | — | v1-user, кнопка выхода и блокировки на схеме |
| `AckAlarms` | фильтр или имя правила | v2, квитирование с кнопки схемы |

Неизвестный тип действия при чтении пропускается (с предупреждением в
редакторе) — старый рантайм не падает на новых пакетах.

**Каталог действий должен стать машиночитаемым.** Сегодня список действий
размазан по четырём местам: иерархия типов в `SCADA.Core/Schemes`,
дискриминаторы `[JsonDerivedType]` в исходном формате, байтовый тип в секции
пакета (с литералом границы в читателе) и эта таблица. Свойства элементов
описаны дескрипторами (`ElementSchemas`), и панель свойств редактора
генерируется из них, а панель действий пришлось бы хардкодить.

Нужен такой же каталог: тип, отображаемое имя, параметры с типами и признаком
«может быть выражением», применимость к событиям, версия. Из него берут
данные сериализация, валидация и редактор, а литерал границы в читателе
заменяется проверкой по каталогу — иначе новое действие однажды молча
пропадёт при чтении. Делается вместе с дескрипторами событий контролов
(§8.4): это одна и та же работа.

## 6. Экраны, навигация, попапы

- В окне АРМ одновременно одна «полная» схема; `OpenScheme` заменяет
  содержимое; стек истории для `Back`.
- **Попап — внутренняя модальная панель поверх схемы, не окно ОС.** Оконный
  менеджер на панельных ПК — источник сюрпризов (окно за экраном, потеря
  фокуса). Контракт фиксируется сейчас: пересадка с окон ОС на внутренние
  панели задним числом — перепись навигации.
- Слои отрисовки снизу вверх: векторный слой схемы → слоты hosted-контролов →
  попап-оверлей → глобальный баннер аварий. Z-порядок между векторными
  элементами и контролами не чередуется (как в TIA) — это сознательное
  ограничение контракта слоёв.

## 7. Шаблоны и экземпляры (UC9, UC11–UC13)

**Шаблон = параметризованный фрагмент схемы.** Объявляет параметры (минимум —
строковый префикс тегов); привязки внутри используют параметрические ссылки
`{$Prefix}.Скорость` (§4.4).

Два применения одного механизма:

- **Элемент `Instance`** на схеме: `{ шаблон, параметры, позиция }`. Правка
  шаблона обновляет все экземпляры. Генератор расстановки (список префиксов +
  сетка) — функция редактора, не рантайма.
- **Попап по действию** `OpenPopup(шаблон, {Prefix: "Н7"})` — панель агрегата.

Раскрытие при загрузке: подстановка параметров → резолв имён в `TagId` (раннее
связывание сохраняется). Байткод выражений общий у всех экземпляров; различаются
только `TagIndices` экземпляра. Скомпилированный шаблон кэшируется — 100
насосов не компилируются 100 раз.

Правила сборки:

- экземпляр с параметрической ссылкой на несуществующий тег (`Н7.Скорость`
  отсутствует в проекте) — **ошибка сборки**, не серый попап на объекте;
- рекурсия шаблонов (шаблон включает себя) — ошибка сборки.

## 8. Hosted-контролы (TrendView, AlarmView, экзотика)

### 8.1 Контракт слота

- Вид элемента `Control`, свойство `ControlType` (`trend`, `alarmview`, …).
- В границах слота живёт настоящий контрол Avalonia со своим вводом:
  **указатель над слотом → ввод получает контрол**, схема не панорамируется.
- Жизненный цикл: создаётся при открытии экрана (подписки), уничтожается при
  уходе (отписки). Данные не хранятся в контроле — источник истины рантайм.
- Конфигурация — свойства элемента (перья, фильтры, оси); ссылки могут быть
  параметрическими → контролы работают в шаблонах (UC14/15).
- Состояние вида (диапазон тренда, страница журнала) по умолчанию локально;
  опционально публикуется/читается через сессионные теги — синхронизация
  видов между экранами и управление ими со схемы (UC17, §8.5,
  `docs/session-tags-concept.md`).

### 8.2 TrendView

- Данные: хвост реального времени — `ReadRecent` (кольцо в памяти, §16.4);
  история — `ReadBucketsAsync` (бакетов столько, сколько пикселей); якорь
  левого края — `ReadAtAsync`. Лимиты — `HistoryQueryLimits` на сервере.
- Поведение: зум времени колесом, драг-пан по истории, режим слежения
  (выключается ручным паном), курсор со значениями перьев, вкл/выкл перьев
  в легенде, экспорт CSV по текущему диапазону.

### 8.3 AlarmView

- Данные: `GetActiveAlarmsAsync` + push `SubscribeAlarmsAsync` (без polling),
  история — `GetAlarmHistoryAsync` постранично.
- Поведение: фильтры/сортировка в шапке, квитирование выбранных
  (`AcknowledgeAlarmsAsync` с `requestedBy`), двойной клик по строке → действие
  (переход на схему секции / попап агрегата — общий механизм действий).
- Звук новых аварий — из той же push-подписки (звуки упакованы, M5).

### 8.4 Контрол как участник схемы

Контракт слота (§8.1) описывает контрол как получателя: схема даёт ему место
и конфигурацию. Этого мало. Готовый контрол должен уметь и **сообщать
о происходящем внутри**, и **отдавать своё состояние наружу** — иначе тренд
и журнал остаются вещами в себе: показывают, но в логике экрана не участвуют.
Три механизма, все три опираются на дескриптор типа контрола.

**События контрола.** События сегодня — фиксированный список: указательные
(`Click`, `MouseDown`, …) и жизненный цикл экрана (`Opened`, `Closed`, §5.1).
У типа контрола должен быть **свой список событий**, объявленный дескриптором,
как уже объявлены свойства (§3.2): нажали кнопку в тулбаре, выбрали строку,
сменили диапазон. Расширять общий enum под каждый контрол нельзя — он
превратится в свалку из `TrendViewModeChanged` и `AlarmRowSelected`.

Попутно: запись события — единственная в секции схем **без префикса длины**
(у элемента, привязки и действия он есть, §11.2). Раз раскладка всё равно
меняется, префикс стоит добавить, чтобы следующее расширение не ломало формат.

**Событие «свойство изменилось».** Привязка сегодня однонаправленная:
тег → свойство. Контролу нужен обратный путь — выбранная строка журнала,
выбранный диапазон тренда.

Отдельного понятия «свойство-выход с адресом публикации» **не вводим**.
Вместо него — обычное событие изменения свойства, на которое вешается та же
цепочка действий, что и на клик. «Выбрали строку в журнале» перестаёт быть
особым механизмом: контрол поменял своё свойство, сработало событие, а что
делать дальше — решает инженер: записать в тег, открыть попап, выполнить
по условию. Это подход TIA, и он ложится на нашу модель без новых сущностей
в формате.

**Событие даёт свободу, тег даёт память.** Событие — мгновение, а не значение:
кнопка «квитировать выбранную» должна знать, что выбрано *сейчас*. Читать
чужое свойство напрямую можно, но это связность между элементами — кнопка
начинает знать про внутренности журнала. Поэтому состояние, которое кто-то
индицирует, синхронизирует между экранами или которое должно пережить переход
на другой экран, кладётся действием в **сессионный тег**
(`docs/session-tags-concept.md`), и все привязываются к нему. Если состояние
никому не показывается и нигде не хранится — хватает одного события.

**Действие «задать свойство элемента».** Адресует другой элемент экрана по
имени и задаёт ему свойство напрямую, без тегов. Не альтернатива тегам,
а второй инструмент — для того, что не стоит заведения тега: сиюминутные
команды без состояния (сбросить масштаб, снять выделение), массовые мелочи
(свернуть панель на сорока экранах), работа внутри экземпляра шаблона, где
адресация разрешается в границах экземпляра.

Разделение: **состояние, которое кто-то показывает или которое должно
сохраняться, — тег; сиюминутная мелочь внутри экрана — внутреннее состояние
контрола или прямое задание свойства.**

### 8.5 Правила управления состоянием контрола

Без этих правил конструкция разъезжается, а поломки выглядят как «кнопка
работает через раз».

1. **Пишут только действия, привязки только читают.** Двусторонняя привязка
   (контрол сам пишет в привязанный тег) запрещена: это петля.
2. **Свойство либо привязано, либо управляется локально**, не одновременно.
   Иначе ближайший пересчёт привязки затрёт то, что сделал оператор.
   Нарушение — ошибка сборки.
3. **Внутренние кнопки контрола маршрутизируются через тот же источник, что
   и внешние.** Если свойство привязано, кнопка тулбара не меняет состояние
   сама, а порождает событие; действие пишет в тег — как и большая кнопка на
   схеме.
4. **Три ситуации определены явно:**
   - свойство не привязано, действия нет → контрол переключает себя сам,
     тулбар работает из коробки;
   - свойство привязано, действие есть → состояние меняется только через тег;
   - свойство привязано, действия нет → кнопка неактивна. Хуже всего вариант
     «переключилось и тут же отскочило назад».

Пример целиком (UC17): свойство `ViewMode` окна трендов привязано к сессионному
тегу; большие кнопки «Тренд» и «Таблица» на схеме пишут в этот тег и к нему же
привязывают свою подсветку; кнопка в тулбаре контрола порождает событие с тем
же действием. Индикация активного режима получается сама — источник правды
один. Доработка под требование заказчика («оператор не видит мелких кнопок»)
сделана проектом, без правки кода контрола.

### 8.6 Ограничения события изменения свойства

Механизм из §8.4 мощный и ровно поэтому опасный: в TIA каскады «изменение →
действие → изменение» — известный источник тяжело отлаживаемых проблем.
Четыре ограничения обязательны, иначе мы получим тот же класс дефектов.

1. **Событие только на свойствах, которыми не управляет привязка.** Иначе тег,
   меняющийся десять раз в секунду, породит десять срабатываний, а
   анимированное свойство — тридцать в секунду: инженер вешает «при изменении
   записать в тег» и получает шторм записей в контроллер, каждая с аудитом.
   Это то же правило 2, что и выше, но здесь оно защищает не от гонки,
   а от нагрузки.
2. **Гашение по равенству:** новое значение равно текущему — события нет.
   Дешёвый барьер против самых частых петель.
3. **Предел глубины каскада.** Событие, порождённое действием, обрабатывается
   до фиксированной глубины (порядка восьми), дальше цепочка обрывается
   с записью в журнал. Петли бывают не прямые, а через два-три элемента,
   и статически такое не поймать; без предела первая же петля вешает
   интерфейс наглухо.
4. **Аудит отличает человека от схемы.** Запись в сессионный тег локальна
   и следов не требует, а запись в тег устройства идёт с правом `Operate`
   и попадает в журнал действий. Если её инициировало автоматическое событие,
   в аудите появится действие без человека — на разборе инцидента никто
   не поймёт, кто нажал. Нужен признак «выполнено автоматически по цепочке»
   в записи аудита (`docs/users-plan.md` §7).

И инструментальное требование: **режим трассировки цепочек**. Каскад
невозможно разобрать по симптомам на объекте, а без инструмента первая же
проблема превращается в гадание.

### 8.7 Экзотика и карта (UC18, UC28)

Hosted-контрол — универсальный люк расширения: любой будущий объект, не
ложащийся в векторный слой (карта, видео, web-виджет, приборная панель),
добавляется как новый `ControlType` со своим контролом — ядро, формат и
существующие схемы не трогаются. Это и есть ответ на «вдруг понадобится»:
не планируем экзотику, но платформа под неё заложена.

Карта как частный пример, если запрос появится:

- Уже сейчас: Image-элемент (карта-картинка) + маркеры-символы с PositionX/Y
  по выражениям + готовый пан/зум схемы — живые маркеры без новых механизмов.
- Если понадобится настоящая: hosted-контрол `map` (WebView/офлайн-тайлы).
  Вес браузерного движка (~100+ МБ на экземпляр) означает правило:
  тяжёлые контролы — редко и по согласованию.

## 9. Соседние вехи (не визуализация) и их крючки

| Веха | Что это | Крючок в визуализации |
|---|---|---|
| Отчёты | генерация по шаблонам (сменные/суточные), PDF/Excel; опирается на `ReadHistoryAsync` | действие `ExportCsv` v1, дальше кнопка «сформировать отчёт» |
| Рецепты | именованные наборы «тег → значение»; применение = batch-запись (M7 уже batch-native, двухфазная валидация) | действие `ApplyRecipe`; табличный контрол — hosted |
| ScheduledTask | планировщик в Runtime (записи, вычисления, запуск отчётов); задел — `LogSchedule` в Core | статус задач — системными тегами |
| Интеграции (API/БД) | серверный модуль-шлюз; **исполняет сервер, не АРМ** (credentials и сетевой доступ не живут на клиентах) | действие `CallIntegration` |

расширения (тип действия, hosted-контрол, системные теги).

## 10. Аварии как системные теги (UC7–UC9)

Движок сигнализации публикует состояние в TagTable при каждом переходе:

```
@Alarm.<ИмяПравила>.Active     0/1
@Alarm.<ИмяПравила>.Unacked    0/1
@Alarm.<ИмяПравила>.Severity   0..3 (low..critical)

@AlarmGroup.<Путь>.AnyActive    0/1   // путь — префикс dotted-имени правила
@AlarmGroup.<Путь>.AnyUnacked   0/1   // («Цех.Секция.Насос7.Перегрев» → группы
@AlarmGroup.<Путь>.MaxSeverity  0..3  //  «Цех», «Цех.Секция», «Цех.Секция.Насос7»)
@AlarmGroup.<Путь>.Count        N активных

@AlarmSystem.AnyActive / AnyUnacked / MaxSeverity / Count   // корень дерева
@AlarmSystem.JournalSizeMb                                  // здоровье подсистемы
```

Отдельного поля `Group` у правила нет: иерархия строится из dotted-имён,
как у тегов — один механизм на весь проект. Перекрёстные группировки
(«все аварии по насосам независимо от цеха») делаются выражениями над
тегами правил.

Почему теги, а не функции ВМ (`AlarmActive("…")`): пересчёт схем построен на
эпохах TagTable — функция, ходящая мимо таблицы, не даст грязного пересчёта и
сломала бы модель. Теги встраиваются в существующий механизм бесплатно.
Прецедент: диагностические теги подключений и архива работают так же.

Свойства этих тегов: системные — не архивируются по умолчанию, не аудируются,
**недоступны для записи** (`NotWritable`, M7) — иначе запись со схемы
«погасила» бы аварию.

Порядок сборки пакета: правила аварий обрабатываются **до** компиляции схем —
служебные теги должны быть в каталоге, когда схема компилирует
`@Alarm.Насос7.Перегрев.Active > 0`.

## 11. Формат пакета

### 11.1 Состав

```
tags.bin  devices.bin  code.bin  alarms.bin        — уже есть
schemes/<имя>.bin      — схемы (несколько; перечисление через манифест)
templates/<имя>.bin    — шаблоны (тот же формат, что schemes + параметры)
symbols/*.svg  images/*  fonts/*  sounds/*         — ассеты плоскими секциями
```

### 11.2 Правила эволюции (главное в формате)

- Байт версии секции.
- Запись элемента: `вид (число) + длина блока + содержимое`. Неизвестный вид →
  блок пропускается по длине; в редакторе — placeholder «неподдерживаемый
  элемент». Старый софт читает новые пакеты.
- Свойства разреженные `(id, тип, значение)` — неизвестный id пропускается.
  Забытое свойство = новый id, а не новая версия формата.
- Привязки, действия, события — списки с длинами и байтами-типами; неизвестное
  пропускается.
- Принцип «неизвестный хвост пропускается» — общий для проекта, здесь он
  применён на уровне каждой записи.

### 11.3 Цвет в формате

`тег (прямой | ключ темы) + значение` — ссылка на тему резервируется сразу
(UC22): перекраска проекта под заказчика не должна быть обходом всех схем.

### 11.4 Порядок сборки и валидация (ProjectBuildService)

1. Теги, устройства (как сейчас).
2. Правила аварий → пул `code.bin` + генерация системных тегов `@Alarm.*` в
   каталог.
3. Шаблоны → затем схемы: компиляция всех выражений привязок/условий в общий
   пул, резолв абсолютных ссылок в `TagId`, проверка параметрических по
   экземплярам, проверка рекурсии шаблонов.
4. Ассеты: ссылки на символы/картинки/шрифты/звуки существуют → иначе ошибка;
   неупакованный системный шрифт → предупреждение.
5. Ошибки — диагностики `BuildResult` (Source `scheme:<имя>[:<элемент>]`),
   пакет не пишется.

## 12. Производительность в рантайме

Что уже правильно (не трогаем): пересчёт по эпохам (`TagIndices`, O(изменившееся)),
свой Skia-рендер мимо дерева контролов Avalonia, дедупликация выражений в
`code.bin`, realtime из кольца без диска, лимиты истории на сервере.

Риски и гашение:

| Риск | Гашение |
|---|---|
| Мусор на кадр: список визуалов пересобирается каждый Render, `SKTypeface` создаётся на каждый текст | Кэш шрифтов/картинок/SVG (SymbolCache уже есть), переиспользуемые буферы |
| Volatile-привязки гоняют ВМ каждый тик | Тик 5 Гц (не vsync); volatile — явный флаг, по умолчанию выключен |
| Интерполяция цвета перерисовывает при каждом дрожании тега | Опциональное квантование: не перерисовывать, если выход стопа изменился меньше порога |
| Огромные схемы (10k+ элементов) | Куллинг по видимому viewport при рендере; эпохи уже O(изменившееся) |
| Hosted-контролы тяжелы (WebView ~100+ МБ) | WebView-виды — редко и по согласованию; тренды/журналы — свои лёгкие контролы |
| Экземпляры шаблонов × выражения | Кэш скомпилированного шаблона; per-instance только TagIndices |
| Скрытые экраны тикают в фоне | Жизненный цикл: ушли с экрана — подписки отменены |

## 13. Разделение работ

**Dev A (данные/пакет):**
- модель схем в `SCADA.Core/Schemes` (чистые данные, без Avalonia — как
  `AlarmRule`; проверяется `DependencyRulesTests`);
- `SchemeSectionWriter/Reader` (schemes/, templates/) + шаг сборки с
  компиляцией выражений в общий пул (по образцу `CompileAlarmRules`) +
  валидации и диагностики в `ProjectBuildService`;
- системные теги аварий: поле `Group` у правила, публикация `@Alarm.*` /
  `@AlarmGroup.*` движком, генерация в каталог при сборке;
- копирование ассетов (symbols/images/fonts) в пакет + ошибки сборки;
- строковые теги (§4.6): `TagDataType.String`, текст в слоте TagTable с
  общими эпохами, `ReadString`/`WriteLocalString` в IRuntimeClient,
  прямые строковые привязки и защита сборки — реализовано (A7).

**Dev B (графика/UI):**
- миграция `SchemeElement` (8 каналов → привязки/разреженные свойства),
  `SchemeCanvas`/`SchemeDrawOperation` под новую модель;
- загрузчик схемы из пакета (`PackageReader` → `Scheme` → исполняемые
  элементы через `CodePool.Expressions[i].TagIndices` — штатное использование);
- чтение символов из пакета; тонирование SVG;
- hit-test по геометрии; слоты hosted-контролов; TrendView/AlarmView;
- попап-оверлей и навигация.

**Граница:** reader отдаёт `Scheme` со связанными `TagId` и индексами
выражений пула; дальше — графика.

## 14. Что осознанно НЕ делаем

- Скриптовый язык (VBS-стиль) — выражения + условные цепочки действий.
- Окна ОС для попапов — внутренний оверлей.
- Чередование z-порядка векторных элементов и контролов.
- Строки в языке выражений (конкатенация и т.п.) — строки живут как тип
  значения тега (§4.6), ВМ остаётся числовой; расширение ВМ — отдельное
  решение, если таблиц стопов и шаблонов текста перестанет хватать.
- WebView-карта и прочая тяжёлая экзотика в v1 — люк расширения заложен
  (§8.4), сама экзотика — по факту запроса.
