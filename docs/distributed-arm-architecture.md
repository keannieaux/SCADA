# Распределённая архитектура АРМов для SCADA

Этот документ описывает архитектуру, в которой несколько автоматизированных рабочих мест (АРМов) операторов работают с одной системой сбора данных. Основная идея — **одно приложение может работать в разных ролях**, а серверная часть может быть как встроена в АРМ-мастер, так и вынесена в отдельный headless-процесс.

---

## Общая концепция

Система состоит из трёх логических частей:

1. **SCADA.Server** — собирает данные с PLC, пишет историю в БД, раздаёт данные клиентам.
2. **SCADA.Client** — Avalonia-приложение с UI, подключается к серверу.
3. **SCADA.Core** — общая библиотека с моделями, сервисами и протоколами.

Один и тот же физический ПК может выполнять роль сервера, клиента или обе роли одновременно.

---

## Компоненты системы

### SCADA.Core

Общая библиотека, которая используется и сервером, и клиентом.

```text
SCADA.Core/
├── Models/
│   ├── Tag.cs
│   ├── TagValue.cs
│   └── Alarm.cs
├── Services/
│   ├── IPlcService.cs
│   ├── ITagHistoryService.cs
│   └── ITagCacheService.cs
├── Protocols/
│   └── TagUpdateMessage.cs
└── ViewModels/
    └── ViewModelBase.cs
```

### SCADA.Server

Headless-приложение на `Microsoft.Extensions.Hosting`.

**Задачи:**
- опрос PLC через Modbus/OPC UA/MQTT;
- хранение истории в PostgreSQL + TimescaleDB;
- публикация текущих значений и аварий;
- обслуживание клиентских подключений.

**Способы запуска:**
- консольный процесс;
- Windows Service;
- systemd service на Linux;
- launchd на macOS.

```text
SCADA.Server/
├── Program.cs
├── WorkerServices/
│   ├── DataAcquisitionService.cs
│   └── ClientBroadcastService.cs
├── Services/
│   └── ModbusPlcService.cs
└── appsettings.json
```

### SCADA.Client

Avalonia desktop-приложение.

**Задачи:**
- отображение мнемосхем, трендов, таблиц тегов;
- управление авариями;
- подключение к серверу.

```text
SCADA.Client/
├── App.axaml
├── Views/
│   ├── MainWindow.axaml
│   ├── HeaderView.axaml
│   └── TagsTableView.axaml
├── ViewModels/
│   ├── MainViewModel.cs
│   └── TagsTableViewModel.cs
└── Program.cs
```

### SCADA.Server.Tray (опционально)

Маленькое приложение в системном трее для управления сервером.

**Задачи:**
- показывать статус сервера;
- запускать/останавливать сервер;
- открывать SCADA.Client.

Этот компонент не обязателен. Альтернатива — управление сервером через `services.msc`, systemd или из GUI клиента.

## Роли ПК на объекте

### 1. Single ARM

Один ПК выполняет все функции.

```text
┌─────────────────────┐
│       ПК 1          │
│  SCADA.Client       │
│  SCADA.Server       │ ← встроен в клиент или отдельный процесс
│  PostgreSQL         │
│  PLC connection     │
└─────────────────────┘
```

**Когда:** один оператор, небольшой объект.

### 2. Master ARM

Один ПК — и сервер, и рабочее место. Остальные ПК — клиенты.

```text
┌─────────────────────┐         ┌─────────────┐
│      ПК мастер      │         │    ПК 2     │
│  SCADA.Client       │◄───────►│ SCADA.Client│
│  SCADA.Server       │  LAN    │             │
│  PostgreSQL         │         └─────────────┘
│  PLC connection     │         ┌─────────────┐
└─────────────────────┘         │    ПК 3     │
                                │ SCADA.Client│
                                └─────────────┘
```

**Когда:** 2–10 АРМов, объект небольшой, не критична отказоустойчивость.

### 3. Dedicated Server

Сервер вынесен на отдельный ПК или VM. Все АРМы — клиенты.

```text
┌─────────────────────┐         ┌─────────────┐
│   Сервер сбора      │         │    ПК 1     │
│   SCADA.Server      │◄───────►│ SCADA.Client│
│   PostgreSQL        │  LAN    │             │
│   PLC connection    │         ├─────────────┤
└─────────────────────┘         │    ПК 2     │
                                │ SCADA.Client│
                                ├─────────────┤
                                │    ПК 3     │
                                │ SCADA.Client│
                                └─────────────┘
```

**Когда:** более 10 АРМов, критичная стабильность, сервер должен работать 24/7.

### 4. Client-only ARM

ПК, который только подключается к серверу и не выполняет серверных функций.

**Когда:** рабочие места операторов, диспетчерские пункты, начальник смены.

## Режимы запуска SCADA.Server

| Режим | Описание | Использование |
|---|---|---|
| **Console** | Запуск в консоли, видны логи | Разработка, отладка |
| **Windows Service** | Фоновая служба Windows | Production на Windows |
| **systemd** | Фоновый сервис Linux | Production на Linux |
| **launchd** | Фоновый сервис macOS | Production на macOS |
| **Tray-managed** | Запускается и управляется из SCADA.Server.Tray | Удобство для мастер-АРМа |

## Взаимодействие компонентов

### Client ↔ Server

Клиенты подключаются к серверу по сети.

**Рекомендуемые транспорты:**

| Транспорт | Когда использовать |
|---|---|
| **gRPC streaming** | Надёжное двунаправленное соединение, контракты |
| **MQTT** | Лёгкий pub/sub, стандарт для IoT |
| **SignalR** | Если уже используется стек ASP.NET |

**Данные, которые передаются:**
- текущие значения тегов;
- изменения значений (по подписке);
- аварии и события;
- команды на сервер (квитирование аварии, ручное управление);
- исторические данные для трендов.

### Server ↔ PLC

Сервер опрашивает или принимает данные от оборудования.

| Протокол | Оборудование |
|---|---|
| **Modbus TCP/RTU** | ПЛК, частотники, счётчики |
| **OPC UA** | Промышленные контроллеры, SCADA-интеграция |
| **MQTT** | IoT-устройства, облачные шлюзы |
| **S7** | Siemens |

### Server ↔ Database

Сервер пишет историю в реляционную или time-series БД.

| БД | Когда использовать |
|---|---|
| **SQLite** | Прототип, один АРМ |
| **PostgreSQL + TimescaleDB** | Несколько АРМов, долгосрочная история |
| **InfluxDB** | Высокочастотные данные, облако |

## Сценарии использования

### Сценарий 1: Запуск на мастер-АРМе

1. Устанавливаешь `SCADA.Client.exe` и `SCADA.Server.exe` на ПК мастера.
2. Запускаешь `SCADA.Server.exe` как службу или из трея.
3. Запускаешь `SCADA.Client.exe` — он подключается к `localhost`.
4. На остальных ПК устанавливаешь только `SCADA.Client.exe` и указываешь IP мастера.

### Сценарий 2: Выделенный сервер

1. На серверном ПК устанавливаешь `SCADA.Server.exe` и PostgreSQL.
2. Регистрируешь сервер как службу.
3. На всех АРМах устанавливаешь `SCADA.Client.exe`.
4. Все клиенты подключаются к серверу по IP.

### Сценарий 3: Переключение GUI ↔ headless

- GUI-клиент может запускать сервер как отдельный процесс.
- При закрытии GUI сервер может продолжать работать.
- Повторный запуск GUI подключается к уже работающему серверу.

## Плюсы выбранной архитектуры

| Плюс | Описание |
|---|---|
| **Гибкость развёртывания** | Один и тот же софт может быть сервером, клиентом или и тем, и другим |
| **Простота установки** | На мастер-АРМ ставятся оба компонента, на остальные — только клиент |
| **Масштабируемость** | При росте можно вынести сервер на отдельный ПК без переписывания кода |
| **Кроссплатформенность** | Сервер работает на Windows/Linux/macOS, способ запуска — платформенно-зависим |
| **Отделение UI от сбора данных** | Сервер работает стабильно, независимо от того, открыт ли GUI |
| **Удобство обновления** | Можно обновлять клиентов, не трогая сервер, и наоборот |

## Минусы и решения

| Минус | Решение |
|---|---|
| Единая точка отказа (мастер) | Резервный мастер, standalone-режим клиентов, watchdog |
| Нагрузка на мастер | Вынести сервер на выделенный ПК, БД на отдельный сервер |
| Зависимость от сети | Локальная сеть, резервный канал, кэш последних данных на клиенте |
| Нужно настраивать IP сервера | Автообнаружение в LAN, конфигурационный файл |
| Безопасность | Авторизация, TLS, firewall, VLAN |

## Эволюция системы

| Этап | Архитектура |
|---|---|
| **Прототип** | Single ARM, SQLite |
| **Маленький объект** | Master ARM + 2–5 клиентов, PostgreSQL на мастере |
| **Средний объект** | Dedicated Server + 5–20 клиентов, PostgreSQL на сервере |
| **Большой объект** | Кластер серверов / MQTT-брокер + 20+ клиентов, Redis, InfluxDB |

## Рекомендации по выбору

| Условие | Рекомендация |
|---|---|
| 1–3 АРМа | Single ARM, сервер встроен в клиент |
| 3–10 АРМов | Master ARM + клиенты, PostgreSQL на мастере |
| 10–50 АРМов | Dedicated Server, MQTT или gRPC |
| Критичная отказоустойчивость | Резервированный сервер + резервный PLC-шлюз |
| Нужен web в будущем | Добавить HTTP/gateway слой между сервером и веб-клиентом |

## Ключевые принципы

1. **Сервер не знает про UI.** Он собирает данные и раздаёт их по сети.
2. **Клиент не знает про PLC.** Он получает данные от сервера.
3. **SCADA.Core — единый источник истины.** Модели и контракты общие.
4. **Сервер запускается отдельно от GUI.** GUI может быть закрыт, сервер работает.
5. **Способ запуска сервера зависит от ОС**, но сам код сервера кроссплатформенный.
