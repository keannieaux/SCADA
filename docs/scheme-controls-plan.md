# Контролы как участники схемы — план

**Дата:** 2026-08-20
**Исполнители:** A (модель, формат, каталоги, валидация) + B (контролы,
диспетчеризация, трассировка)
**Относится к:** `docs/visualization-concept.md` §5.2–5.3, §8.4–8.6;
`docs/session-tags-concept.md`

---

## 1. Цель

Сделать hosted-контрол полноценным участником схемы, а не картинкой
с внутренней жизнью. Сегодня тренд и журнал умеют показывать, но не умеют
ни сообщать о происходящем внутри, ни отдавать своё состояние наружу —
значит их нельзя встроить в логику экрана без правки кода контрола.

Побочная, но не менее важная цель: сделать **добавление действия дешёвым**.
Сейчас новый тип действия — это правка в пяти местах, и именно это, а не
число типов, ограничивает развитие.

**Результат, по которому проверяем:** инженер сдал проект; приходит запрос
«у оператора плохое зрение, он не видит мелких кнопок в тулбаре тренда» —
и доработка делается **проектом**, без единой строки кода: две большие кнопки
на схеме, привязка режима к сессионному тегу, индикация активного режима сама.
Второй проверочный сценарий: «выбрал строку в журнале — кнопка рядом квитирует
именно её».

---

## 2. Что делаем и чего не делаем

**Делаем:** каталог действий с метаданными, выражения в параметрах действий,
дескрипторы событий контролов, событие изменения свойства с ограничениями,
действие «задать свойство элемента», признак автоматического действия
в аудите.

**Не делаем — сознательно:** скриптовый движок, циклы, пользовательские
переменные (их роль выполняют сессионные теги), двусторонние привязки
(петля по построению). Границы записаны в концепции §5.2 и §8.6.

## 3. Этапы

### C1. Каталог действий (Dev A)

Сегодня список действий размазан по четырём местам: иерархия типов,
дискриминаторы JSON, байтовый тип в секции с литералом границы в читателе
и таблица §5.3. Свойства элементов описаны дескрипторами `ElementSchemas`,
и панель свойств редактора генерируется из них; панель действий пришлось бы
хардкодить.

- `ActionCatalog` по образцу `ElementSchemas`: тип, отображаемое имя, список
  параметров (имя, тип, обязательность, признак «может быть выражением»),
  применимость к событиям, версия.
- Писатель и читатель секции берут байтовый тип из каталога; литерал
  `type > 6` заменяется проверкой по каталогу.
- Валидация параметров при сборке — из каталога, а не из кода каждого типа.

**Приёмка:** архитектурный тест «каждый наследник `SchemeAction` есть
в каталоге» (иначе действие однажды тихо пропадёт при чтении); round-trip
секции; неизвестный тип пропускается с предупреждением.

### C2. Выражения в параметрах действий (Dev A)

Главный рычаг против размножения типов: `IncreaseTag`, `DecreaseTag`,
`CopyTag`, `SetTagFromTag`, `ScaleTag` — это один `WriteTag` со значением
`Тег + 1`, `ДругойТег`, `Уставка * 0.9`.

- Значение действия — константа **или** выражение; выражения компилируются
  в общий пул `code.bin` при сборке, в секции лежат индексы (как условия
  действий сегодня).
- Строковый тег в выражении — ошибка сборки (переиспользуется существующий
  `StringTagGuard`), сессионный тег — разрешён.
- Параметры навигации (`OpenScheme`/`OpenPopup`) — тем же механизмом, чтобы
  «открой окно насоса, выбранного в списке» работало без новых действий.

**Приёмка:** запись вычисляемого значения на демо-схеме; ошибка сборки
на строковом теге в выражении; round-trip.

### C3. Дескрипторы событий контролов (Dev A + список от Dev B)

События сегодня — фиксированное перечисление: указательные и жизненный цикл
экрана. У типа контрола должен быть свой список, объявленный дескриптором,
как объявлены свойства.

- `ControlSchemas`: для `ControlType` — список событий (имя, отображаемое имя,
  параметры события).
- Формат: запись события получает имя и **префикс длины** — сейчас это
  единственная запись в секции схем без него, а расширять её придётся.
- Валидация: событие, которого нет у этого типа контрола, — ошибка сборки.

**Нужно от Dev B до начала:** какие события реально нужны `TrendView`
и `AlarmView`. Проектировать дескрипторы под воображаемые случаи
бессмысленно.

**Приёмка:** round-trip именованного события; ошибка на несуществующем
событии; неизвестное событие в пакете от более новой версии пропускается.

### C4. Событие изменения свойства (Dev A — модель, Dev B — исполнение)

- Модель: событие с указанием свойства, дальше обычная цепочка действий.
- **Ограничение 1 (Dev A, ошибка сборки):** событие изменения допустимо
  только на свойстве, которым не управляет привязка. Иначе тег, меняющийся
  десять раз в секунду, породит десять записей в контроллер, каждую с аудитом.
- **Ограничение 2 (Dev B):** гашение по равенству — новое значение равно
  текущему, события нет.
- **Ограничение 3 (Dev B):** предел глубины каскада (порядка восьми);
  превышение обрывает цепочку и пишет в журнал. Петли бывают не прямые,
  а через два-три элемента — статически их не поймать.
- **Ограничение 4 (Dev A):** признак автоматического действия в аудите (C6).

**Приёмка:** «выбрали строку в журнале → кнопка квитирует выбранную»;
ошибка сборки на событии изменения у привязанного свойства; искусственная
петля обрывается на пределе глубины и попадает в журнал.

### C5. Действие «задать свойство элемента» (Dev A — модель, Dev B — исполнение)

Для состояний без памяти и без индикации: сбросить масштаб, снять выделение,
свернуть панель. Не альтернатива тегам — второй инструмент.

- Адресация по имени элемента, разрешается в границах экрана, а внутри
  экземпляра шаблона — в границах экземпляра.
- Валидация при сборке: элемент существует, свойство у его вида существует
  и анимируемо.

**Приёмка:** кнопка внутри экземпляра шаблона попадает в своё окно, а не
в чужое; ошибка сборки на несуществующем элементе или свойстве.

### C6. Признак автоматического действия в аудите (Dev A)

Пока запись в тег инициирует человек кликом, логина сессии достаточно.
С появлением C4 в журнале появятся записи без человека — и «кто нажал»
перестанет быть ответом.

- Поле в `AuditEntry` и в схеме `events.db`: выполнено оператором или
  автоматически по цепочке; желательно источник — экран и элемент.
- Заполняется исполнителем действий.

**Приёмка:** запись по клику и запись по цепочке различимы в журнале.

### C7. Трассировка цепочек (Dev B, формат согласуем)

Диагностический режим: что сработало, какое действие выполнилось, с какой
глубиной. Каскад невозможно разобрать по симптомам на объекте — без
инструмента первая же проблема превращается в гадание.

## 4. Порядок и зависимости

```
C1 (каталог) ──► C2 (выражения) ──► C4 (событие изменения) ──► C6 (аудит)
      └────────► C3 (события контролов) ──► C4
      └────────► C5 (задать свойство)
```

C1 первый: он делает дешёвыми все остальные. C2 независим от контролов
и полезен сам по себе — им можно закрывать проекты, пока идёт остальное.
C3 требует входных данных от Dev B.

Формат схем меняется в C1–C5; версия секции остаётся 1, **пакеты
пересобираются** (до релиза совместимость не поддерживается).

## 5. Открытые вопросы

- **Момент срабатывания события изменения:** немедленно по ходу пересчёта
  привязок или после того, как весь кадр посчитан. Немедленно проще
  и понятнее инженеру, но именно это даёт вложенность; отложенно
  предсказуемее, но появляется очередь и вопрос «что если в очереди то же
  свойство дважды».
- **Нужен ли дебаунс** у события изменения, если ограничения 1–2 окажется
  мало на реальных экранах.
- **Адресация внутри вложенных шаблонов** (экземпляр в экземпляре):
  достаточно ли границы ближайшего экземпляра.
- **Кто генерирует панель действий в редакторе** — из каталога C1
  автоматически или редактор описывает представление отдельно.
- **Состав событий и выходных свойств** `TrendView` и `AlarmView` — от Dev B.
