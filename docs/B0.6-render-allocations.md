## 1. Результат

Стенд твой, без изменений: `dotnet run -c Release --project SCADA.Benchmarks -- --filter '*SchemeRendering*'`.
Машина Ryzen 5500GT, ShortRun (3 итерации) — времена порядковые, разброс до ±50 %; **аллокации детерминированы, им можно верить точно**.

| Элементов | Tick до | Tick после | Render до | Render после |
|---|---|---|---|---|
| 500 | 112 мкс / 109 КБ | **46 мкс / 0 Б** | 2,92 мс / 262 КБ | **1,45 мс / 78 КБ** |
| 1000 | 229 мкс / 219 КБ | **90 мкс / 0 Б** | 5,84 мс / 524 КБ | **2,93 мс / 156 КБ** |
| 2000 | 463 мкс / 438 КБ | **200 мкс / 0 Б** | 12,1 мс / 1,05 МБ | **6,41 мс / 313 КБ** |

Критерий из `scheme-rendering-benchmark.md` §5.1 (1000 элементов: Render ≤ 8 мс, аллокации в разы ниже 524 КБ) — **выполнен**: 2,93 мс и 156 КБ.

`Tick` теперь не аллоцирует вообще — ноль байт и ноль сборок Gen0 на всех трёх размерах, при том что пересчитываются все элементы и все они volatile.

Кадр целиком (Tick + Render) на 1000 элементах: было 743 КБ, стало 156 КБ. При 30 FPS это **4,7 МБ/с вместо 22 МБ/с** — твоё опасение из вывода 4 («~30 МБ/с мусора, частые Gen0 на 4-ГБ машине») снято.

## 2. Что менялось на стороне графики

Все правки в `SCADA.Graphics`, логика движка не тронута — эпохи, `IsDirty`, куллинг, стопы работают как работали.

| Пункт §5.1 | Что сделано | Файл |
|---|---|---|
| кэш `SKTypeface`/`SKFont` | шрифт вынесен в `static readonly` (твой рефакторинг `DrawItems` затёр нашу прежнюю правку — вернули) | `SchemeDrawOperation.cs` |
| кэш `SKPaint` | фиксированные кисти статические, заливки — словарь по цвету | `SchemeDrawOperation.cs` |
| статика в `SKPicture` | элементы без привязок пишутся один раз в `SKPicture`, кадр стоит один `DrawPicture` | `SchemeCanvas.cs`, `SchemeDrawOperation.cs` |
| текст только при изменении | последнее сырое значение и готовая строка кэшируются в элементе | `SchemeElementRuntime.cs`, `SchemeCanvas.cs` |

Сверх твоего списка, по факту профиля, убрали ещё четыре источника мусора в цикле пересчёта — это и увело `Tick` в ноль (219 КБ → 0 на 1000):

- `binding.Expression.ToExpression()` вызывался на каждую привязку каждый тик — теперь `CompiledBinding` хранит готовый `Expression`, конвертация делается один раз при компиляции схемы (см. §3);
- `AllTagIndices.Any(index => ...)` — лямбда захватывала `context`, то есть замыкание плюс делегат на каждый элемент; заменено обычным циклом;
- `foreach` по `IReadOnlyList<CompiledBinding>` боксировал энумератор — заменено индексным циклом;
- то же в `PickDiscrete` по `IReadOnlyList<Stop>` — соседний `Interpolate` был написан индексным циклом и изначально чист.

Общая закономерность на будущее: в этом цикле любой `foreach` по интерфейсу коллекции и любая LINQ-лямбда с захватом стоят аллокации на элемент на кадр. При 1000 элементов и 30 FPS это десятки мегабайт в секунду на ровном месте.

**Совместимость:** формат пакета, байткод и публичные контракты не затронуты. `DrawItems` получил параметр `SKPicture? staticPicture = null` со значением по умолчанию — твой `SchemeRenderingBenchmarks.cs` компилируется и работает без правок.

## 3. Просьба: `Expression` как `readonly struct`

**Не срочно и не блокирует.** Речь про ловушку в API, а не про живой баг.

`SCADA.Expressions/Expression.cs` — это `sealed class` с двумя полями-ссылками:

```csharp
public sealed class Expression
{
    public required byte[] Code{get; init;}
    public required double[] Constants{get; init;}
}
```

Из-за этого `CompiledExpression.ToExpression()` (`SCADA.Expressions.Compiler/CompiledExpression.cs:17`) **аллоцирует новый объект на каждый вызов**, хотя оба массива неизменны и просто перекладываются по ссылке. Мы звали его в цикле пересчёта 30 раз в секунду на каждую привязку — это и был самый крупный источник мусора в `Tick`.

У себя мы это уже обошли: конвертируем один раз при компиляции схемы. У тебя в `AlarmEngine` та же схема — `RuleRuntime.Condition` хранит готовый `Expression`, так что и там аллокации нет. То есть **прямо сейчас чинить нечего** — просьба в том, чтобы на грабли нельзя было наступить снова.

Предложение: сделать `Expression` структурой — два поля-ссылки, 16 байт, передаётся в `ExpressionVM.Evaluate` по значению не дороже указателя:

```csharp
public readonly record struct Expression
{
    public required byte[] Code{get; init;}
    public required double[] Constants{get; init;}
}
```

Тогда `ToExpression()` перестаёт быть аллокацией в принципе, и любой будущий вызов в горячем цикле безопасен.

Что придётся поправить (всё в твоей зоне, по мелочи):

- `SCADA.Alarms/Engine/RuleRuntime.cs:24` и `SCADA.Alarms/PreparedAlarmRule.cs:17` — `Expression? Condition` станет `Nullable<Expression>`. Паттерны `is { } condition` продолжат работать, но прямые разыменования потребуют `.Value`.
- `SCADA.Benchmarks/ExpressionBenchmarks.cs:13` — `private Expression _expr = null!;` перестанет компилироваться, нужен обычный `_expr;`.
- `default(Expression)` станет возможен, а `required` от него не защищает — если это важно, стоит либо проверять `Code is null` на входе в ВМ, либо зафиксировать инвариант комментарием.

Если решишь, что цена миграции выше пользы — это нормальный ответ, у нас всё уже работает. Просто хотел, чтобы ты знал, где лежат грабли.

## 4. Вопрос: нужно ли вписывать схему в окно

Всплыло на B2 — схемы поехали из пакета, и стало видно, что поведение при несовпадении авторского размера с окном нигде не описано.

В `ElementSchemas.SchemeProps` есть `DesignWidth` (id 101, умолчание 1920), `DesignHeight` (102, 1080) и `StartZoom` (103, 1.0). Читаем пока только `Background` и `StartZoom`. Прогрепал `visualization-concept.md`, `visualization-plan.md` и остальные документы — про вписывание схемы в окно нет ни строчки.

**Со смыслом самих полей вопросов нет.** Попап всё объясняет: у шаблона те же свойства уровня схемы, и если инженер задал шаблону 300×300, то оверлей должен быть ровно 300×300 — вписывать его не во что, он сам себе размер. Значит `DesignWidth/Height` — это авторский размер поверхности, одинаково для схемы и для шаблона.

**Открыт вопрос политики отображения**, и он, похоже, решается по-разному для двух случаев:

- **Попап** рисуется своим размером и центрируется в окне. Масштабировать его бессмысленно — размер задан осознанно, под содержимое.
- **Полноэкранная схема** — вот тут выбор. Сейчас канва рисует **1:1** в координатах файла: `StartZoom = 1` значит один пиксель схемы = один пиксель экрана, левый верхний угол в начале координат. Схема меньше окна — справа и снизу пусто; больше окна — часть уезжает за край, оператор доводит панорамированием.

Два варианта для экрана:

1. **Оставить 1:1.** Инженер рисует под конкретное разрешение АРМ, `StartZoom` — начальный зум для ручного разглядывания. Просто и предсказуемо, но на панели меньшего разрешения часть дежурного экрана окажется за краем, и оператор увидит её только панорамированием.
2. **Вписывать `DesignWidth/Height` в доступную площадь** (равномерно, с полями по короткой стороне), `StartZoom` — множитель поверх вписывания. Тогда одна схема на АРМ 1920×1080 и на панели 1366×768 выглядит одинаково по компоновке. Так обычно ведут себя HMI на панелях с разным разрешением.

Нам нужен только твой выбор. Реализация наша в любом случае: вариант 1 — не делаем ничего, вариант 2 — десяток строк в `SchemeCanvas`. Ничего не блокирует, B2 закрыт и работает.

Если вариант 2 — заодно реши, обрезать ли схему по проектной области: сейчас элемент, нарисованный за пределами `DesignWidth`, всё равно виден, и при вписывании он вылезет на поля.

## 5. Что подтвердилось на твоей стороне

Проверял специально, претензий нет:

- `ExpressionVM.Evaluate` — `stackalloc` под стек ВМ, аргументы встроенных функций передаются срезом `Span` без копий. Аллокаций **ноль**.
- `BuiltinFunctions.Get(id)` — делегат из статической таблицы, тоже ноль.
- `now()` и оператор `%` из B0.4 отработали ровно как задумано: непрерывное вращение по `now() * 90 % 360` идёт плавно, `NowUnixMs` заполняется на нашей стороне при создании контекста.

## 6. Что дальше

Твой пункт §5.5 (dirty-rect при 2000+ анимаций на целевом железе) пока не нужен: 2000 элементов дают 6,4 мс на кадр против бюджета 33 мс, и это на CPU-поверхности без GPU. Вернёмся к нему по факту замера на целевом АРМ (ТЗ §4.1, M8).

**B2 закрыт** уже после написания этого документа: схема грузится из `.scadapkg` через `GetScheme`, привязки берутся из пула по `CompiledExpressionIndex`, действия резолвятся через `TryGetTagId`, символы — ассетами пакета (`GetAsset("symbols/имя.svg")`), диск не используется вообще. Контракт A6 подошёл без единой доработки с твоей стороны. Ручной сборки схемы в коде больше нет.

Из мелкого, что выяснилось по дороге: `SymbolName` — это имя файла **с расширением** (`pump.svg`), сборщик подставляет его в `symbols/<имя>` как есть. Мы сначала записали `pump` — и `CheckAssetsExist` честно поймал это ошибкой сборки ещё до запуска. Работает как задумано.
